**Version:** 0.1 (pre-1.0; wire compatibility NOT guaranteed across 0.x minor versions)
**Status:** Draft
**License:** Apache 2.0
**Website:** https://volley.systems
**Repository:** https://github.com/kryptek/volley

## 1. Overview

Volley is a protocol for inter-agent coordination on a single machine, a single LAN, or across the internet. It defines:

- A topic hierarchy for addressing agents and channels
- A JSON payload envelope shared by all messages
- Lifecycle states agents publish on the `status` channel
- QoS and retention conventions per channel
- A registry for discovery
- A crash-detection mechanism via MQTT Last Will and Testament
- Conformance requirements (MUST / SHOULD / MAY)

Volley is **transport-agnostic**. The reference implementation uses MQTT v5; conforming implementations MAY use any transport that supports retained messages, wildcard subscriptions, QoS at-least-once delivery, and a Last Will and Testament equivalent.

Volley sits **adjacent to the Model Context Protocol (MCP), not in competition with it**: MCP is how an agent talks to tools; Volley is how agents talk to each other and to humans observing them.

### 1.1 Non-goals (v0.1)

- Agent-to-agent direct streaming (all routing through topics)
- Authentication or authorization (broker-level concern; spec MAY require)
- Message encryption (transport-level concern; spec MAY require `mqtts://`)
- Multi-broker federation (reserved namespace `volley/_system/federation/*` exists; not specified in v0.1)

### 1.2 Terminology

- **Agent** — any process that registers with the broker and publishes/subscribes to Volley topics.
- **Coordinator** — an agent whose primary role is to subscribe to wildcard topics and observe other agents. Not a special protocol-level role; just a usage pattern.
- **Broker** — an MQTT broker (mosquitto for the reference implementation).
- **Conforming implementation** — any client library, MCP server, or CLI that follows the requirements in §11.

### 1.3 Notification (informative)

*Notification is a client-side concern on top of the existing `status` channel. The protocol does not standardize notification semantics — when, where, or how an observer surfaces a state transition to a human is left to each implementation. The reference implementation ships two surfaces in v0.1.3 (`volley notify` CLI and a Settings popover in the web dashboard); both consume the status channel via the standard subscribe mechanism and introduce no new envelope fields, topics, or MCP tools. Conforming implementations MAY ship their own notification UIs against the same channel.*

## 2. Topic hierarchy

Topics follow this structure:

    volley/<namespace>/<agent_id>/<channel>

### 2.1 Namespace

`namespace` is a logical grouping (e.g. `issues`, `homelab`, `cursor-team`). Default value is `default`.

- MUST match `[a-z0-9][a-z0-9_-]{0,62}`
- Cross-team brokers SHOULD use per-team namespaces to prevent registry collisions

### 2.2 Agent ID

`agent_id` is a unique, stable identifier per agent.

- MUST match `[a-z0-9][a-z0-9_-]{0,62}`
- Recommended format: `<slug>-<4-char-random>` (e.g. `issue-42-fix-7a3f`)
- Stable across reconnects of the same logical agent within a session

#### Agent identity at runtime (informative)

A conforming Volley MCP server MUST produce a unique `agent_id` per
process start, unless an assigned identity (§6.5) is present. The
recommended mechanism is:

1. Read the `VOLLEY_AGENT_ID` environment variable as a **prefix** (not
   a literal agent_id). The prefix MUST match the SPEC §2.2 grammar
   restricted to length 1-58 (leaving 5 chars for the `-XXXX` suffix).
   If unset, the implementation MAY derive a per-process prefix from
   another source (e.g. the cwd basename — see `generateAgentId` in
   the volley-mcp reference implementation).

2. Append `-${random}` where `${random}` is a 4-character lowercase-
   alphanumeric value. Sourcing the randomness from a uniform RNG over
   `[a-z0-9]` (36 chars) gives ~20 bits of entropy per suffix, plenty
   for per-machine uniqueness.

3. The resulting `agent_id` MUST satisfy the full SPEC §2.2 grammar
   `[a-z0-9][a-z0-9_-]{0,62}`. A server MUST reject a prefix that would
   produce an out-of-grammar id.

**Why a prefix, not a literal?** Two MCP-server processes spawned from the
same user-scope MCP registration on one machine inherit the same env
block, so a literal `VOLLEY_AGENT_ID` would produce identical agent_ids
and the second to publish would overwrite the first's retained registry
entry. The auto-suffix makes the user-scope-MCP-shared-across-sessions
case correct by default.

**Discovering an agent_id.** Because the suffix is fresh per process,
the agent_id is not knowable ahead of time (unless an assigned identity
(§6.5) is present, in which case the supervisor that wrote it already
knows it). Discovery options:

- The MCP server's `vol_register` tool returns `{ agent_id, namespace }`
  so the calling Claude session learns its own id immediately.
- A peer Claude session calls `vol_list_agents` and finds the agent by
  `capabilities`, `parent_id`, or `cwd`.

**Examples:**

| `VOLLEY_AGENT_ID` env | resulting `agent_id`              |
|-----------------------|-----------------------------------|
| (unset)               | derived from cwd basename — see `generateAgentId` (existing behavior) |
| `coordinator`         | `coordinator-7b9c`                |
| `coordinator-base`    | `coordinator-base-2d8e`           |
| `issue-42-fix`   | `issue-42-fix-4ec0`          |
| `Foo` (uppercase)     | (rejected — fails grammar)        |
| `x` (single char)     | `x-0a3f` (1 + 1 + 4 = 6 chars OK) |

This is INFORMATIVE not NORMATIVE — the grammar at the top of §2.2 is
the only NORMATIVE constraint. A non-MCP Volley client (a CLI, a shell
publisher) MAY use any other mechanism to pick a grammar-conforming
`agent_id`.

**Assigned identity.** When a supervisor has written `.volley/agent.json`
into the agent's working directory, the MCP server uses the literal
`agent_id` from that file instead of the prefix + suffix mechanism above —
see §6.5.

### 2.3 Channel

`channel` is one of the reserved channel names listed in §4.1, OR a user-defined channel under the `_user/*` prefix, OR a supervisor channel defined in §4.6 (informative in 0.1).

### 2.4 Reserved namespaces

The following top-level namespace prefixes are reserved:

- `volley/_system/*` — protocol-level state (registry, broker health, federation config; `volley/_system/federation/coordinator`, the coordinator role's state, §4.6.25)
- `volley/_meta/*` — implementation tooling (debug taps, replay logs, capture files)
- `volley/_waves/*` — supervisor state: wave snapshots, decisions, journal events, effective supervisor config (§4.6)
- `volley-auth/*` — one-time token redemption (§4.6.10), outside the `volley/` root so a broker ACL can confine a token's login to its own two topics

Implementations MUST NOT publish user-space messages under these prefixes. One exception: any agent MAY publish lease requests to `volley/_system/leases/<pool>/requests` (§4.6.5). Every other topic under these prefixes is written only by the broker, the implementation's own tooling, or a supervisor (§4.6).

## 3. Payload envelope

All Volley messages share a common JSON envelope:

```json
{
  "schema_version": "0.1",
  "agent_id": "issue-42-fix-7a3f",
  "parent_id": "coordinator-abcd",
  "wall_time": "2026-05-14T02:11:23.000Z",
  "channel": "status",
  "type": "done",
  "payload": { },
  "correlation_id": "0a4f3e7c-8b21-4f3a-9d2e-1c8f7a3e2b41"
}
```

### 3.1 Required fields

- **`schema_version`** (string) — semver of the Volley protocol. v0.1 implementations MUST emit `"0.1"` and MUST reject envelopes whose major version does not match a supported major. See §8.
- **`agent_id`** (string) — sender's agent ID, MUST match the grammar in §2.2.
- **`wall_time`** (string, ISO-8601 UTC with milliseconds) — sender's wall-clock at publish time. Receivers MUST NOT rely on this for ordering; it is informational.
- **`channel`** (string) — one of the reserved channels (§4.1), a `_user/*`-prefixed user channel, or a supervisor channel defined in §4.6.
- **`type`** (string) — channel-specific event type (e.g. `done` on the `status` channel, `tests-green` on `progress`).

### 3.2 Optional fields

- **`parent_id`** (string | null) — if the publishing agent was spawned by another Volley agent, the parent's `agent_id`. Used to build dispatch trees.
- **`payload`** (object) — channel-specific data; shape governed by the per-channel schema (§4).
- **`correlation_id`** (string | null) — UUID v4 linking related messages (e.g. mailbox request → mailbox response).

### 3.3 Unknown fields

Receivers MUST accept envelopes containing unknown fields and MUST NOT error on them. This permits forward-compatible spec extensions.

## 4. Channels

### 4.1 Reserved channels

| Channel | QoS | Retained? | Purpose |
|---|---|---|---|
| `status` | 1 | yes | Last-known lifecycle state of an agent (see §5). |
| `progress` | 0 | no | Streaming progress events (e.g. `tests-green`, `mvn-verify-done`). Fire-and-forget. |
| `mailbox` | 1 | no | Inbound requests / commands directed at this agent. Must-deliver. The topic's `<agent_id>` segment identifies the recipient; the envelope's `agent_id` (§3.1) identifies the sender. Not retained, so the broker only holds a message for a recipient with a persistent session (see §4.4); delivery is confirmed end-to-end by an `ack`, not by PUBACK. |
| `control` | 1 | no | Reserved for agent control (`kill`, `pause`, `resume`, `nudge`). Reserved in v0.1; semantics deferred to v0.2+. |
| `result` | 1 | yes | Final artifact pointer (PR URL, log path, deploy summary). |
| `capability` | 1 | yes | Tools / models this agent advertises. |

### 4.2 User-defined channels

User-defined channels MUST use the `_user/<name>` prefix. v0.1 does not constrain user-defined channel QoS or retention; that is a deployment concern.

### 4.3 Publishing requirements

Conforming agents MUST:

- Publish to the `status` channel with the correct lifecycle `type` (see §5) at the corresponding state transitions
- Use the QoS and retention values in §4.1 for reserved channels

Conforming agents SHOULD:

- Publish `progress` events at meaningful checkpoints
- When the agent can estimate a percent-complete, include `payload.progress` as a number in `[0, 100]` on `progress` and/or `status` envelopes — dashboards and coordinators use it to render determinate progress bars instead of indeterminate sweeps. Implementations MUST treat the field as advisory (an estimate from the agent itself) and MUST tolerate `null`, missing, or non-numeric values by falling back to the last seen value or to an indeterminate display.
- Publish a `result` retained message before terminal `status` so late-attaching tools can see the artifact pointer

**Hook activity events (informative).** The `status` state machine (§5.3) is linear, so non-terminal attention states are not status types. A harness hook (e.g. a Claude Code hook running beside the agent) reports them on the `progress` channel instead, with `payload.source: "harness-hook"`, a per-agent monotonic `payload.seq`, and the `payload.hook_event` that fired. The documented types are `heartbeat` (the agent is alive and doing something), `idle` (the turn ended; `payload.text` carries the last assistant line, and `payload.completed: true` says the harness reported the task completed), `awaiting_input` (the harness is waiting on a human; `payload.text` / `payload.notification_type` carry the notification, `payload.screen_tail` MAY carry the last terminal lines, and `payload.class` says why the harness is waiting when it is not a question, e.g. `credit` for a provider usage limit that the harness resumes from on its own; `payload.background_wait: true` says the session ended its turn without a question while a background task it started is still running, so it is waiting on that task's events, not on a human: a dashboard SHOULD NOT present it as needing a person, and a supervisor SHOULD treat it as a wait on the agent's own work, not idleness (no "continue" nudge, no stall alarm, for a bounded time). `background_wait` MAY also be set on the `idle` that ended such a turn, and is never set on a `permission_prompt` or on an `awaiting_input` that carries a question the turn ended on), `resumed` (the agent is working again; it clears any earlier `awaiting_input`), `activity` (a work-log line: `payload.msg` is one line of at most 120 characters saying what the session just started, e.g. `Bash: gh pr checks 153` for a tool call with secrets redacted, or `prompt received` for a new prompt, whose text is never published; `payload.tool_calls` counts this session's tool calls so far (a new session, not a resumed or compacted one, starts again from zero); a hook publishes at most one line per 5 s, and the newest line held back in a window is published at the next slot, so the last call of a burst is not lost; the `idle` that ends a turn carries `tool_calls` too; a tool call's `activity` from `hook_event: "PreToolUse"` also carries its boundary, `payload.tool_use_id` (the harness's id of the call) and `payload.tool` (the tool's name), and is published for every call, outside the 5 s limit: inside it, the boundary goes out without `msg` / `tool_calls`; the `heartbeat` from that call's `PostToolUse` carries the same `tool_use_id` and `tool`, the end of the call; between the two a tool is in flight, and a supervisor SHOULD NOT treat the silence of a long foreground tool call as broken hooks), `picker_opened` (the harness put a question picker to its user, e.g. Claude Code's `AskUserQuestion`: `payload.tool_use_id` names the tool call and `payload.questions` is the tool input's `[{ question, header, options: [{ label, description }], multiSelect }]`, verbatim; a coordinator's also carries `session_url` / `workspace` when known), `picker_answered` (that picker was answered, wherever: `payload.tool_use_id` and `payload.answers`, the harness's question → answer map; several labels of a multi-select answer are joined with `, `) and `steering_applied` (reserved: a hook MAY publish it when it injects mailbox steering into the session; the reference hooks ack the mailbox message instead and do not publish it). For a coordinator session, `awaiting_input` additionally carries `payload.question` (what it is asking: the reference hooks send the question paragraph whole, or an excerpt of its end beyond 8192 characters; a supervisor's wave-state `coordinator.question`, §4.6.1, carries only its first one or two lines), `payload.session_url` and `payload.workspace` when known, so a dashboard can surface and link the waiting session; the coordinator's registry entry carries the same `session_url` / `workspace` when known, and `workspace_title`, the workspace's title in the terminal multiplexer, when the hook can read it. A registry entry whose `model_source` is one a hook sets (`harness-hook` or `unknown`; not `self-reported`) with no `parent_id` and no wave task is an interactive **session** rather than a dispatched agent: a dashboard SHOULD present it as one (its purpose from `workspace_title` and the basename of `cwd`; working or idle from these events, not from its `status`, which stays `working`). When the model itself has acted on a steering message it publishes `type: "steering_acked"` with `correlation_id` set to that mailbox message's id. A hook that re-publishes the registry entry with the harness-reported model sets `payload.model_source: "harness-hook"`, or `"unknown"` when the hook input carries no model. A registry entry without `model_source` (an agent's own `vol_register`, including the reference MCP server's auto-registration) carries a self-reported `model`, if any; the value `"self-reported"` is reserved for publishers that want to say so explicitly. The `type` field stays an open string; observers ignore progress types they do not recognise. A broker delivers one copy of a message per matching subscription, so an observer MAY treat byte-identical `progress` messages as one delivery; a publisher that can send the same content twice includes `seq` to keep them distinct. See `spec/schemas/progress.schema.json`.

### 4.4 Mailbox message types

The `mailbox` channel's `type` field is one of:

- `steering` — free-text guidance to redirect or inform the agent
- `cancel` — request the agent to abort its current task
- `nudge` — a lightweight prod to re-evaluate or report status
- `query` — a question expecting a response (typically correlated via `correlation_id`)
- `ack` — the recipient's confirmation that it received a mailbox message (see below)

This list matches the `type` enum in `spec/schemas/mailbox.schema.json`.

**Message ids.** A mailbox message's `correlation_id` is its message id. Senders SHOULD set it to a fresh UUID unless they are deliberately correlating with an earlier message (a `query` reply, an `ack`); a message without one cannot be acked. The reference `vol_send_mailbox` generates it when the caller omits it and returns it as `message_id`.

**Optional payload fields.** In addition to the required `text`:

- `seq` — a non-negative integer, monotonic per sender, so a recipient can order messages and drop duplicates
- `supersedes` — the message id of an earlier message from the same sender that this one replaces; a recipient that has not yet acted on the earlier message SHOULD act on this one instead

**Acks.** A recipient acknowledges a message by publishing `type: "ack"` to the **sender's** mailbox (`volley/<ns>/<sender agent_id>/mailbox`) with `correlation_id` set to the acknowledged message id. `correlation_id` is REQUIRED on an `ack`. The payload SHOULD be `{ "text": "ACKED", "acked_type": "<type of the acknowledged message>" }`, plus `seq` when the acknowledged message carried one. A sender waiting for an ack MUST only accept one whose envelope `agent_id` is the recipient it addressed. An ack means *received*, not *obeyed*: acting on the message is reported through the agent's normal channels. Recipients MUST NOT ack an `ack`. A broker that enforces ACLs (§11.5) must let a recipient write each sender's mailbox for its ack to arrive: the reference roles (§4.6.13) let an agent login write the mailboxes of the fixed steering identities, `volleyd` and `desk`, and no other, with no per-agent grant; the broker silently drops any other ack. A coordinator session's agent id is random-suffixed (`coordinator-ab12`), which no static role can name, so an agent's ack to a coordinator is dropped and the coordinator's `wait_ack_ms` reports `acked: false`; steering that must be confirmed goes through the supervisor (whose mailbox every agent can ack) or the Desk.

**Delivery.** Because mailbox messages are not retained, the broker drops a message published while the recipient holds no subscription to its mailbox. An agent that honours its mailbox (§11.3) MUST therefore keep its mailbox subscription in a **persistent MQTT session** (a live subscription on a clean session still loses whatever arrives before it subscribes or while it reconnects): connect with `clean: false` (MQTT 3.1.1) or a non-zero session expiry interval (MQTT 5), with a stable clientId it owns exclusively, and subscribe at QoS 1. The broker then queues messages while the agent is offline and delivers them on its next connect. Two clients that connect with the same clientId kick each other off, so each persistent consumer of one agent (e.g. the MCP server and a hooks drain client) MUST use its own clientId, such as `volley-<agent_id>-mcp` vs `volley-<agent_id>-hooks`. A session expiry interval applies to new connections only: an existing persistent session keeps the expiry it was created with until the client reconnects. A sender that needs confirmation SHOULD wait for the `ack` rather than trust PUBACK, which only confirms receipt by the broker.

**No live recipient.** A supervisor asked to steer a task that has no live agent (its last agent retired, the next one not yet registered) MUST NOT publish to a retired agent's mailbox, which nobody drains; it SHOULD queue the message for the task's next agent, deliver it once that agent registers (with the id and `seq` it was queued with), and tell the sender it was queued rather than delivered.

### 4.6 Supervisor topics (informative in 0.1)

A **supervisor** (e.g. the `volleyd` daemon) is an agent that spawns other agents in *waves* — a set of tasks with dependencies, each driven through a review pipeline — and publishes their state for dashboards, panes and coordinators. Supervisor state lives under the reserved `volley/_waves/*` prefix and, for machine-global resources, under `volley/_system/leases/*` and `volley/_system/admission`. These topics are informative in 0.1: a deployment without a supervisor never sees them, and nothing in §11 requires them.

Every message on these topics is a standard envelope (§3) whose `agent_id` is the publisher; the field tables below describe `payload`. Clearing a retained topic means publishing a zero-length retained payload (the MQTT convention), which is not an envelope and is not schema-validated. Ids that appear as topic segments (`<wave>`, `<decision_id>`, `<pool>`) use the §2.1 grammar. Wave ids and lease-pool names MUST NOT be a reserved channel name (§4.1): ACLs that grant per-channel writes through a namespace wildcard (`volley/+/<agent>/status`) would otherwise also match `volley/_waves/<wave>/<channel>` or `volley/_system/leases/<channel>`. Task ids come from the wave file and are case-preserving (`[A-Za-z0-9][A-Za-z0-9_-]{0,62}`, e.g. `T1`).

| Topic | QoS | Retained? | `channel` / `type` | Schema |
|---|---|---|---|---|

| `volley/_waves/<wave>/decisions/<decision_id>` | 1 | yes, while open | `_waves/decisions` / `decision_opened` \| `decision_resolved` | `decision.schema.json` |

#### 4.6.1 Wave state

`volley/_waves/<wave>/state` holds the full current snapshot of one wave, re-published after every change. A late-attaching client needs nothing else to render the wave.

| Field | Type | Meaning |
|---|---|---|
| `wave` | string | Wave id. |
| `version` | integer ≥ 1 | Wave file version (bumped by a versioned re-submission). |
| `owner` | agent id \| null | Coordinator that owns the wave; `null` when orphaned. Either an agent id or a coordinator name (§6.2, in the same grammar): a name is bound to the newest live registry entry carrying it, and that agent acts for the owner (below). |
| `repo`, `release_branch` | string | Where the wave's PRs land. |
| `github` | object | `{ slug, url }`: the repository on GitHub as the supervisor read it for the current plan version (`gh repo view`: `nameWithOwner`, `url`), so a client can link issue `n` as `<url>/issues/<n>`. Absent when it could not be read; never derived from `repo` or a remote. |
| `status` | enum | `running` \| `paused` \| `awaiting_decision` \| `releasing` \| `complete` \| `stopped` \| `archived`. `releasing`: every task is settled and the wave's release train runs (§4.6.19); the wave is `complete` once the owner answers `release_go` `go`. `archived` is published once, with `open_decisions` empty, just before the topic is cleared (§4.6.20). |
| `tasks[]` | object | `{ id, issue, stage, agents, waiting_on?, why_waiting?, host?, host_actual?, host_planned?, host_down?, placement?, base_sha?, pr?, evidence_path?, screen_stale?, queued_steers?, steer_unacked?, last_error?, attempt?, next_retry_at?, reviews_skipped_by_plan?, stage_label?, stage_group?, alarms?, remediation?, synthetic? }`. |
| `tasks[].stage` | enum (closed) | `queued` \| `implement` \| `spec_review` \| `quality_review` \| `fixup` \| `merge_ready` \| `done` \| `blocked` \| `awaiting_decision` \| `cancelled`. |
| `tasks[].agents` | object | Current agent id per role: `implementer?`, `spec_reviewer?`, `quality_reviewer?`, `fixup?`, `rebase?`. |
| `tasks[].waiting_on`, `why_waiting` | string[], string | What the task is blocked on, and a human-readable reason (e.g. `tunnel down to <target>` while a remote host's broker tunnel is down). |
| `tasks[].host` | string | The remote host the task's agents run on (its name from the wave file, the `hosts` tunable or placement, §4.6.15); absent for the supervisor's own host. Per task: every agent of a task runs on the same host. |
| `tasks[].host_actual` | string | The host the task's agents were spawned on, as its `agent_spawned` names it (`local` for the supervisor's own machine). Once a task has spawned, a later plan version never moves it (§4.6.15): every later role and check of the task runs there. |
| `tasks[].host_planned` | string | The host the current plan version writes for a started task, while it differs from `host_actual` (e.g. `auto` after the wave switched to `placement: auto`); absent otherwise, and for a placed task the plan still leaves to placement (`auto`). |
| `tasks[].host_down` | string | While the task's host is a paired machine that is down (§4.6.14): why (`disconnected`, `no heartbeat for 90 s`). Set on every unfinished task on that host, running ones included; absent otherwise. |

**Coordinator names.** A wave's `owner` MAY be a coordinator name (§6.2) rather than an agent id, so the session that owns it keeps it across restarts of its MCP server (each of which gives it a new agent id). The supervisor binds the name to the newest registry entry whose `coordinator` is the name and whose status is not terminal. The bound agent may do whatever the owner may (resolve, pause, resume, stop, steer); any other agent id is refused, naming the owner. When a new agent binds to a name that owns waves, the supervisor journals `owner_reconnected { owner, agent_id, previous_agent_id }` in each of them and re-publishes their state; ownership does not change and nothing is claimed. A claim measures the name's newest binding, never an agent id the name has left: the wave is claimable once that binding's presence (§7.5) is offline past `autopilot.reconnect_grace_s`, so a wave whose `coordinator.state` is `reconnecting` is never claimable. An agent-id owner's wave is claimable as soon as its presence is offline; a quiet connected owner never loses its wave.

**Archiving.** An ended wave (`stopped` or `complete`) is retired by archiving it (§4.6.20): its state is published once with `status: "archived"`, then the retained topic is cleared. A client that attaches later never sees it; a live client sees the final publish, then the clear, and drops the wave.

#### 4.6.2 Decisions

A decision is a question only a human (or the owning coordinator) can answer. It is published retained to `volley/_waves/<wave>/decisions/<decision_id>` while open, MAY be re-published once with `type: "decision_resolved"` and `resolved` set, and is then cleared. Archiving a wave (§4.6.20) closes each of its open decisions the same way, with `resolved: { answer: "archived", by, at }`.

| Field | Type | Meaning |
|---|---|---|
| `decision_id`, `wave` | string | Identity. |
| `task` | task id \| null | `null` for a wave-level decision. |
| `kind` | enum (closed) | One of the decision kinds listed below the table. |
| `question` | string | What needs answering. |
| `options` | string[] | Suggested answers (optional; free text is always allowed). |
| `option_help` | object | Optional: hover text for some of `options`, keyed by the option's text. A client SHOULD show it with the option. |
| `pointers` | object | `{ diff?, transcript?, screen?, pr? }` — where the evidence lives. |
| `opened_at` | date-time | |
| `resolved` | object | `{ answer, by, at }`; required when `type` is `decision_resolved`. |
| `held` | object | Optional, on an open decision only: `{ on: { task?, pr?, issue? }, note?, by, at }`. The decision waits on a blocker (a task of the wave, a PR, an issue; at least one, released when any of them lands), not on a person. |
| `waiting` | task id[] | Optional, on a shared-precondition decision (`repo_untrusted`): every task whose launch parks on it, the opener first. |

**Held decisions.** A decision MAY be held: it stays open (its task stays parked) but waits on a blocker rather than on a person. A hold is set by the `hold` control op `{ decision_id | item, on, note?, wave? }` (`item` being its §4.6.18 inbox item id), under the same ownership rule as `resolve` (§4.6.1; a Desk login on its own account-op topic is the owner, §4.6.18), or by the supervisor itself: under autopilot (§4.6.16), an open red-head decision of a task parked on a flake whose fixer is still at work is held on the fixer task. The supervisor MUST refuse a hold on a task that is the decision's own, unknown, or already `done` or `cancelled`, and SHOULD refuse one on a task that waits on the decision's own task (through `after:`, or an open decision of its own held on it), which would never release. A second hold replaces the first. It is journaled as `decision_held { decision_id, kind, on, note?, by }`; the retained decision and its inbox item carry `held`. While the wave is running, the supervisor MUST release a hold when its blocker (any one, when `on` names several) lands: a task `done` or `cancelled`, a PR merged or closed, an issue closed (checked on its own cadence; for a PR or issue with `gh pr view` / `gh issue view --json state`, at most once per CI poll interval per hold); the `release` op `{ decision_id | item, wave? }` lifts one by hand. A release is journaled as `decision_released { decision_id, kind, why, by }`, removes `held`, and the decision is open in its normal tier again: autopilot's rule for its kind runs again (an escalation it already carries is not journaled twice); a red-head decision SHOULD first read its PR's head and the CI on it again, and a `ci_failed` green now is answered `re-verify`. A supervisor that escalates a held decision to the owner MUST release the hold first. A client MUST NOT escalate a held decision or item to the owner (no "needs you", no pulse); it SHOULD show it with what it waits on. A supervisor that never holds decisions never sets `held`. The supervisor does not auto-hold a decision whose hold was released before.

**Shared preconditions.** A decision about a precondition several launches share rather than about one task (`repo_untrusted`: a repo root's folder trust on one machine, in one Claude profile) is keyed by that precondition, never by the task or attempt that hit it: within a wave, a supervisor MUST keep at most one such decision open per precondition. A later launch that needs the same precondition joins the open decision instead of opening another, journaled as `decision_joined { decision_id, kind, task, role, question, option_help?, agent_id? }`: its task parks on it (`awaiting_decision`, resuming where it was) and is appended to `waiting`, and `question` (and `option_help`) are rendered again to list the waiting tasks; the retained decision is re-published. One answer resumes every waiting task. A launch that hits the precondition once its decision is resolved opens a new one.

**Decision kinds** (one per line; `bun run check:spec-refs` checks the list against `decision.schema.json`):

A boolean has no bounds; an enum (`nudge_on_merge`) is bounded by its values.

**The hard ceiling.** `hard_ceiling` caps the agents the supervisor runs or is starting at once, across every wave and machine: each agent it supervises, launched and still being verified, or spawning (a release stage's agent too), plus one slot for each admitted task of a running wave with no agent live that will spawn its next one: queued for its first agent (its spawn backed off too, not once refused for good), or between pipeline roles in `implement`, `spec_review`, `quality_review` or `fixup` (its reviewers or a fixup still to come: no role of its current step refused for good, and no agent of it retired unverified unless its respawn is on the way).
Those held slots keep admission from handing a new task the slot of a task whose next role is still to come.
A pipeline role's spawn, and an admitted task's first agent (a retry after a backoff, or a resumed wave's backlog), start only while the agents running or starting leave room under the ceiling; held slots never hold a spawn, so tasks waiting on each other's slots never all wait.
A task's stage counts nothing otherwise: a task awaiting a decision or blocked, or one in a paused, stopped or ended wave, holds a slot only while one of its agents is live.
Admission holds a ready task back with `hard ceiling reached: <live>/<hard_ceiling> live agents` in its `why_waiting`.

**Branch updates and agent MCP servers.** `branch_update` is how a supervisor's pipeline brings a PR branch up to date when the release branch moved before the gate.
Under `rebase` the agent rebases onto the release branch and publishes with a lease-guarded force-push.
Under `merge` it merges the release branch into the PR branch and publishes with a normal push: the supervisor MUST NOT instruct any force-push, and accepts the new head only if it descends from the head the update started at.
The mode is fixed when the update starts (a supervisor records it with the step), so a change applies to later updates only.
A PR the host reports as conflicting with the release branch (GitHub's `mergeable: CONFLICTING`) gets no CI at all, so a supervisor MUST NOT hold it for CI or ask the owner about the missing run: it journals `pr_conflicting { pr: { number, url }, head, release_branch, role? }` and starts the update at that head at once, its directive saying the PR conflicts.
While the host is still computing mergeability (`UNKNOWN`) the head is pending, as if CI were running.
`agent_mcp` is which MCP servers a supervisor-launched agent loads.
Under `strict` it loads only the supervisor's own Volley server.
Under `inherit` it also loads the user's own servers (plugins, connectors).
The supervisor MUST name its own Volley server `volley`, so that it takes over a user-scope entry of the same name (such as a coordinator's), and every Volley server in the session carries the agent's identity from `.volley/agent.json` (§6.5), never a coordinator's.
A user entry under another name that runs a Volley server still starts, a second Volley server in the session: at spawn under `inherit` the supervisor SHOULD warn (journal and log) when the profile's `~/.claude.json` `mcpServers` or the worktree's `.mcp.json` has such an entry.
`agent_mcp_allow` narrows `inherit`: when it is non-empty, the supervisor MUST start only the named user servers beside its own, by copying each named entry from the user's configuration on the agent's machine (the profile's `~/.claude.json` user- and local-scope `mcpServers`, and the worktree's `.mcp.json`, the narrower scope winning a name) into the agent's own MCP configuration and loading nothing else.
The worktree's `.mcp.json` comes from the branch checked out, so the supervisor MUST copy an entry of it only when the user approved that server for the repository (Claude Code: `enabledMcpjsonServers` or `enableAllProjectMcpServers`, less `disabledMcpjsonServers`, in the repository's project entry).
A name found nowhere, or only as an entry the supervisor does not copy (unapproved, or of a shape it does not copy), is skipped, and the supervisor SHOULD journal it once per wave and machine (`alarm_raised { alarm: "agent_mcp_allow_missing", name, host }`).
A copied entry may hold the user's secrets: the supervisor MUST NOT journal, log or publish an entry, only its name.
Empty, `inherit` loads every user server.
`strict` gives a minimal, reproducible agent; `inherit` gives it more tools, at the cost of depending on the machine it runs on.

**Auto-compaction.** `agent_auto_compact_pct` is the share of the model's context window at which a supervisor-launched agent's harness compacts its conversation. A supervisor that launches Claude Code agents sets the harness's auto-compact window to that share of the model's window in tokens (`CLAUDE_CODE_AUTO_COMPACT_WINDOW`, clamped to the harness's accepted range) in the launch it renders, for every role; `0` sets nothing and the harness's own default applies. The window is fixed at launch (a supervisor records it with `agent_spawned`), so a change applies to later spawns only. The usage channel's `used_percentage` (§4.6.12) keeps measuring the full window.

**Ending a retired agent's session.** When a supervisor retires an agent it first writes `<worktree>/.volley/retired.json` = `{ "agent_id", "status", "at" }` beside the agent's `agent.json` (§6.5), then deletes its login (§4.6.13). An agent's hooks that find a marker naming their own `agent_id` SHOULD end quietly (exit 0, nothing printed, no broker connection): the refused login is the intended outcome, not an auth failure. A marker naming another `agent_id` (a reused worktree) is ignored. With `retire_close_session` on, the supervisor then ends the agent's session: it closes its workspace (bounded by a timeout) and, on its own machine, stops the agent's `claude` process (SIGTERM, a grace, SIGKILL), journaling `agent_session_closed { agent_id, workspace, how, pids }` before `agent_retired` (`how`: `close-workspace`, `kill-session`, `signal` when only a process was stopped, or `none`). Off, finished sessions stay open for inspection.

**The local terminal.** `fleet.local_terminal` (`cmux` \| `tmux`) is the terminal agents on the supervisor's own machine run in: a cmux workspace, or a detached tmux session named `volley-<wave>-<task>-<role>` (a later attempt's name gains `-<n>`) on the user's default tmux server, which runs only the agent's `.volley/launch.sh`, so `tmux attach -t <session>` shows it. `null`, the default, resolves to `cmux` on macOS when cmux is installed and to `tmux` otherwise (every Linux supervisor); cmux is a macOS app, so `cmux` set on another platform also runs agents in `tmux`. A supervisor reads it when it starts: a running agent's workspace belongs to the terminal it started in, so a change applies to agents spawned after the next start, and a supervisor that restarts under another value keeps reaching each running agent through the terminal its `agent_spawned` recorded. Either way the agent, its worktree and its signals are the same; `agent_spawned` carries `terminal`, and the agent's `screen` channel's `source` is that terminal. A task that names `host: local` runs in it like any other.

Per-wave overrides use the same shape with every key optional (a wave file's `config:` block) and appear in the wave state as `effective_config`. The exception is `lease_pools`: pools are machine-global (§4.6.5), so a supervisor rejects a wave file that overrides them rather than accept an override it cannot apply.

**Changing config.** A client sends a mailbox message (§4.4) to the supervisor with `type: "query"`, a fresh `correlation_id`, and `payload: { op: "config_set", patch, by, text }`, where `patch` is a partial tunables object (`config-set-request.schema.json`). Senders MUST include `text` (a one-line human summary), so the request is also a well-formed mailbox message (`mailbox.schema.json`), and MUST set a non-null `correlation_id` so they can match the acknowledgement. The supervisor answers with a mailbox acknowledgement correlated to the request carrying `{ applied, rejected: [{ path, reason }] }`; a patch with an unknown key or an out-of-bounds value is rejected as a whole. On success the supervisor re-publishes the retained `_config` topic with `version` incremented.

#### 4.6.5 Leases

Heavy operations (integration test suites, builds, browsers) are gated by machine-global lease pools. `volley/_system/leases/<pool>` holds the retained pool state `{ pool, capacity, per_machine?, held: [{ lease_id, holder, host?, since, ttl_s }], queue: [{ lease_id, holder, host?, since }], reasons[] }`; `queue` is FIFO and `reasons` explains the queue in human terms (e.g. `"queued: 3/3 backend-it leases held"`). `host` is the machine the holder runs on (§4.6.15: a host name, the supervisor's own machine under its `fleet.local_name`), or `null` for a holder the supervisor did not spawn (a hand-run agent, whose machine it does not know); a supervisor that predates it omits it. A pool whose config sets `per_machine` (1 to `capacity`; unset means `capacity`) also caps the leases that holders on one machine hold at once, and publishes it in the pool state: a grant needs a free slot under both caps (a `null`-host holder counts toward `capacity` only), the supervisor grants the earliest queued request that both caps admit (so a request its own machine's cap holds back does not block one from another machine), and the `reasons` line for a held-back request names the cap that holds it (e.g. `"queued l-004: 1/1 backend-it leases held on box-a (per machine)"`). A pool's `per_machine_overrides: { <machine>: n }` (0 to 64, at most `capacity`, which the supervisor checks on `config_set` and at load, naming the path: `lease_pools.js-suite.per_machine_overrides.box-a: 5 is over capacity 3`) caps a named machine's holders in place of `per_machine`, so a laptop and a large server can take different shares of one pool; 0 lets no holder on that machine hold one. `<machine>` is a `hosts.<name>` key, the supervisor's `fleet.local_name`, or `local`, an alias for the supervisor's own machine that the effective config resolves to its name (when the name is set too, it is the one in force). An override alone (no `per_machine`) caps only the machine it names. The pool state carries `per_machine_overrides` when the config sets any, so a client shows the cap in force on each machine (`on box-a 2/3, on laptop 1/1`). Agents ask on `volley/_system/leases/<pool>/requests` with `payload: { op: "acquire" | "release" | "renew", lease_id, holder, ttl_s? }` (the one user-space publish §2.4 allows under a reserved prefix); the supervisor answers by re-publishing the pool state, and expires leases on TTL or when the holder's `status` turns terminal. The supervisor ignores a request whose `holder` differs from the envelope `agent_id`, so an agent can only acquire, renew or release its own leases. Requests are not retained, so one sent while the supervisor is down is lost: an agent that does not see its `lease_id` in `held` or `queue` within 30 seconds SHOULD re-send `acquire`, and the supervisor treats a repeated `acquire` for a `lease_id` it already holds or queues as a no-op. When a pool is removed from config, the supervisor keeps its holders (nothing is preempted) but drops its queued requests, adding `rejected <lease_id>: <why>` to the pool's `reasons` (or clearing the topic once the pool is empty); a client whose queued `lease_id` leaves the pool state without a grant SHOULD treat the request as rejected.

#### 4.6.6 Screen channel

`screen` is a reserved per-agent channel in addition to those in §4.1: QoS 0, **retained**, published by a supervisor *on the agent's behalf* (the envelope `agent_id` is the supervisor; the topic's `<agent_id>` segment names the agent). `payload: { lines (≤ 40 strings), captured_at, workspace, hash, source }` is the tail of the agent's terminal (`source` is the capture mechanism, a closed enum: `cmux` or `tmux`, the terminal the agent runs in: `fleet.local_terminal` on the supervisor's own host (§4.6.4), `tmux` on a remote SSH + tmux host); publishers SHOULD skip captures whose `hash` is unchanged. The supervisor clears the topic when the agent is retired. A supervisor whose capture is slow or failing SHOULD back off and set `tasks[].screen_stale` in the wave state (§4.6.1) until a capture succeeds in time. Agents MUST NOT publish their own `screen` channel.

**Terminal size.** A client showing an agent's screen larger than the agent's terminal MAY ask the supervisor to resize it with the mailbox control op `terminal_resize { agent_id, cols, rows }` (each an integer, 20 to 500), or `terminal_resize { agent_id, reset: true }` to return it to its launch size (the `tmux_cols` × `tmux_rows` in effect when it launched, §4.6.4; a supervisor that no longer knows that size, e.g. after a restart, MAY use the default) when it stops showing it. The op changes only how the agent's output wraps, so any sender that may write the supervisor's mailbox may send it (no wave ownership check); the supervisor MUST refuse an agent it does not supervise and a size out of bounds. A supervisor SHOULD coalesce a burst of requests for one agent to the last one. On a tmux host (a remote SSH + tmux host, or the supervisor's own under `fleet.local_terminal: tmux`) the reference supervisor runs `tmux resize-window -t =<session>: -x <cols> -y <rows>` (its sessions start at the launch size, never tmux's 80×24 default); a host with no way to resize (cmux) answers `ok` with `result.resized: false`. The agent's program re-wraps its output on the resulting SIGWINCH.

#### 4.6.7 Spawn admission

A supervisor throttles *starts* (never running work) by measured machine load. `volley/_system/admission` holds its latest verdict, re-published after every pressure sample: `{ sampled_at, allow, throttled, reasons[], signals, waves?, ceiling? }`, where `allow` is how many more agents may start now (`null`: pressure sets no limit; the hard ceiling and per-wave spawn budget still apply), `reasons` has one human-readable line per signal holding starts back (e.g. `"memory pressure critical (level 4 > max 2)"`), and `signals.<name>` is `{ state, value?, max?, clean_samples?, error? }` for `memory_pressure`, `cmux_ping`, `containers`, `api_overload` and `ci_queue`, with `state` one of `clear` \| `over` \| `recovering` \| `unknown`. Thresholds and the hysteresis sample count are the §4.6.4 `admission.*` tunables: a signal over its threshold sets `allow` to 0, and must then be clear for `hysteresis_samples` consecutive samples (`recovering`) before the allowance rises again; a signal that cannot be measured is `unknown` and never trips; on a signal already tripped, an unmeasurable sample counts toward its clean samples (so a measurement tool that breaks cannot hold starts back forever), and the signal reports `recovering` with `clean_samples` and the `error` until the count is reached. A supervisor admits nothing before its first sample. `waves.<wave>` is the same verdict with that wave's overrides and its repository's CI queue applied; the supervisor also copies those reasons into `why_waiting` of the wave's ready-but-unstarted tasks (§4.6.1). `ceiling` is `{ live, max, launching, by_wave }`: what the hard ceiling counted (§4.6.4) as of `sampled_at` (the retained verdict is not re-counted between samples; the `admission` control op answers with it re-counted), `max` the global `hard_ceiling`, `launching` the part not supervised yet (agents starting, and slots held for a task's next agent), and `by_wave` each wave's share. This verdict is the supervisor's own machine plus the global signals (`api_overload`, `ci_queue`). In a wave that places its tasks (§4.6.15), a task placed on a peer is admitted instead by that peer's own signals, read from its machine record at each new heartbeat (a record whose `last_seen` is not newer is the same heartbeat and is not counted again): memory available under `placement.mem_available_min_pct` or load per core (the higher of the 1- and 5-minute load averages) over `placement.load_per_core_max` (the wave's effective values) holds starts there, with the same `hysteresis_samples`, plus the global signals; its reasons name the host (`"box-a: load 2.00 per core (max 1.5)"`). So in such a wave agents may start on peers while `allow` is 0 for a signal of the supervisor's own machine (its memory pressure, cmux ping or containers); a peer's hysteresis shows in its readiness verdict instead (§4.6.15).

#### 4.6.8 Pipeline results and the merge-ready gate

A supervisor that reviews work before it is merged (by a human, or by the supervisor itself under §4.6.17) MAY ask its review roles for a structured retained `result` (§4.1) published before their terminal `done`: `type: "review"` with `payload: { findings: [{ severity, file, line?, text }], verdict }`, where `severity` is `P1` (blocks the merge) \| `P2` \| `P3` and `verdict` is `approve` \| `changes_requested`, and `hygiene: { checked: true, findings: [...] }` — the reviewer's check of the diff, commit messages and PR text for person names, local usernames, machine paths, private hostnames or IPs. When the supervisor's `public_hygiene` setting (§4.6.4) resolves to public — `on`, or `auto` for a public repository or one whose visibility the supervisor could not read — the block is required and each hit is a `P1` finding (a review without `hygiene.checked` is not a review result); for a private repository a supervisor MAY ask for the check at `P3` (the block optional, hits never blocking the merge) or not at all (`off`). A supervisor that reads the visibility SHOULD do so once per wave version, journal it (`repo_visibility_detected`) and show it on the wave state (`repo_visibility`, `hygiene_level`); a supervisor that shows the repository's GitHub name and URL (`github`, §4.6.1) reads them in that same read, and makes it whatever `public_hygiene` resolves to (under `on` or `off` the visibility it returns is not used). A fix-up role publishes `type: "fixup"` with `payload: { resolved: [{ finding, how }] }`; a release stage's agent (§4.6.19) publishes `type: "stage"` with `payload: { stage, commands: [{ argv, code, seconds }], notes?, artifacts?: { tag?, files?, urls? } }`; all three result types are in `review-result.schema.json`. A supervisor SHOULD treat an agent's `done` as a claim and verify it (pushed head, the PR for exactly that head branch, CI on exactly that head) before acting on it, and SHOULD re-check that the PR is still at the verified head before gating it. CI on exactly that head means the latest run per workflow and trigger event: a run superseded by a newer run of the same workflow for the same head is not that head's CI. A draft PR is not merge-ready, and its repository may skip CI jobs on drafts: a supervisor SHOULD mark it ready (`gh pr ready`) before gating it, journal `pr_marked_ready { pr, head, at }`, and count as that head's CI only once a run created at or after `at` exists (a draft's earlier green says nothing about the jobs it skipped); a merge refused because the PR is a draft is handled the same way, never escalated (§4.6.17). A task whose claims are verified enters stage `merge_ready`, is listed in `gates`, and carries `evidence_path`, a supervisor-local file describing that head. The supervisor does not merge unless §4.6.17 autopilot merging is on for the wave; then it merges only a gated head, exactly that head, and journals it. Otherwise a task becomes `done` only when the supervisor observes that a human merged its PR. It SHOULD look for that merge in every stage short of `done` and `cancelled` while the task has a PR, not only at `merge_ready`; a merge it observes before the gate, or at a head other than the gated one, is recorded as such (`merged_unverified_head`). Before the task becomes `done` the supervisor resolves the task's open decisions as `superseded_by_merge`.

A repository may have no CI at all. A supervisor SHOULD read the repository's CI once per wave version at admission, beside its visibility, and never infer it from a head with no run: its active workflows and the status checks its release branch requires (branch protection and rulesets). It journals `ci_mode_detected { mode, workflows, required_checks, source }` and shows `ci_mode` on the wave state: `none` when it finds neither an active workflow nor a required check, `required` when the release branch requires checks, `workflows` otherwise. Under `none` a verified head with no CI run is accepted at once with `ci: none` (CI not applicable, not green), the review roles and the gate being the check: the supervisor holds nothing for CI, waits for no run after marking a draft ready and asks no one about it. A run that does exist on a head is honoured in every mode. Under `workflows` a head with no run is held, and the owner asked once a grace has passed; under `required` that question names the required checks and offers no acceptance (the host refuses the merge without them). A read that fails is never `none`: the supervisor proceeds as `workflows` and raises the alarm `ci_mode_unknown`. A wave file's `ci: auto | none | required` (default `auto`, the detection) overrides it; `ci: none` on a release branch that requires checks is refused at submit, naming them. The same reads serve the repository check a submit makes (§4.6.21).

A supervisor that runs review roles MUST NOT move a task to `merge_ready` unless every review role in that task's pipeline has a recorded review with a verdict that holds for the head being gated: a review of that head, or of a head it descends from only through fix-ups that ran after that review, branch updates from the release branch (a rebase onto it or, under `branch_update: merge`, a merge of it, §4.6.4), and heads pushed outside the pipeline that the owner explicitly accepted without a re-review (a `pr_head_moved` decision answered `fixup`, or answered `accept` for a merge of the release branch only, §4.6.2), each such acceptance recorded, with who gave it, in the gated head's evidence. Any other push to the PR after a review voids that review. A pipeline without review stages is honoured only when the wave file lists it explicitly; the supervisor then sets `tasks[].reviews_skipped_by_plan` (§4.6.1).

#### 4.6.9 Brief preface

A supervisor that writes briefs for the agents it spawns SHOULD let a repository set rules every one of them gets. The **brief preface** is a file — `<repo>/.volley/brief-preface.md` by default, or the path in the wave file's `brief_preface` key (relative to `repo`, or absolute) — whose bytes the supervisor puts verbatim (no placeholder expansion) at the top of every brief it writes for that wave, for every role, above the role's own text and separated from it by a rule. The file MUST be UTF-8; a supervisor refuses one that is not, rather than alter its bytes. A blank file (only whitespace) counts as no preface. A supervisor bounds its size (`brief_preface_max_bytes`, §4.6.4) and refuses a wave whose preface is larger. The wave state's `brief_preface` (§4.6.1) is `{ path, sha256, bytes }` of the file as read for the current plan version (`sha256` over its bytes), or `null` when there is none, so a client can show which rules the agents got.

#### 4.6.10 Accounts and one-time tokens

A deployment with broker authentication keeps **accounts**: broker logins with a **role** that selects the shared broker roles they hold (§4.6.13). `admin` may do everything a coordinator may, plus the account ops below; `steer` reads everything and writes mailboxes (steering, control requests) and lease requests; `watch` adds no writes of its own; `supervisor` (a volleyd) reads and writes everything except the account-op and answer topics below (its role denies publishing to `volley/_system/auth/ops/#` and `volley/_system/auth/replies/#`, so it can neither impersonate an admin nor forge an answer); `peer` (a paired machine) writes its own agent channels and its machine record `volley/_system/machines/<username>`, which is exactly what the shared `account` role grants, so it adds nothing beyond it. Every account holds that `account` role (read `volley/#`; write its own channels and registry entry, lease requests and its own machine record `volley/_system/machines/<username>`, the record topic only: never a topic under it, such as the readiness verdict of §4.6.15), so even a `watch` account may write its own identity's records. Agent logins minted for dispatched agents are not accounts. The registry is a file kept by the account tool (`account.schema.json`: `{ name, role, kind, created, label? }`); it never holds a password. `account_list` adds `last_seen`: the newest of the account's retained registry entry, its retained `status` (where its LWT lands) and its last auth request to this supervisor process. Auth requests are kept only in that process's memory, so the `result` also carries `seen_since`, when the process started: a `last_seen` before it, or none, says nothing about the time since. A client that flags idle accounts SHOULD measure idleness from the later of `last_seen` (else `created`) and `seen_since`.

**Account ops.** An admin sends `payload: { op, ... }` (`auth-request.schema.json`) in an envelope with `channel: "_system/auth"`, `type: "query"` and a fresh `correlation_id` to `volley/_system/auth/ops/<username>`, where `<username>` is its own broker username. The broker ACL grants that topic to admin accounts, to Desk logins (the `desk` role) and to the fixed `coordinator` identity, each only for its own username, so the topic names the sender; the supervisor MUST also check the named account's role per op and refuse any other sender with a reason: `admin` for the account, setup and peer ops and `archive`, a Desk login (a `steer` or `admin` account, or the fixed `desk` identity) for `inbox_answer` and `resolve` (§4.6.18), and, besides an admin, the fixed `coordinator` identity for the repository ops of §4.6.21 (`paths` excepted; every other op from it is refused). The fixed `desk` and `coordinator` identities have no account entry: the supervisor trusts the literal username, which only that login may write. The mailbox is not used for the account ops (`inbox_answer` and `resolve` stay mailbox ops for the owner's own sessions): anyone who may steer may write the supervisor's mailbox, so it cannot name the sender. Requests MUST NOT be retained; the supervisor clears a request topic's retained message so it is never replayed. Ops: `account_list`; `account_create { name, role, kind? }`; `account_rotate { name }` (refused for the sender's own account: setting a new password disconnects the client holding the old one before the answer arrives, so an admin rotates itself from a terminal or through another admin); `account_revoke { name }`; `signin_link { role, label, ttl_s?, desk_url? }`, where `role` is `steer` or `watch`; with `desk_url` its `result` carries `link_base` (the URL without a fragment) and the client builds the link `<link_base>#signin=<token>`. A supervisor journals each successful op in the `_system` journal (§4.6.3: `account_created`, `account_rotated`, `account_revoked`, `signin_link_issued`, each with `by`; `at` is the event's) and never writes a password itself: the account tool does.

**Setup ops.** The same topic, admin check and answers carry the setup ops, which run the account tool's own first-run setup (`volley setup`: the steps `detect`, `security`, `accounts`, `network`, `services`, `phone`, in that order) for a client such as the Desk; the supervisor runs the same planners and steps, never a second implementation. `setup_plan { lan?, network?, network_address?, repair? }` plans every step fresh (never cached) and answers `result: { steps: [{ step, title, found, notes?, changes: [{ summary, detail?, terminal? }], blocked?, skipped?, plan_id, lan?, network? }], last_setup?, broker? }` (`setup-result.schema.json`, `$defs/plan`): what each step found, what the supervisor notes but cannot check itself (`notes`, such as the macOS keychain, which only the logged-in session reads: neither a check that passed nor a change), the changes it would make, why it cannot run (`blocked`, which also stops every later step) or is left out (`skipped`), and `plan_id`, which names that plan of the step (a digest of its changes). `lan` feeds the security step's plan exactly as the terminal's `--lan` / `--no-lan` (omitted: what the broker config has), and that step reports the choice it planned for as `lan: { planned, current }`, `current` being what the config has now (`null` when it is not Volley's), so the plan a client shows is the plan it applies. `network` (`tailscale`, `manual` or `none`) and `network_address` feed the network step exactly as the terminal's `--network` and `--network-address` (omitted: the kind the machine's setup record has, else `tailscale`; `network_address` only with `manual`, and it must be one of the machine's own addresses, else the step is `blocked` naming its interfaces), and that step reports the kind it planned for as `network: { planned, current }`, `current` being the record's kind now (`null`: none). The network step installs Tailscale (`tailscale`), signs it in and records the machine's MagicDNS name and tailnet IPv4 address; records the owner's own VPN address (`manual`); or records `none`. It never opens a listener, a relay or a public endpoint (Tailscale Funnel, `tailscale serve`). Its sign-in reports the line `Sign in to Tailscale: <url>` in the applied step's `lines`, for the person to open (on a phone too); the step is planned again once the machine is signed in. `repair` is `--repair`: no new admin token, no phone link. `broker: { accounts_required, listeners: [{ port, anonymous }] }` carries the detect step's probes as data (`anonymous` is `refused`, `accepted` or `unreachable`), so a client never parses `found`, which is display text. `setup_apply { step, plan_id, lan?, network?, network_address?, repair?, reply_key }` plans that step again and applies it only when the fresh plan's `plan_id` is the one sent, else refuses with an error that starts with `plan changed` before anything changes; it also refuses while an earlier step is `blocked` or another `setup_apply` runs. It answers `result: { step, lines, problems, terminal?, restarting? }` (`$defs/applied`): what each change reported and what the step's checks found afterwards. A change only a terminal can make (one that needs `sudo`, such as installing and signing in Tailscale on Linux, or that would stop the supervisor answering) carries `terminal: { reason, command }` in the plan and is never applied by `setup_apply`, which applies the step's other changes and lists the rest in `terminal`. A broker restart is applied last, after the answer is published, which says so with `restarting: true`; the restart drops every client's connection, an answer is not retained, so a client re-plans once it has reconnected rather than assuming the step failed. Over this topic the accounts step's one-time admin token is in `sealed: { token }` only, never in `result`, a log or the journal; the phone step's link is not made by `setup_apply` (a client asks `signin_link`). `admin_token { reply_key }` issues a one-time admin token to an admin: `result: { token_id, expires_at }`, the token in `sealed: { token }`. Sealing it to an admin adds no privilege (an admin may already create an admin account). Over this topic a new identity's password is never shown: the supervisor's and the coordinator's go to their credential files, and the shared `desk` login (which no file keeps) gets one only through `desk_password { reply_key }`, which gives it a new password and answers `result: { username: "desk" }` with `sealed: { username, password }`; it signs out whatever used the old one. The `_system` journal records `setup_step_applied { by, step, summaries }` for a `setup_apply` that applied (or, for a restart, scheduled) at least one change, `admin_token_issued { by, token_id, expires_at }`, never the token, and `desk_password_issued { by }`, never the password. A supervisor that does not implement an op answers `unknown op '<op>'`.

**One-time tokens.** An operator's terminal prints a single-use token (`vly_admin_<id>_<secret>`, by default valid 10 minutes), or an admin asks for one with `admin_token` and receives it sealed; `signin_link` yields a `vly_signin_<id>_<secret>` token for one device (a Desk link carries it as `<desk_url>#signin=<token>`). Only a hash of each token is stored. A token is also the password of a short-lived broker login whose username is the token id `<id>`, so the broker can keep refusing anonymous clients. That login holds only the `token` role (§4.6.13), which grants exactly two things through `%u`: write its own request topic `volley-auth/redeem/<id>` and read its own answer topic `volley-auth/redeem/<id>/reply`. It cannot read anything under `volley/` (the broker refuses the subscription), nor another token's topics. These two topics are the one exception to the `volley/` root, so that no grant any other role holds under `volley/` reaches them. Only the supervisor reads the request topics and writes the answer topics. The login is removed once the token has expired, or about a minute after it was redeemed, by the account tool's next run; the supervisor runs it periodically (`token_prune_ms`) so an unused token stops being a login soon after it expires. The client publishes `payload: { op: "token_redeem", token, label, reply_key }` on its request topic; the supervisor refuses a token whose id is not the topic's, burns the token and creates an account with the token's role (`admin` for an admin token) bound to `label`, journaled as `token_redeemed`. Redemption does not remove the token's login at once: deleting a login disconnects the client using it, and the redeeming client is still connected as that login, waiting for its answer. A used, expired or unknown token is refused. There is no other way to obtain an admin account from a browser.

**Answers.** The supervisor answers an account op on `volley/_system/auth/replies/<correlation_id>` and a `token_redeem` on `volley-auth/redeem/<id>/reply` (QoS 1, not retained) with `type: "ack"`, the request's `correlation_id`, and `payload: { text: "ACKED", acked_type: "query", op, ok, error?, result?, sealed? }`. Every account may read the account-op answer topics, so a secret (a password, a sign-in token and link) MUST NOT appear in clear text: it is in `sealed`, the base64url RSA-OAEP (SHA-256) encryption of `{ username, password }` or `{ token }` to the request's `reply_key`, an RSA public JWK of at least 2048 bits whose private half only the requester holds. A request whose answer would carry a secret and that has no usable `reply_key` is refused before anything is created. Clients MUST accept an answer only from `agent_id: "volleyd"` (§4.4); the broker ACL lets no account but the fixed `volleyd` identity write the answer topics.

**Owner decisions (2026-10-18).** The redemption path uses per-token broker logins, not an anonymous redeem topic; account ops use the dedicated `volley/_system/auth/ops/<username>` topic, not the supervisor's mailbox; every request whose answer carries a secret MUST carry `reply_key`; a token login reaches only its own two topics.


#### 4.6.11 Claude account profiles

A supervisor that launches Claude Code agents MAY run them under several Claude accounts. Each account is a separate Claude Code profile: its own configuration directory, passed to the agent as `CLAUDE_CONFIG_DIR` (one canonical absolute path with no trailing slash; Claude Code keys the profile's login to that exact string). `primary` names the user's own default profile (no `CLAUDE_CONFIG_DIR`). A profile is signed in only through Claude Code's own sign-in flow. A supervisor MUST NOT read, store, log, parse, forward or otherwise handle a Claude credential, session token or authorization code: it never reads a profile's credential store, never uses a flow that prints a bearer token, and never sets a credential variable in an agent's environment, with two exceptions. First, a person MAY paste the code Anthropic's code page shows, or the localhost address their browser ended up on, into a Volley client to finish one waiting sign-in (**Sign-in**, below): the supervisor carries it once, over the fenced path, to the machine where that sign-in waits, and never keeps, logs, journals or echoes it. Second, the machine that holds a login MAY read that login's own stored OAuth access token, in memory, for exactly one read-only request to Claude's usage endpoint from that machine (§4.6.12, the usage probe), and publishes only percentages and reset times. It never refreshes, writes, forwards, logs or journals the token, never carries it over ssh or the broker, and skips an expired one (Claude Code renews it on its next request). Rationale: Claude Code's statusLine exposes no per-model weekly window, balancing (§4.6.12) needs the model-family windows, and this read is of the same kind as reading a profile's `.claude.json` identity (below): by the machine, on the machine, numbers out. A supervisor MAY open a fenced, transient ssh port forward that carries the browser's redirect to Claude Code's own loopback listener on the machine signing in: the forward is an opaque encrypted pipe (like the broker tunnel), is bound to that one sign-in's port and target, and is torn down when the sign-in ends or times out. (The credential variables are `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN`.)

**Selection.** An agent runs under its last account move (`agent_account_moved`), else its task's `account` (wave file), else the wave's last move (`wave_account_moved`: `wave_account_set` below, or an `account_limit` answer, §4.6.12; a move to `null` balances), else the wave's `account`, else the `claude.default_account` tunable (§4.6.4) when it names `primary` or a registry id. Otherwise (the default, `null`, or `most_headroom`, a legacy name) the supervisor balances: the agent runs under the account the rank rule (§4.6.12) puts first among the candidates of the machine it runs on, for its model. The candidates are, on the supervisor's machine, `primary` and every signed-in local profile; on a paired machine, `primary@<name>` and every signed-in profile the registry keeps for that machine (`<acct>@<name>`) whose sign-in recorded its directory there. With the primary alone there is nothing to balance: a one-login machine runs every agent under its login as before. A spawn under an unknown account, or one whose sign-in has not finished, is refused with a reason. A profile on a paired machine is selectable only by an agent placed on that machine, and a profile on the supervisor's machine only by a local agent; a config default naming a profile kept elsewhere does not apply on a paired machine (it balances there). Such an agent launches there with `CLAUDE_CONFIG_DIR=<home>/.volley/claude/<acct>`, the directory recorded at sign-in; sharing and the MCP servers sync are the supervisor's machine's only, so nothing is copied to a paired machine's profile. Every pick is journaled in the agent's wave right before its `agent_spawned`, as `account_chosen { task, role, attempt, account, machine, source, why, candidates[] }`: `source` is `task`, `wave`, `config`, `balance`, `move` or `default` (the primary alone), `why` is one line the supervisor writes (`work: 18% left, resets in 52m (use it or lose it) on peer-a; primary@peer-a 7d 72% left, resets in 2d 4h`, `task names work`, `moved off primary (5h 91%) by autopilot`), and `candidates` are the machine's candidates as the rank rule ordered them, each `{ account, five_hour_pct, weekly_pct, model_weekly_pct?, agents, headroom, score?, binding?, eligible?, binding_left?, binding_resets_at?, in_flight?, projected_pct? }` (§4.6.12); `agent_spawned` repeats `why` as `account_why`. Neither names an e-mail. `claude_balance { model?, machine? }` answers, per machine, its ranked candidates and the pick for `model` (default: each model family's pick), from the current records. The agent's `.volley/agent.json` and its registry entry carry `claude_account` (§6.2, §6.5). Folder trust is per profile, so a `repo_untrusted` decision (§4.6.2) for such an agent carries `claude_config_dir` and is answered in that profile.

**Sign-in.** `claude_account_add { label, machine?, by }` creates the profile — on the supervisor's machine, or, when `machine` names a paired machine (§4.6.14), there, as `<home>/.volley/claude/<acct>` on that machine — and starts Claude Code's sign-in for it in the background, a paired machine's through the same sign-in terminal as its own default profile's; `claude_signin { acct }` restarts it for an existing profile. The supervisor publishes the authorize URLs Claude Code produced, as `claude_signin_url { acct, url, flow, attach, manual_url?, callback_url?, code_prompt? }`, on `volley/_system/claude/<acct>/signin`, then `claude_signin_done { acct, plan? }` or `claude_signin_failed { acct, reason }` there. The topic is not retained: whoever opens the URL first chooses the account bound to the profile. Not retaining it does not confine it: every client that may read the topic while the sign-in runs sees the URL, and under the example broker ACL every authenticated client, agents included, may read all of `volley/#`. A deployment that must keep the URL from its agents restricts reads of `volley/_system/claude/#` to the owner's clients in its broker ACL.

Claude Code has no switch that picks a sign-in flavour (`claude auth login` takes `--claudeai`, `--console`, `--email` and `--sso` only, and no environment variable selects one). Every `claude auth login` runs both flavours of one PKCE sign-in at once: it hands `$BROWSER` the authorize URL whose `redirect_uri` is its own `http://localhost:<port>/callback` listener, and prints the authorize URL whose `redirect_uri` is Anthropic's code page (`code=true`) while its prompt waits (`Paste code here if prompted >`). Both carry the same `state`; which page the person lands on depends only on which URL they open. So the printed URL is the link: it works from any device, and its page shows a code. `url` is that printed URL and `flow` is `manual_code`, with `manual_url` the same URL; `callback_url` is the `$BROWSER` URL, a shortcut for a browser on the supervisor's machine, never a requirement (for a paired machine, present only while the forward below is up). Before Claude Code has printed one, `url` is the `$BROWSER` URL and `flow` is `browser_callback`; the event is published again when what it says changes (the printed URL, or the prompt, appearing later). `code_prompt: true` says the sign-in terminal shows Claude Code's `Paste code here` prompt. `attach` is the one-line command that reaches that terminal; for a remote machine it is prefixed with ssh (`ssh <target> -t tmux attach -t volley-signin-primary`). A paired machine's own default profile is the account `primary@<name>`, and a profile the supervisor created there is `<acct>@<name>` (the §4.6.12 naming of a remote host's account); its sign-in session there is `volley-signin-<acct>`. The URL is not journaled; while a sign-in waits, `claude_accounts` returns it, so a client that attached late can still show it.

`claude_signin_entry { acct, entry, by }` finishes a waiting sign-in from whatever device the person is on. `entry` is what they pasted: the code the code page shows, or the address their browser ended up on when a `callback_url` redirect could not reach the listener (`http://localhost:<port>/callback?code=…&state=…`). The supervisor types a code into the sign-in terminal on the machine where the sign-in waits (`tmux send-keys -l`, then Enter, on that machine); it completes an address by requesting exactly that callback, the query byte for byte, from `127.0.0.1:<port>` on the machine whose listener waits, and only when the port and the `state` are those of that sign-in's own `$BROWSER` URL (otherwise it refuses with `that address belongs to another sign-in; open a fresh link`, and runs nothing). Each travels over the supervisor's fenced path: its own process runner locally, the fenced remote step for a paired machine. The answer comes when the sign-in ends: `{ acct, signed_in: true, email? }` on `claude_signin_done`; when it has not ended within a bounded wait, or ended failed, the supervisor reads the sign-in terminal for Claude Code's refusal, restarts the sign-in (a new `claude_signin_url`) and answers `ok: false` with `error: "code rejected: <the line>"` and `fresh: true`. No sign-in waiting for `acct` is refused (`no sign-in waiting for <acct>`).

The code and `state` are credential-grade. A supervisor MUST NOT journal, log or keep them after the request, and MUST NOT echo them in an acknowledgement or an error: the journal records `claude_signin_entry { acct, kind, by }` (`kind` is `code` or `redirect`) and never the value; any message that could carry one (Claude Code's refusal line, a failure reason) has every `code=` and `state=` value and the pasted code itself replaced with `•••` first. The `$BROWSER` URL's port and `state` are kept in memory for that sign-in's lifetime only. A client clears what was pasted once it is sent, and shows only the supervisor's answer.

A paired machine's sign-in runs on the machine, as above; the supervisor MAY additionally hold a forward that carries a browser's redirect from its own loopback to the machine's listener, so `callback_url` also works in a browser on the supervisor's machine. A remote machine's `claude_signin_url` (the URLs shortened; `redirect_uri` decoded for reading):

```json
{
  "acct": "primary@box-a",
  "url": "https://claude.ai/oauth/authorize?code=true&client_id=…&redirect_uri=https://platform.claude.com/oauth/code/callback&state=…",
  "flow": "manual_code",
  "attach": "ssh dev@box-a -t tmux attach -t volley-signin-primary",
  "manual_url": "https://claude.ai/oauth/authorize?code=true&client_id=…&redirect_uri=https://platform.claude.com/oauth/code/callback&state=…",
  "callback_url": "https://claude.ai/oauth/authorize?code=true&client_id=…&redirect_uri=http://localhost:51051/callback&state=…",
  "code_prompt": true
}
```

While it waits the supervisor holds `ssh -N -L 127.0.0.1:51051:127.0.0.1:51051 dev@box-a`, and drops it when the sign-in ends or times out. The forward binds the very port in `redirect_uri` on the supervisor's loopback, never another, and is best-effort: when that port is taken there, the supervisor holds no forward and publishes no `callback_url`, and the sign-in proceeds (the code page, or a pasted address, still finishes it).

**Priming.** A finished sign-in is primed, on whichever machine the profile lives: the supervisor reads the login's plan and identity again (`claude auth status` under the profile's configuration directory there; the profile's `.claude.json` when the status reports no e-mail) into the registry entry, then runs that machine's usage probe (§4.6.12) for that one login, so the account's record carries its e-mail and its meters as soon as it is added. `claude_prime { acct, by }` asks for the same (`acct` a registry account, `<acct>@<name>`, `primary` or `primary@<name>`; the machine's own login has only the probe): a client SHOULD send it for an account whose identity or reading is missing, rather than tell the person to run anything. A supervisor primes a login at most once per 5 minutes; inside that window `claude_prime` is refused with when it last ran and when it next may (`primed 2 min ago; next in 3 min`). A prime is not journaled.

**Identity.** A profile's identity is the e-mail address and organisation name Claude Code itself records for the login (`oauthAccount.emailAddress` and `oauthAccount.organizationName` in the profile's `.claude.json`, or `email` and `orgName` as `claude auth status` reports them); a supervisor MAY read exactly those two fields of that file and nothing else from it, and reports them as `email` and `org` on the registry entry, `claude_signin_done` and the account's usage record (§4.6.12), so that a client can tell when profiles on several machines are one account. They are identity, not credentials; a supervisor MUST NOT journal or log them.

**Ops.** Mailbox control queries (§4.6.4's request/acknowledgement shape): `claude_accounts` (the registry: `{ id, label, machine, created, plan?, signed_in_at?, email?, org?, dir?, signin: { state, url?, flow?, attach?, manual_url?, callback_url?, code_prompt? } }`, plus the sharing modes, `primary: { plan?, email?, org? }` — the plan of Claude Code's default profile on the supervisor's machine as `claude auth status` reports it when asked, and the login's identity (below), each absent when not known — `machines: [{ name, kind?, claude, plan?, email?, org?, tunnel }]`, every machine record's Claude login state (§4.6.15), and `remote_signins: [{ acct, state, url?, flow?, attach?, manual_url?, callback_url?, code_prompt? }]`, the paired machines' sign-ins still waiting, their own and the profiles the supervisor created there; `dir` is absent for a profile on a paired machine until the supervisor knows that machine's home); `claude_account_add`; `claude_signin_entry { acct, entry }` (above); `claude_signin` (`acct` a registry account, `primary@<name>`, a paired machine's own profile, or `<acct>@<name>`, a profile the supervisor created there); `claude_sync { acct? }`; `claude_prime { acct }` (above); `claude_account_rename { acct, label }` and `claude_account_remove { acct }` (below); `claude_balance { model?, machine? }` (above); `wave_account_set { wave, acct }` (`acct` an account a spawn of the wave could use, or `null` for balanced: the account the wave's agents not yet spawned start under, ahead of its wave file's `account` and `claude.default_account`; a task naming its own keeps it, and a task on a machine with no profile of `acct` keeps what the wave file and the config default give it; running agents finish where they are. An unknown or not signed-in account is refused, as a `move wave` answer is. The supervisor journals `wave_account_moved { from, to, by }` in the wave, `null` meaning balanced; when an open `account_limit` (§4.6.12) offers `move wave <wave> to <acct>`, the request is that answer instead, and the event carries its `decision_id`; the wave state's `account` (§4.6.1) says the result); `agent_move_account { agent, acct }` (`acct` an account of the agent's own machine: a local one for a local agent, a profile kept for that machine, as `<acct>` or `<acct>@<name>`, for an agent on a paired machine). A move is never silent: the supervisor journals `agent_account_moved { agent_id, role, from, to, by, decision_id?, why }` first (`decision_id`: the `agent_account_limit` decision whose answer asked for it, §4.6.12), cancels the agent (§4.4), and only once it has stopped retires it and respawns its role under the other account, as a new attempt in the same working directory with a resume note in its brief. An agent that does not stop is not respawned.

**Sharing.** What a profile shares with the primary is chosen per item (`settings.json`, `CLAUDE.md`, `skills`, `agents`, `commands`, `plugins`, `mcp`): `linked` (a symbolic link to the primary's; Claude Code writes through it), `copy` (copied once) or `own`. `mcp` is the `mcpServers` section of the profile's `.claude.json`, copied from the primary's and re-synced by `claude_sync` and before each spawn; it is never linked. The profile's `.claude.json` holds its own account and is never linked or copied whole. MCP server entries can hold third-party secrets, so a supervisor never publishes or journals them.

**Rename and remove.** `claude_account_rename { acct, label, by }` gives an account a new name: every profile of its login (the same `email`) on every machine takes `label`, or the one profile `acct` names while it has no e-mail yet; `label` is validated as `claude_account_add`'s is (non-empty, not a reserved id), and ids never change. The usage records (§4.6.12) carry the new `label` from the supervisor's next publish. `claude_account_remove { acct, by }` removes one profile (`acct` is `<acct>`, or `<acct>@<name>` for one on a paired machine; `primary` and `primary@<name>` are never removable). It is refused, with the reason, while a supervised agent runs under it, a running wave's file pins it (the wave's or a task's `account`), or `claude.default_account` names it. Otherwise the supervisor stops the profile's pending sign-in, removes its configuration directory on its machine — on the supervisor's machine only under the profiles root, and on a paired machine only the directory the registry recorded, and only when it is `<home>/.volley/claude/<acct>` there — and drops its registry entry, its usage record and the retained record on `volley/_system/claude-accounts/<acct>`. The answer says whether the directory was removed (`dir_removed`), and when it was not, why (`dir_left`). Removing a profile does not sign it out at the provider: the supervisor never holds the credential. Both are a person's acts and are journaled: `claude_account_renamed { acct, from, to, by }` and `claude_account_removed { acct, machine, by, dir_removed }`.

**Registry changes.** After every change to the registry (an add, a rename, a remove, a finished sign-in, a sync) and when it starts, a supervisor publishes `claude_registry_changed { rev, at }` retained on `volley/_system/claude/registry` (`claude-registry.schema.json`). `rev` is 0 at start and one more at each change; it carries no account, and a client compares it for equality only (a restart starts it again): when it changes, a client that shows the registry asks `claude_accounts` again. At start and on every change the supervisor prunes its usage records: an account the registry no longer has (other than `primary` and `primary@<name>`) is dropped and its retained record cleared, as is any retained record on `volley/_system/claude-accounts/<acct>` the supervisor has no account for.

The `_system` journal (§4.6.3) records `claude_account_added`, `claude_account_renamed`, `claude_account_removed`, `claude_signin_started`, `claude_signin_done`, `claude_signin_failed`, `claude_signin_entry` and `claude_profile_synced`; a move is journaled in its wave.

#### 4.6.12 Usage metering

`usage` is a reserved per-agent channel in addition to those in §4.1: QoS 1, **retained**, published by the agent's own harness (the reference publisher is a Claude Code `statusLine` command in the hooks' settings, so Claude Code hands it the session's usage after each assistant message). `payload: { account, config_dir?, model, context_window: { used_percentage, used, size }, rate_limits: { five_hour?, weekly? }, captured_at }` (`usage.schema.json`), where each window is `{ pct, resets_at }` (`resets_at` a date-time or `null`). `account` is the Claude account the session runs under (§4.6.11: the `claude_account` of its identity, `primary` for a session without `CLAUDE_CONFIG_DIR`); when the publisher cannot tell, it is `null` and `config_dir` carries the session's `CLAUDE_CONFIG_DIR`, which the supervisor maps to its profile. A window is absent until the harness reports it (subscriptions only, after the first response). A publisher SHOULD throttle: the reference one publishes at most once per 15 seconds unless a percentage moved by more than one point (or the account, model or a reset time changed). A supervisor clears the topic when it retires the agent. Under an ACL that grants per-channel writes through a namespace wildcard, agent ids MUST NOT be `usage` or `claude-accounts`, for the same reason wave ids must not be channel names (§4.6).

**Per account.** The rate-limit windows belong to the account, not to the agent. A supervisor folds every agent's samples into one retained record per account on `volley/_system/claude-accounts/<acct>` (`claude-account.schema.json`): `{ account, label?, plan?, email?, org?, five_hour, weekly, model_weekly?, probe?, agents, waves, sampled_at, sampled_by? }`, where `email` and `org` are the account's identity (§4.6.11), when known, each window is the one from the newest sample or usage probe reading (below) that carried it (`null` while none has: where both report a 5-hour or weekly window, the freshest wins), `model_weekly` holds the weekly windows scoped to one model family (`fable`, `opus`, `sonnet`, `haiku`; only the probe reports them, and a family's window is kept until a newer reading has one), `probe` is the newest probe attempt for the account's login, a failed one included (`{ machine, state, attempted_at, read_at? }`), `sampled_at` is the newest of sample and reading, and `sampled_by` the agent of the newest sample (absent while only probes reported), `agents` are the agents whose latest sample is on the account and recent, and `waves` the waves they belong to: a session the supervisor does not supervise (an owner's interactive session, a dead one) still moves the account's windows, but the reference supervisor forgets it an hour after its last sample and clears its `usage` topic, so a restart does not bring it back; a supervised or launching agent stays however old its sample, until it is retired. The record outlives its agents: an account's windows stay known when nothing runs on it, and across a supervisor restart (the reference supervisor keeps them in a state file, not on the broker). An agent's wave is the one its spawn was journaled in, so its retained sample is attributed (and can open a decision) as soon as the supervisor reads it, before the agent is supervised again. A remote host's agent (`tasks[].host`, §4.6.1) runs under that host's own Claude login, which is not the supervisor's account of the same name: its samples are folded into a record of their own, `<acct>@<host>`, never into a local account. **Rank.** Balancing (§4.6.11) spends the room that expires first, without hitting a limit. The windows that count for an agent are the 5-hour, the weekly and, when the agent's model has a family (`fable`, `opus`, `sonnet`, `haiku`, read from `claude-<family>-…`; an unreadable id has none) and the record has that family's `model_weekly` window, `model_weekly[family]`; one not reported is left out, and a probe reading that is no longer fresh still counts until its `resets_at` passes. Each window has a length `L` (5 hours for the 5-hour window, 168 for a weekly one), a live percentage `pct` (0 once its `resets_at` has passed) and the hours `h` until it resets, at least one minute; a window whose `resets_at` is `null` or has passed is a full window (`h = L`) away from its reset. Its pace is `((100 − pct) / 100) / (h / L)`: 1 is on pace to use the window exactly as it resets, above 1 its room will expire unused, below 1 it is on course to reach the limit first. An account's `score` is its smallest pace and `binding` the window that sets it (`five_hour`, `weekly`, `model_weekly`; the tightest window decides), so expiring weekly room does not outweigh a nearly full 5-hour window. **In flight.** A window's `pct` above is its *projected* usage: the live percentage plus a reservation for each of the account's `n` agents in flight — the agents running on it and the ones the supervisor picked it for that have not reported usage yet (a spawn pass picks before any new sample lands, so each pick sees the ones before it) — each spending the account's rate for the window over `min(claude.balance.reserve_h, h)` hours, at most 100. The rate is the one the account has shown: when a newer reading of a window has the same `resets_at` as the one it is measured from, comes at least five minutes later, has not fallen and the account has agents, the observation is the rise per agent-hour, blended into the account's rate for that window kind (the 5-hour, the weekly, each model family's weekly) by an exponential moving average; a new window or a fall teaches nothing, and the rate outlives the window. Until a rate has two observations the tunable default stands in (`claude.balance.agent_cost_pct_h` for the 5-hour window, `agent_cost_weekly_pct_h` for the weekly ones, §4.6.4). With nothing in flight the projection is the live percentage. An account is `eligible` while every window it reported projects under `claude.balance.cap_pct` (§4.6.4, default 97). Eligible accounts rank before ineligible ones; each group by score, highest first, an account with no usage data counting as on pace (1). Scores within `claude.balance.tie_band_pct` percent of a band's leader (the highest score not yet in a band) form a band, ordered by fewer agents in flight (its `n`, so the picks of one pass spread; the record's `agents` do not count), then a signed-in profile before `primary`, then candidate order. Every candidate is ranked: the cap orders, it never refuses a spawn, so when every candidate is over it the first of them by score is picked (the one whose window resets soonest for its room, not necessarily the least over) and the all-hot `account_limit` (below) is how a person hears of it. `account_chosen` candidates carry `score`, `binding`, `eligible`, `binding_left`, `binding_resets_at`, `in_flight` (its `n`; their `agents` equals it) and `projected_pct` (the binding window's projection, `null` with no data) besides `headroom` (the smallest room left as sampled, `null` with no data); a pick's `why` names its binding window's room and reset (`work: 18% left, resets in 52m (use it or lose it) on peer-a`), with its projection when agents are in flight (`work: 18% left (8% after 1 in flight), resets in 52m …`); with no future reset known (`resets_at` `null`, or passed) the room has no time: `work: 5h unused on local` when the whole window is left, `work: 7d 68% left on local` otherwise; and an ineligible candidate is `over the 97% cap`.

**The usage probe.** Claude Code's statusLine reports the 5-hour and weekly windows only, and only while an agent runs on the account. Every machine therefore probes the logins it holds (§4.6.11's one exception to never reading a credential): its doctor (§4.6.15) reads, for its default profile (`default`) and each profile under its profiles root (`<id>`), at most 16, the login's stored OAuth access token and its expiry (macOS: Claude Code's Keychain item for that config dir, else the profile's `.credentials.json`; elsewhere that file), in memory, and makes one read-only request to the usage endpoint Claude Code's own `/usage` calls (`GET https://api.anthropic.com/api/oauth/usage`, the token as a bearer, Claude Code's own User-Agent, a 10 s timeout, no redirects). It never refreshes or writes a credential, never runs Claude Code, and skips a token whose expiry has passed (state `expired`, no request). The machine publishes only numbers, in its record's `claude_logins[]` (§4.6.14): `{ profile, state, attempted_at, reading?: { read_at, five_hour?, weekly?, model_weekly? } }`, `state` `ok`, `expired`, `no_credential`, `rate_limited` (429), `rejected` (401/403) or `error` (5xx, a timeout, a network error or an unexpected answer), and `reading` the last successful one, which survives later failures so that a client can show its age. The probe is gentle: at most one request per login per 5 minutes (kept in an on-disk memo of numbers only, since the supervisor's own doctor is a fresh process every heartbeat), and after a 429, 5xx, timeout or network error none until a backoff of 10, 20, 40, then 60 minutes has passed, reset by the next success. The token never crosses ssh or the broker, never reaches a log, journal, memo or published payload, and any error on the request's path has it replaced before it can travel. A supervisor folds each record's logins into account records: `default` is `primary` on its own machine and `primary@<name>` on a paired machine, and a profile `<id>` is `<id>` (or `<id>@<name>`) when the registry has that profile on that machine; a login the registry does not know there is skipped.

**Threshold.** When an account's 5-hour window reaches `claude.warn_at_pct` (§4.6.4; a wave's own override applies to that wave), the supervisor opens a wave-level `account_limit` decision (§4.6.2) for each wave with agents on that account, carrying `acct`, `pct`, `resets_at` and `suggested` (the account the rank rule puts first among those under the threshold in both windows, where a signed-in account that has no 5-hour usage data yet counts as available and ranks as on pace, as the rule says, and is labelled "no usage yet" in the question and in a client's picker ("no 5-hour usage yet" when it has reported weekly usage); or `null`, when none is under the threshold and only `not now` is offered), with the options `move wave <wave> to <suggested>` and `not now`. It does not open another for the same wave and account while one is open, nor after one was answered for the same window (`resets_at`). The weekly window opens no wave-level decision, and neither does a remote host's record (a wave move cannot reach its agents). A wave whose spawns balance (neither it nor a task names an account, and `claude.default_account` is `null` or `most_headroom`) gets no `move wave` decision: its new agents already avoid a hot account and its running ones get their own decision (below). Only when every candidate of a machine it uses is at or over `claude.warn_at_pct` in its 5-hour window does it get one `account_limit`, with `suggested: null` and only `not now`, saying that every signed-in account on that machine is at or over the level, that new agents start on the one the balance puts first, and when its window resets. **Nothing switches without a journaled decision:** autopilot answers `agent_account_limit` under its budget (§4.6.16); a person may answer it too. For a wave with a pinned account, only the answer `move wave <wave> to <acct>` moves the wave: the supervisor checks that a spawn could use the account (an unknown or not signed-in account is refused and the decision stays open), journals `wave_account_moved { from, to, by, decision_id }` in the wave, and from then on starts the wave's new agents that would have run under `from` under `to`. Running agents finish where they are; an agent moved on its own (`agent_move_account`) keeps its own move.

**Running agents.** When an account a supervised agent runs under reaches `claude.warn_at_pct` (its wave's) in a window that counts for it — its 5-hour window, its weekly window, or the weekly window of its model's family (the model of its latest sample, else its spawn's) — the supervisor opens a task-level `agent_account_limit` decision for the agent that does not park its task (the agent keeps working until the answer), carrying `agent_id`, `role`, `acct` (its account record), `window` (`five_hour`, `weekly` or `model_weekly:<family>`), `pct`, `resets_at` and `suggested`: the account the rank rule puts first among the other candidates of the agent's machine that are under the level in every window that counts for the agent (a window not reported counts as room), or `null`. The options are `move <agent> to <suggested>` and `not now`, or `not now` alone. No decision opens for an agent whose task, wave or `claude.default_account` names an account (the wave-level decision above covers a pinned wave), for one already moving, or when one for the same task, role, account, window and `resets_at` exists, open or answered: after `not now` the next one waits for the window's reset. The answer `move <agent> to <acct>` runs the account move of §4.6.11 with `by` the answerer and the decision's id; the respawn's `account_chosen` has `source: move`.

**Limit hit.** When a supervised agent hits its account's usage limit (the hooks' `awaiting_input` with `class: "credit"`, or the usage-limit prompt on a silent agent's screen: `credit_exhausted`), the supervisor first marks the account at its limit: its 5-hour window reads `pct: 100` until `resets_at` (the window's known reset when it is still ahead, else 5 hours on), as a reading of that moment, so a later sample or probe reading replaces it, and the mark survives a restart. The account's record is re-published, new spawns rank it last until the reset, and its other agents get their own `agent_account_limit` (above). It journals `alarm_raised { alarm: "account_limit_hit", agent_id, acct, resets_at, source }`. Then, when another candidate of the agent's machine is under the level in every window that counts for the agent, it opens an `agent_account_limit` with `class: credit_exhausted`, `window: five_hour`, `pct: 100`, `suggested` that account (the same rule as above), `source` (`hook` or `screen`, with the screen capture as a pointer) and the options `move <agent> to <suggested>` and `not now` (the agent waits at the prompt and Claude Code resumes it at the reset). A task, wave or `claude.default_account` pinning the account does not prevent it: the pin cannot be honoured while the account is at its limit, and the question and the move's `why` say so. When no other account has room, it opens `model_switch` (§4.6.2) instead, as for any credit limit. A `switch to …` answer to the limit-hit `agent_account_limit` switches no model.

#### 4.6.13 Broker logins

The reference deployment authenticates every client with mosquitto's Dynamic Security plugin and therefore requires **mosquitto 2.1 or newer**: its roles scope per-identity grants with `%u` (the client's username), which mosquitto substitutes in Dynamic Security ACLs only from 2.1 on. Tools that manage logins (the account tool, the supervisor) read the broker's version from the retained `$SYS/broker/version`, else from the local `mosquitto -h`, and refuse an older or unknown broker (`BROKER_TOO_OLD`, `BROKER_VERSION_UNKNOWN`) before changing anything.

**Shared roles.** Eight roles are created once and are never edited while clients hold them, because an ACL change on a role disconnects every client holding it: `agent` (read `volley/#`; write its own channels `volley/+/%u/{status,progress,result,capability,usage,control,_user/#}`, its registry entry `volley/_system/registry/%u`, lease requests, and the mailboxes of `volleyd` and `desk` for its acks, §4.4), `account` (the same reads and own-identity writes, plus its machine record `volley/_system/machines/%u` and nothing under it, so no account writes a readiness verdict, §4.6.15), `desk` (write any mailbox and its own `volley/_system/auth/ops/%u`; read `volley/_system/desk-probe/%c`, `%c` the client id, for a browser client's resume probe), `coordinator` (operator-level: any mailbox and any agent's standard channels and registry entry, plus its own `volley/_system/auth/ops/%u`: its username is the fixed `coordinator`, so the topic names the sender, and the supervisor answers only the repository ops there, §4.6.21, so the wave owner adds a wave's repository without an admin account), `admin` (`coordinator`'s operator-level writes plus its own `volley/_system/auth/ops/%u`), `supervisor` (the whole tree except the account-op and answer topics), `volleyd` (the whole tree and `volley-auth/#`) and `token` (its own two `volley-auth/redeem/%u` topics). The fixed identities hold `volleyd`, `account` + `desk`, and `account` + `coordinator`; accounts hold `account` plus their role's (§4.6.10). A login's roles are checked in the order it holds them and the first ACL whose topic matches decides, so a `supervisor` account is bound by any deny in `account`: a topic only the supervisors may write is left ungranted in `account`, never refused there. Changing a role is an explicit, announced operation that reconnects its holders: a broker set up before a change reports the role as drifted, and `volley auth migrate --roles` applies it (the readiness change of §4.6.15 is one such change, and the `desk` role's own account-op topic of §4.6.18 another).

**One login per agent.** A supervisor mints each agent's login as one client (username = agent id, password random, role `agent`) and gives it to the agent in its identity file (§6.5). Logins created or deleted at the same moment (a wave's parallel spawns, a sweep) go to the broker as one control message: mosquitto rewrites its whole state file per message, so the batch window (`dynsec_batch_ms`, §4.6.4) turns N rewrites into one, and each command's answer is matched to its own agent (one failed element fails only that spawn).

**Deleting a login.** Deleting (or disabling) a client disconnects it without publishing its will, so no LWT reports the agent gone. Whenever a supervisor deletes an agent's login (retiring the agent, stopping its wave, a sweep) it first publishes the agent's retained `status` as `reaped` with `payload.reason: "credentials_deleted"`, then clears the agent's retained records (registry entry, `status`, `progress`, `result`, `capability`, `screen`, `usage`), then deletes the login, and journals `agent_reaped_by_supervisor` and `credentials_revoked`. Stopping a wave deletes the logins of all its agents that have not ended by the end of its grace (`stop_grace_s`) at once.

**Sweep.** Logins never expire, and every change costs a rewrite of a file that grows with the number of logins, so a supervisor sweeps: at start and every `credential_sweep_interval_s` it lists the logins holding only the `agent` role and deletes, through the sequence above, each one with no live agent behind it (none of its tasks' agents running in a wave that is neither stopped nor complete, no worktree lock, no non-terminal retained status) that it did not mint within `spawn_timeout_s`; journaled `credentials_swept { agent_ids }` in the `_system` journal. It never touches a login holding any other role.

**Cleanup.** A wave's cleanup (§4.6.26) also deletes, through the sequence above, every login of the wave that a retired agent left behind (`agent_spawned { credentials: "minted" }` with no `credentials_revoked` since, as a crash leaves it); agent logins only, never an account. An account made for one wave (`account_create { wave }`, `volley auth add <name> --role <r> --for-wave <wave>`; `account_created { …, wave }`) is revoked by that wave's cleanup (`account_revoked`); an account without `wave` is a person's or a device's and no cleanup touches it.

#### 4.6.14 Machines and pairing

A supervisor MAY run agents on other machines (§4.6.1 `tasks[].host`). **Pairing** turns a machine into such a host with one code: the operator asks the supervisor for a pairing code, and one command on the new machine uses it.

**Who may call them.** `peer_invite` and `peer_remove` create and revoke broker accounts' access, and `peer_doctor` runs commands on a paired machine, so they are admin ops: an admin sends them exactly like an account op (§4.6.10: `payload: { op, ... }` on `volley/_system/auth/ops/<username>`, answered on `volley/_system/auth/replies/<correlation_id>`), and the supervisor applies the same admin-role check. It refuses them on its mailbox, which does not name the sender. `peer_join` and `peers` are mailbox control queries (§4.6.4's request/acknowledgement shape): a join's credential is its code.

**Ops.** `peer_invite { reply_key, ttl_s?, for? }` answers with a single-use code `XXXX-XXXX` (by default valid 10 minutes, at most that), sealed in `sealed` to `reply_key` as `{ code }` exactly like an account op's secret (§4.6.10), since every account may read the answers; `result` carries only `{ expires_at, ttl_s, for? }`. The supervisor keeps only a salted hash of each code. `for` binds the code to a name (a §2.1 name, else `for must be a machine name ([a-z0-9][a-z0-9_-]{0,62})`): a machine this supervisor paired (a re-pairing code), or a name not configured yet (the code pairs that new machine, as an unbound code would; `volley machine add`); a host configured by hand that it did not pair is refused (`"<for>" is a host configured by hand, not one this supervisor paired: no code re-pairs it`). The binding is kept in the code's hashed entry, so the code joins only as that name. `peer_join { code, name, target, volley_dir, repo?, worktree_root?, port?, tunnel?, os?, cores?, memory_total_mb?, replace?, reply_key }` burns the code, creates an account `name` with role `peer` and kind `machine` (§4.6.10), adds `hosts.<name>` to its configuration (§4.6.4) with `target`, `repo`, `worktree_root`, `volley_dir`, `tunnel: { remote_port: <port>, supervise: false }` and, when the join carries `cores` and `memory_total_mb`, `max_agents` derived from them (§4.6.15; a re-pairing keeps a configured one), and answers `result: { name, namespace, broker: { host, port }, remote_port, tunnel? }` with the new account's `{ username, password }` in `sealed`. `broker.port` is the broker's MQTT port on its machine as the machine roles record names it (`broker.address.mqtt_port`, §4.6.24). `tunnel` is `ssh` (the default: the machine keeps its own `ssh -L` tunnel and reaches the broker at `127.0.0.1:<remote_port>`) or `none`, for a machine the broker itself runs on: no tunnel, `remote_port` is the broker's port and is what `hosts.<name>.tunnel.remote_port` records, so its agents' launch environment names `VOLLEY_BROKER_URL=mqtt://127.0.0.1:<broker port>`. `name` uses the §2.1 grammar and is never `local`, `auto` (both reserved by a wave file's `host:`, §4.6.15) or a fixed identity (`volleyd`, `desk`, `coordinator`); a name that is already a configured host, or the supervisor's own machine name (§4.6.15), is refused, except by a re-pairing (below). A code bound to another name is refused (`this pairing code re-pairs <for> only`), and so is a configured name joined with an unbound code or without `replace: true`, or an existing account of that name whose role is not `peer` (`"<name>" is a <role> account, not a peer: not replaced`). These refusals come before the code is burned. **Re-pairing**: `replace: true` with a code bound to `name` re-pairs an already paired machine (a new ssh target, a lost credential, a fresh install) without removing it first: the supervisor rotates the existing `peer` account's password instead of creating an account (or creates it if it is gone), merge-patches `hosts.<name>` with the join's fields (so a hand-set `max_agents` or `drain` stays), and answers as a join does, the new password in `sealed`. An unknown, used or expired code is refused (`invalid or expired pairing code`); after `peer_join_max_failures` wrong codes every outstanding code is revoked, so a code cannot be guessed. The supervisor remembers the names it paired. `peer_remove { name }` revokes the account (refused for an account whose role is not `peer`), removes `hosts.<name>` and clears the machine's retained record; it is refused for a name that is neither a paired machine nor a `peer` account, so a host configured by hand is never removed. `peer_remove { name, drain: true }` on a machine with live agents (supervised, launched and not yet verified, or spawns in flight there) does not remove it at once: it sets `hosts.<name>.drain: true` (nothing new is placed or spawned there, §4.6.15), answers at once with `result: { name, removing: "drain", agents, revoked: false, host_removed: false }` and journals `peer_drain_started`, and the supervisor removes the machine as above once no agent runs there (journaling `peer_removed`). `{ name, now: true }` does the same but also stops those agents: each is sent a mailbox `cancel` (at once, or, for one that comes up later, once it is supervised), and one still live `stop_grace_s` after its own `cancel` is force-retired (`agent_force_retired { reason: peer_remove }`): its role ends as stopped and opens its respawn decision, which offers `respawn on <best>` (§4.6.15). A `done` an agent publishes before that is verified as any `done` is. A machine being removed stays closed to new agents until the removal finishes; a removal is not called off. `drain` and `now` are booleans and exclude each other; on a machine with no live agent either removes at once; a second removal of a machine being removed is refused (`"<name>" is being removed already`). A pending removal survives a restart. `peers` lists the paired machines' names (`hosts`) and their records (`machines`). `peer_doctor { name, fix?, clone?, repos_add?, repos_remove? }` (a Desk's Repair) runs the machine's doctor on the configured host `name` over ssh: the supervisor runs the machine's own checkout, `bun <volley_dir>/packages/volley-cli/src/cli.ts peer doctor --json --supervisor-volley-dir <volley_dir>`, never a `volley` on the machine's `PATH` (once more without that flag when the machine's volley refuses it), plus `--fix --yes` when `fix` is `true` and `--clone --origin <url>` when `clone` is `true`, in the host's `volley_dir` as one step of the same `ssh -T <target> bash -s` that launches agents there; besides `peer_retarget`'s and a machine role move's steps (§4.6.24), run the same way, it runs no other `volley` command on a machine. When the doctor prints no report because `bun` is not on the machine's ssh `PATH` or the checkout's CLI is not at that path, the reason names which and its fix. `fix` and `clone` are booleans (default `false`), and `clone` needs `fix` (`clone needs fix: true`). `<url>` is the wave repo the machine clones: the running wave's origin as the supervisor's own clone reports it (§4.6.15), as `https://<host>/<path>`, never with credentials or a port; while none is known (no wave runs, or its origin has a port) `clone` is refused (`the wave repo's origin is not known …`). `repos_add` (each `<owner/name>` or `<owner/name>=<absolute path>`) and `repos_remove` (each `<owner/name>`), at most 64 and one list or the other, pass `--repo-add` / `--repo-remove` for each (§4.6.21); with `repos_add`, `clone` passes `--clone` alone (each added repository is cloned from its GitHub URL) and needs no origin. The repository ops (`repo_add`, `repo_remove`, `repo_list`, `repo_status`, `repo_probe`) are §4.6.21's. An unknown name is refused (`no configured host named "<name>"`), and so is a second `peer_doctor` for a host whose run has not ended (`a doctor run on "<name>" is already in progress`), so two fixes never overlap on one machine; these refusals come before anything runs. The answer is `result: { name, fix, checks, versions?, auth?, repo?, memory?, disk?, doctor_at, plan? }`: the doctor's report (each check `{ id, ok, severity, detail, fix? }`), and, when `fix` is `false`, `plan`, the failing checks that carry a fix as `{ id, severity, detail, fix }` in the doctor's order, so a client shows what a fix would do before anyone runs it. When ssh fails, or the doctor prints no report, the answer is `ok: false` with the reason. A run can take minutes (a fix may check out and install volley), so the supervisor answers it when it ends and handles every other request meanwhile. `peer_retarget { name, address, port?, tunnel? }` (admin) re-points the tunnel of the configured host `name` (a step of a broker move, §4.6.24): `address` is the ssh destination its tunnel reaches the broker's machine at from now on (never starting with `-`), `port` its tunnel port on its loopback (1024..65535), `tunnel` `ssh` or `none` (no tunnel: the broker runs there; `port` then defaults to the broker's). The supervisor runs `volley peer retarget --to <address> [--port <port>] [--tunnel ssh|none]` there over ssh, as `peer_doctor` runs the doctor; the machine rewrites its `peer.json`, restarts its service and exits 0 only once the tunnel answers. A given or implied `port` is written to `hosts.<name>.tunnel.remote_port`. The answer, `result: { name, address, port?, tunnel?, up: true }`, waits for the machine's record to come `up` through the new tunnel; when it does not within the grace, or ssh or the command fails, the answer is `ok: false` with the reason. An unknown name and a malformed address are refused before anything runs. `machine_add { address, auth: { key } | { password_ref }, sudo_ref?, name? }` (admin; the Desk's Add a bare machine) makes the bare box at the ssh destination `address` a paired machine `name` (default: the host's short name) by running `volley machine add`'s steps without a terminal (ssh, Volley, Setup, ssh back, Pairing, Sign-ins, Doctor), every one over `ssh -T <address> bash -s` (never `ssh -t`): the first ssh installs the supervisor's own key on the box, signing in with `key` (an absolute path to a key file on the supervisor's machine) or `password_ref` (the password: ssh reads it through an `SSH_ASKPASS` helper from a 0600 file in a fresh temporary directory, removed when that step ends), and every later step is BatchMode with that key; a host key is trusted on first contact. Install.sh runs sudo only when the box lacks what only sudo installs (git, tmux, curl or gh on Linux), announced first, through a `SUDO_ASKPASS` helper on the box that reads `sudo_ref` from a 0600 file its trap removes when the step ends; without `sudo_ref` such a box stops at that step. The pairing code is minted bound to `name` and never leaves the supervisor; the two sign-ins are left to the Machines window's own buttons. Neither password is ever journaled, logged, answered or sent in an argv (both travel only on ssh's stdin). While it runs the supervisor publishes `progress` envelopes on the reply topic with the request's `correlation_id`, `{ op: "machine_add", step, total, title, state: "running" | "failed", line? }` (a step starting has no `line`), then answers `result: { name, target, ready, signin: { gh, claude }, checks, doctor_at? }` (`ready`: §4.6.15's readiness of the doctor's report), or `ok: false` with `step <n> (<title>): <what failed and its fix>`. A malformed request, a name that is a host configured by hand, a key file that is not there, and a second `machine_add` for a name whose run has not ended (`"<name>" is already being added: wait for that run to end`) are refused before anything runs. The `_system` journal records `peer_invited { by, expires_at, for? }` (never the code), `peer_joined { by, name, target, os?, cores?, memory_total_mb?, max_agents?, replaced?, tunnel? }` (`max_agents`: the value the join derived, when it wrote one) (`replaced: true` on a re-pairing), `peer_drain_started { by, name, mode, agents }` (`mode`: `drain` or `now`; `agents`: the live agents it waits for), `peer_removed { by, name, revoked, host_removed }` and `peer_doctor_run { by, name, fix, clone, ok }`, `peer_retargeted { by, name, address, port?, tunnel? }`, `machine_added { by, name, target, auth, sudo, ok, ready?, step? }` (`auth`: `key` or `password`; `sudo`: whether a sudo password was given); the configuration change is a `config_changed` as usual (a removal's patch reads `{ hosts: { <name>: null } }`).

**The tunnel.** A paired machine keeps its own way to the broker: a service on the machine (the reference one runs `volley peer run` under systemd or launchd) holds `ssh -N -L 127.0.0.1:<remote_port>:<broker host>:<broker port> <supervisor's machine>`, so its `127.0.0.1:<remote_port>` is the broker, as a supervised reverse tunnel would make it (§4.6.1, `supervise: false`: the supervisor only checks it). Every remote step of the join runs on the supervisor's machine as a script on stdin to `ssh <host> bash -s`; the code travels in that script, never on a command line.

**Machine records.** `volley/_system/machines/<name>` (QoS 1, retained, `machine.schema.json`) holds `{ name, os, arch?, cores, tunnel, reason?, load, agents, remote_port?, last_seen }`, where `load` is the 1, 5 and 15 minute load averages, `agents` the machine's agent sessions and `tunnel` `up` or `down`, plus the optional Fleet fields of §4.6.15 (`kind`, `memory`, `disk`, `uptime_s`, `versions`, `auth`, `repo`, `repos`, `checks`, `claude_logins`, `doctor_at`). `repos[]` lists each repository the machine works on (its doctor's configured repositories, by GitHub `owner/name`) as `{ slug, path, exists, origin?, managed, fetched_at, release_branch?, toolchain: { ok, missing, outdated } }`: `managed` is `true` for the managed clone (`<repo_root>/<owner>/<name>`), `false` for an adopted one, and `toolchain` names the tools that repository needs which the machine lacks or has older than its minimum. A check about one repository carries `repo: "<owner/name>"`; failing, it is that repository's, not the machine's. While exactly one repository is configured, `repo` carries it too (kept for one release). The machine publishes it as itself (`agent_id` = `name`; the shared `account` role grants `volley/_system/machines/%u`, §4.6.13) through its tunnel every `machine_heartbeat_ms` (30 s), so a record that arrives means the tunnel works; its LWT is the same record with `tunnel: "down"` and `reason: "disconnect"`, retained. An LWT is set when the machine connects, so its `last_seen`, `load` and `agents` are the connection's; a supervisor keeps the values of the last `up` record it received when an LWT arrives. Only records for a configured host count (every account may publish its own). A supervisor folds the records in on its own clock (a machine's clock may be skewed) and marks a machine whose record has not arrived for `machine_down_after_ms` (90 s) down: it republishes the record as itself with `tunnel: "down"` and `reason: "heartbeat_timeout"`. After a `peer_doctor` it started (§4.6.15) on a machine whose record is `up`, the supervisor also republishes that record as itself, its doctor fields (`checks`, `doctor_at`, `versions`, `auth`, `repo`, `repos`, `memory`, `disk`) replaced by the run's report (a report without `repo` or `repos` clears the record's), so clients and readiness follow the run without waiting for the next heartbeat; while the machine's own heartbeats still carry an older run (§4.6.15), it republishes each of them with the newer run's `versions`, `auth`, `repo`, `repos`, `checks` and `doctor_at` and the heartbeat's own `memory` and `disk` (§4.6.15). A record the supervisor publishes is not a heartbeat: it does not keep a machine up, nor bring a down machine back up. While a machine is down, new spawns on its host park (`why_waiting: "tunnel down to <name>: no heartbeat for 90 s"` or `...: disconnected`) and each wave with unfinished tasks there journals `alarm_raised { code: MACHINE_DOWN, host, reason, last_seen, tasks }`; the next record with `tunnel: "up"` resumes them. Running agents are never touched, but the wave state shows them: every unfinished task on the host carries `tasks[].host_down` (§4.6.1) until the machine is back. A machine whose account is revoked stops its tunnel service when the broker next refuses it. The tunnel service never sits idle while it runs: a lost broker connection is dropped (its disconnect bounded) and reopened on the next heartbeat, a heartbeat that has not finished within a bound is given up, and a service that has published no heartbeat for a bound (the reference: 10 minutes) exits non-zero so its service manager restarts it; it logs each connect, loss, reconnect attempt and tunnel start and exit, never a credential.

**The private address.** A record MAY carry `network: { kind, name?, address? }`: how the machine is reached from outside its own network, as its install recorded it (the reference tools: `volley setup`'s network step, in `setup.json`). `kind` is `tailscale` (`name` the MagicDNS name, `address` the tailnet IPv4 address), `manual` (`address` the address the owner's own VPN gives the machine) or `none`. A paired machine publishes it with every heartbeat and the supervisor with its own record; a record without it says nothing about reach. It is informational: readiness (§4.6.15) never reads it. The doctor's `network.private` check is `ok` when the kind is not `none` and the machine is reachable that way now (Tailscale signed in, or the manual address bound to one of its interfaces), else a `warn` whose fix is `volley setup --step network`.

#### 4.6.15 Fleet

The Fleet turns paired machines (§4.6.14) into places the supervisor can put work without being told: each machine reports its health, the supervisor judges whether it can run an agent, and a wave that opts in has its tasks placed by load with every choice explained. Everything here is optional on the wire: a machine record without the fields below, a wave file without `placement` and a config without the Fleet tunables stay valid, and a wave that does not opt in runs exactly as before.

**The machine record.** A machine whose doctor has run (`volley peer doctor`, by hand, by `peer join`, by its heartbeat or by a Desk's Repair) adds to its record (`machine.schema.json`): `kind` (`peer`, the default, or `supervisor`); `memory { total_mb, available_pct }`, where `available_pct` has one definition on every machine so that placement can compare them: memory the kernel can hand out without paging anything active out, over total memory (Linux: `MemAvailable`; macOS: `vm_stat`'s free, inactive, speculative and purgeable pages times the page size, never the free pages alone, which a healthy Mac keeps in single digits; a machine that cannot measure it omits `memory`); `disk { path, free_gb, free_pct }` for the filesystem that holds its worktrees; `uptime_s`; `versions { peer, volley, bun, node?, git, gh?, tmux?, claude? }`, each a string or `null` (missing) as the machine's doctor finds it (for `bun` and `claude`, the copy on the non-interactive ssh PATH when one resolves there); `auth { gh, claude, trust, claude_plan?, claude_email?, claude_org? }` with `gh` `ok` \| `unauthenticated` \| `missing` \| `no_write`, `claude` `signed_in` \| `not_signed_in` \| `missing` \| `unknown` (its default Claude profile) and `trust` `ok` \| `missing` \| `unknown` (that profile's trust of the wave repo's folder); `claude_email` and `claude_org` the default profile's identity (§4.6.11), only while it is signed in; `repo { path, exists, origin?, release_branch?, fetched_at? }`, with `origin` normalised to `<host>/<path>` (no scheme, user, credentials or `.git`); `checks[]` (at most 32), each `{ id, ok, severity, detail }` with `severity` `block` (a failing check makes the machine not ready) or `warn` (a doctor's own estimate of the non-interactive ssh PATH, such as the reference doctor's `bun_on_path` and `claude_on_path`, is a `warn`: the supervisor's `path_ok` probe of the real one decides); `claude_logins[]` (at most 16), each login's usage probe state and last reading (§4.6.12), numbers only: no directory, no e-mail, nothing token-shaped; and `doctor_at`, when that doctor run started (so a run that began before a fix never passes for one that ran after it). A supervisor keeps the newer run's `versions`, `auth`, `repo`, `repos`, `checks` and `doctor_at`: an `up` record whose `doctor_at` is older than the one it holds for that machine updates everything else (its live `memory`, `disk` and `uptime_s` included), not those fields. The record carries states only, never a secret, and never a fix's text: the doctor that reads a record supplies its own. The record stays closed (`additionalProperties: false`), so a field outside this list is invalid.

**The supervisor's own record.** The supervisor publishes a record for its own machine as itself, with `kind: "supervisor"` and `tunnel: "local"` (valid only with that kind), on `volley/_system/machines/<local_name>`, where `<local_name>` is the `fleet.local_name` tunable (§4.6.4). When it is `null` the supervisor derives the name from its host name: the first DNS label, lowercased, every character outside `[a-z0-9_-]` replaced by `-`, leading characters that are not `[a-z0-9]` dropped, cut to 63 characters; a result that is empty, `local`, `auto` or a fixed identity (`volleyd`, `desk`, `coordinator`) becomes `supervisor` (so `MacBook-Pro.local` is `macbook-pro`). The name is never `local` or `auto`, which a wave file's `host:` reserves. It is never a configured host either: the supervisor refuses a configuration (`config_set` or `config.yaml`) in which `fleet.local_name` equals a `hosts.<name>` key, or a `hosts.<name>` equals the resolved name, and `peer_join` refuses it as a name (§4.6.14), so two machines never write one record topic. The retained effective config (`volley/_waves/_config`) carries the resolved name in `fleet.local_name`, never `null`: a client recognises the supervisor's machine by that name, which only the supervisor publishes, not by a record's `kind`, which a machine states about itself. The supervisor likewise treats a configured host's record as a peer whatever its `kind`. The supervisor's machine is a placement candidate like any other; in placement and lease state it appears under that name, while `tasks[].host` stays absent for it (§4.6.1).

The supervisor is its own machine's doctor: it runs the same checks locally when it starts, every `machine_heartbeat_ms` after and whenever the running waves' repos change, and fills its own record's Fleet fields (`checks`, `doctor_at`, `versions`, `auth`, `repo` and the rest) with the results, so its machine is ready on the same terms as a peer. It is no peer and has no peer configuration, so the clones it checks are the running waves' repos: it runs the doctor once per running wave's clone (each clone once, by wave id), given as `--repo`, and folds the runs into one record, the machine-level checks of the first run and, per clone, its `repo.*` checks (tagged with the wave's `owner/name`) and one `repos[]` entry; a clone whose run fails keeps what the last report said of it. While no wave runs it runs once without `--repo` and checks no clone. A clone's `repo.*` checks judge that repository only, never the machine (Readiness, below), and no clone is compared by origin: clones are compared by slug only. There is no ssh hop to itself: its `path_ok` says whether `claude` and `bun` resolve in the environment the supervisor gives its own agent sessions, and it is probed there. Until that first local run completes, its own machine is not ready like any other machine without a doctor report. After a `repo_clone_removed` (§4.6.26) the next doctor run on that machine re-reads its clones: the deleted clone's `repos[]` entry reads `exists: false` until config stops naming the repository there (the registration's `repo_remove`, which follows the delete), and readiness judges it as it judges any missing clone.

**Readiness.** `volley/_system/machines/<name>/readiness` (QoS 1, retained, `readiness.schema.json`) holds the supervisor's verdict on each machine, its own included: `{ name, ready, reasons[], drain, max_agents, placed, path_ok: { claude, bun }, requirements: { volley, bun?, sharing?, repos? }, heavy: { <pool>: { held, per_machine } }, usage: { account, five_hour_pct }, repos?, eligible, ineligible_reason?, local_agents?, checked_at }`. `ready` is `true` when nothing blocks an agent there (the tunnel is up or local, no `block` check fails, `claude` and `bun` resolve on the PATH an agent's session gets, which the supervisor probes itself (`path_ok`: the non-interactive ssh PATH on a peer, its own agent environment on its own machine), the machine's volley matches `requirements.volley`, GitHub may push, git can commit (in the home or in a clone the record reports) and Claude is signed in); `reasons` has one line per blocker and is empty when ready. A repository never blocks `ready`: `repos` judges each one on its own, keyed by its GitHub `owner/name` (every running wave's repository, and every one the machine's record reports; an older record's single `repo` counts as its origin's slug), as `{ state, path?, reasons[], fetched_at? }` with `state` one of `ready` (its clone exists and passes its checks), `blocked` (a failing per-repository `block` check, such as `repo.push`, the machine's own `gh` may not push to that repository, or `repo.worktrees`, the folder its worktrees are cut under can be neither written nor created, or `repo.identity`, git has no commit identity in that clone as git resolves it, its own config before the global and the system's; or a tool the repository needs that is missing or too old: `java not installed (needed by owner/name)`), `absent` (no clone) or `cloning`. On a paired machine a clone is also compared with where the supervisor would spawn the repository's agents (the clone its config and the machine's record resolve to): a `ready` clone reported at another path is `blocked` (`the supervisor would spawn in <path> but <machine> reports its clone at <path>`), and the supervisor probes that path itself on the PATH probe's cadence (`path_probe_interval_ms`, at once when the path changes), so a clone the probe finds missing, or a clone of another repository there, is `blocked` too (`no clone at <path> on <machine>`, `<path> on <machine> is a clone of <owner/name>`); a probe that could not run changes nothing (the PATH probe's reason says so), and until the first probe the record stands. A repository a spawn found no clone of there (below) is `blocked` with that spawn's message until a probe finds the clone. Placement skips a machine whose clone of the wave's repository is not `ready`, with the candidate line `ineligible: no ready clone of <owner/name> (<state>: <first reason>)`. Clones are compared by slug only: a clone of another repository is no blocker of the machine. A record without a doctor report is not ready (`no doctor report: run volley peer doctor`), and nor is one whose `git.identity` check (the home's identity: the global or the system's) fails while no `repo.identity` check of the record passes, a `warn` check that never holds up a join (`git: no commit identity on <machine> (volley setup --peer --step signin)`): an agent's first commit there would fail. A clone with its own identity commits on a machine with no global one, so then only a clone without one is `blocked`. `requirements` is what the supervisor asks of the machine (its own volley version, its lowest accepted bun, its per-item sharing modes, §4.6.11, which the machine's doctor applies to its own Claude profile, and `repos: { <owner/name>: { git_email } }` for each repository config expects an email for, §4.6.4, absent when none does: the machine's doctor fails `repo.identity` for a clone that would commit under another email, compared case-insensitively, and the supervisor blocks that repository there as soon as the record's passing `repo.identity` names another email, before the doctor runs again); `placed` counts the machine's live supervised agents plus the placements reserved for it that have not spawned; `heavy` has the machine's holders' leases in each pool that sets `per_machine` or a `per_machine_overrides` entry for the machine, with the cap in force there (§4.6.5); `usage` is the machine's best candidate account (the one the rank rule, §4.6.12, puts first there, or the account `claude.default_account` pins on the supervisor's machine) and its 5-hour percentage (§4.6.12; `null` while unknown), so a machine with one hot login and one fresh one stays eligible. `eligible` says whether placement may put a new task there now, and when it is `false`, `ineligible_reason` says why in one line: it is placement's own machine filter (below), everything but a heavy task's slots, under the supervisor's config (a wave's own `placement` overrides apply to its tasks), and `ineligible_reason` is the same text as that machine's placement candidate line without its `ineligible: ` prefix, so a client never shows `eligible` next to a placement that skips the machine. The supervisor re-computes the verdict whenever it folds in a record, a config change or a placement, re-publishes it when anything but `checked_at` changed and otherwise at least once every `machine_down_after_ms`, so `checked_at` says when the verdict was last computed, clears it when the host is removed, and journals `machine_readiness_changed { name, ready, reasons }` in `_system` when `ready` or `reasons` change. A verdict waits for its inputs: after the supervisor starts, it neither publishes nor journals a machine's verdict until that machine's record has arrived and its first PATH probe has finished (no probe runs while its tunnel is not up), or, for its own machine, its first local doctor run has finished, and at most `machine_down_after_ms`. So a restart leaves the last retained verdict in place instead of a verdict computed from nothing, and the first verdict with its inputs is compared with the last journaled one (with none, it is the baseline and journals nothing). Only the supervisor publishes readiness. The record is the machine's statement about itself; the verdict needs the supervisor's config and version, and two writers on one retained topic would interleave, so the verdict has a topic of its own. The broker ACL lets no account write a readiness topic, its own machine's included: the `account` role grants the record topic `volley/_system/machines/%u` and nothing under it (§4.6.13), so only the supervisor's identities (`volleyd`, `supervisor`) may publish there. A client MUST accept readiness only from the supervisor's `agent_id` as a sanity check (the envelope's `agent_id` is written by the publisher, so the ACL is what makes the verdict trustworthy), and the supervisor never reads a verdict back (placement uses the one it computed). A client shows a verdict as stale while the supervisor's own `status` is not live, or when its `checked_at` is older than twice `machine_down_after_ms`. A client that shows machines subscribes `volley/_system/machines/#` and gets both.

**Caps and drain.** `hosts.<name>.max_agents` (1 to 100) caps the supervised agents a host runs at once. A join writes it from the machine's size, `clamp(min(floor(cores / 3), floor(memory_total_mb / 4096)), 2, 16)` (a 32-core, 60 GB machine gets 10; a 10-core, 32 GB one 3); unset, the supervisor derives it the same way from the machine record's `cores` and `memory.total_mb`, and uses 4 when either is unknown; an explicit value always wins. The doctor's `machine.size` row shows the derived figure (`max_agents 10 (derived from 32 cores, 60 GB)`). The supervisor's own machine is capped by `hard_ceiling`, which also still caps the total, so its verdict's `max_agents` is `hard_ceiling` and its `placed` counts every live supervised agent, wherever it runs. `hosts.<name>.drain: true` takes a host out of placement: nothing new is placed or spawned there, and its running agents finish. A spawn for a task already placed on a host closed to new agents (draining, being removed, or removed) parks with a plain `why_waiting` (`<name> is draining: nothing new starts there; re-place or cancel <task> (its machine_down decision)`) until the owner answers that host's `machine_down` decision (below).

**The supervisor's own machine as a fallback.** `fleet.local_agents` sets how the supervisor's own machine takes auto-placed tasks: `always` (a candidate like any peer), `fallback` or `never`. `null`, the default, resolves to `fallback` when any `hosts.<name>` is configured and to `always` otherwise; the retained effective config carries the resolved value, and a change that flips it (the first host added, the last removed) is journaled as `config_changed` for `fleet.local_agents` with `by: volleyd-defaults`. Under `never` the own machine is never a candidate for an auto-placed task (its line: `ineligible: local_agents: never`); a task that names `host: local` still runs there, because the wave file is explicit (`volleyd validate` warns about it). Under `fallback` the own machine takes an auto-placed task only while no paired machine is eligible (below); while one is, its line is `ineligible: fallback: <peer> is eligible`. A peer that is down counts as ineligible only once it has been down for `placement.down_decision_after_s` (the `machine_down` grace, below): until then the own machine stays closed (`ineligible: fallback: box-a may be back (down 40 s, grace 300 s)`, which a waiting task's `why_waiting` names), so a tunnel blip never pulls work onto it. A peer the task is being moved off counts as ineligible. "Eligible" here is the peer's task-agnostic readiness verdict (its `eligible`), so readiness and placement agree: a peer that takes work but has no free heavy slot still keeps the own machine closed, and a heavy task waits for a slot there rather than falling back. With no peer eligible, the own machine is eligible under the fallback profile: at most `fleet.fallback.max_agents` (1 to 100, default 3) of the agents on it alone (its live agents and reservations, not every supervised agent; `hard_ceiling` still caps the total), with the line `<n>/<max> agents (fallback max_agents)` when full, and in each heavy pool at most `fleet.fallback.per_machine.<pool>` slots (0 to 64; a pool it does not name gets 1 when the pool has a per-machine cap there; never more than that cap; 0 keeps heavy tasks off it). Its candidate line, when it is chosen, starts `local (fallback: no peer eligible: <closest peer>: <its first reason>)`. When a peer becomes eligible again, the next placement goes to it; nothing running is moved, and a task already placed on the own machine stays placed there for every role. Under `always` nothing changes. The own machine's readiness verdict carries `local_agents: { mode, active, why? }`: its mode, whether the fallback profile is in force now (`fallback` and no peer eligible), and `why`, the closest peer's reason while active, else the eligible peer (`box-a eligible`) or the one that may be back; a peer's verdict never carries it, and the verdict's `eligible` is the same filter. `volleyd status` prints `local agents: fallback (idle: box-a eligible)`, `local agents: fallback (active: box-a: tunnel down …)`, `local agents: always` or `local agents: never` in its header while a paired machine is configured.

**The own machine's terminal.** `fleet.local_terminal` (§4.6.4) sets whether the supervisor's own machine runs its agents in cmux or tmux; a paired machine's agents always run in tmux. `volley setup`'s Terminal step records the choice (`cmux` on a Mac with cmux, else `tmux`, and it blocks while the chosen terminal is missing); a supervisor moved to a machine without cmux runs its agents through tmux once its Terminal step runs there (an explicit `cmux` in `config.yaml` is kept until then). Only a machine with neither terminal should be set `fleet.local_agents: never`.

**Placement.** A wave file's `placement: auto` places every task that does not name a host; `placement: local` keeps them on the supervisor's own machine; a task's `host: auto` places that task under either setting. A wave file without `placement:` takes `placement.default` (`local` \| `auto`, default `auto`; the wave's own `config:` value wins over the supervisor's) when at least one paired machine (a `hosts.<name>`) is configured, and `local` when none is; the supervisor decides it when the wave is first submitted, and a later plan version without `placement:` keeps the placement the wave's current plan has (its own `config: placement.default` does not change it), so pairing or unpairing a machine mid-wave never moves a task's next role; `volleyd validate` / `run` print the outcome with the machines' names (`placement: auto (placement.default; this machine macbook-pro, 1 paired: box-a)`, `placement: local (no paired machine; this machine macbook-pro)`). Every other task runs where its `host:` says, as before. A task's `host:` names a machine as `local`, a configured `hosts.<name>`, an inline host, or the supervisor's own machine by its resolved `fleet.local_name` (§4.6.4), which is the `local` token from then on. `placement_prefer` / `placement_avoid` name machines the same way. Any other name is refused before anything runs (at submit against the effective config; offline by `volleyd validate` against `config.yaml` when there is one), at its path, with the names it knows: `unknown host "mac": this machine is macbook-pro; paired: box-a`. A task is placed once, when the scheduler first admits it, and every agent of the task then runs on that host (§4.6.1). A plan version that changes the host of a task admitted but not yet spawned (`local` → `auto`, `auto` → a name, a name → `auto`) gives its admission back: the supervisor journals `task_admission_returned { task, from_host, to_host, plan_version }`, the task is no longer admitted or placed, and the next tick admits (and, under `auto`, places) it afresh. A spawn never resolves `auto`: a task that reaches one unplaced raises `host_auto_unresolved` and, when admitted, gives its admission back (`task_admission_returned` from `auto` to `auto`), so the next tick places it and its `why_waiting` is placement's; one not admitted waits (`not placed yet: its host is auto`). The candidates are the supervisor's own machine and every configured host with a machine record. A machine is eligible when its readiness is `ready`, it is not draining, `placed` is under its `max_agents`, its load per core (the higher of its 1- and 5-minute load averages) is at most `placement.load_per_core_max`, its available memory is at least `placement.mem_available_min_pct` and its free disk at least `placement.disk_free_min_gb`, its best candidate account's 5-hour usage is under `claude.warn_at_pct` (unknown usage passes; the candidate line names the account, `usage 12% (work)`), and, for a task marked `heavy: true`, every pool in the wave's `heavy_pools` that sets `per_machine` has a free slot there. Each eligible machine scores, in 0..1, the weighted mean of its headrooms: CPU (`1 - load per core / load_per_core_max`, floored at 0), free slots (`(max_agents - placed) / max_agents`), memory (`available_pct / 100`) and usage (`1 - five_hour_pct / 100`), weighted by `placement.weights` (relative weights, default CPU 40, slots 30, memory 15, usage 15; they need not sum to 100, and a configuration with all four at 0 is refused); a headroom that is unknown is left out and the remaining weights renormalised. When the weights of the known headrooms sum to 0, the machine scores 0 and its `line` says that no weighted headroom is known. Eligible machines in the wave's `placement_prefer` rank first, those in `placement_avoid` are used only when no other machine is eligible, and ties go to the machine with fewer placed agents, then the name. The best machine is reserved at once (it counts in `placed` until the task's agent is supervised, and a heavy task also counts in `heavy.<pool>.held` of each of its pools there), so concurrent placements spread and heavy tasks do not stack on one slot. When no machine is eligible, the task stays queued with a `why_waiting` that names the closest machine's reason, and is placed again on the next sample. The supervisor journals `task_placed { task, host, score, candidates, by, from?, why?, local? }` and shows the same in the task's `placement` (§4.6.1): every candidate with its score and a one-line `line` the supervisor writes, an ineligible one with `score: null` and its reason. Under `placement: auto` a task whose host the wave file names is recorded `by: "wave_file"` with that one candidate. Nothing running is ever moved: placement decides where a task starts, never where it continues.

**Fresh base.** Before cutting an agent's worktree on any host, the supervisor fetches the release branch there. With `require_fresh_base: true` (the default, on every host), a fetch that fails fails the spawn as a spawn failure (§4.6.1 `last_error`) rather than cut the worktree from the host's last copy. The commit the worktree was cut from is the task's `base_sha` in the wave state, the `base_sha` of its `agent_spawned` event's `data`, and part of the gated head's evidence (§4.6.8).

**Merge nudge.** When a wave's PR merges, the supervisor sends one `steering` mailbox message (§4.4) to each running implementer of that wave whose task's `files` overlap the merged PR's changed files (`placement.nudge_on_merge: files`, the default), or to every running implementer (`all`), asking it to bring the release branch in before it pushes again; `off` sends none. Each nudge is journaled as `merge_nudge_sent { task, agent_id, merged_pr, files }` (`files`: the overlap; empty under `all`), at most one per agent and merged PR.

**A machine that stays down.** While a machine is down, its spawns park as §4.6.14 says. When it has been down for `placement.down_decision_after_s` (default 300) and a wave has unfinished tasks on it, the supervisor opens one wave-level `machine_down` decision (§4.6.2) per wave and machine, carrying `host`, `down_since` and `tasks`, with the options `wait`, `re-place queued tasks` (pre-filled: the question names where they would go) and `cancel`. A task is running while an agent of it is live (supervised, launched and being verified, or spawning); any other unfinished task there (queued, between roles, or waiting on its respawn decision) is waiting. It never re-places a task without an answer: `re-place queued tasks` places each waiting task of the list again (`by: "decision"`, `from` the down host) and leaves running ones where they are; one with no eligible machine stays (`alarm_raised { code: NOT_REPLACED }`) and is placed as soon as a machine is eligible; `wait` keeps everything parked until the machine is back; `cancel` cancels the listed tasks that have not finished (a running agent is told to stop). A host closed to new agents (draining, being removed, removed) with a waiting task of a wave gets the wave's `machine_down` decision at once, with `machine` set and `wait` offered only while it is draining; an open `machine_down` whose host's trouble changed resolves itself (`superseded` by the supervisor, or `wait` when the host takes new agents again). A decision offering `respawn` for an agent whose host is down or not eligible also offers `respawn on <best>`, which respawns the role on the best eligible machine and re-places the task there; on a closed host it offers `respawn on <best>` instead of `respawn`. The machine is checked again when the answer arrives: one that cannot take the task by then refuses it (the answer is journaled with `(refused: <why>)`) and the question is asked again. An implementer respawn continues the branch its earlier attempt pushed (the same name, cut from origin's copy; its brief names the branch and its open PR), so it never opens a second PR; a branch never pushed is started afresh. A configured paired machine that has been down for `placement.down_decision_after_s` and holds a clone of a running wave's repository SHOULD be told to the owner even when no task waits on it (the supervisor's own machine may have taken its work): the supervisor opens the owner-only notice `n-machine-down-<name>` (§4.6.18; its title names the machine and how long it has been silent, its question the waves it would serve and the command that restarts its tunnel service, `source.since` the down record's `last_seen`) and journals `alarm_raised { alarm: machine_silent, host, down_since, last_seen, waves }` in `_system`, once per outage (an answered notice for the same `last_seen` is not opened again). When the machine's next `up` record arrives, it answers the open notice `superseded` and journals `alarm_cleared { alarm: machine_silent, host }`.

**Falling back off a machine that cannot spawn a task.** A spawn on a paired machine that finds no clone where it would run (`REMOTE_REPO_MISSING`) marks that repository `blocked` in the machine's readiness (above), and when the supervisor chose the machine (`by` other than `wave_file`: `auto`, `decision`, or an earlier `fallback`) and the task has not spawned there yet (no `host_actual`, §4.6.1) it places the task again away from that machine: it journals the `spawn_failed`, then `task_placed { by: "fallback", from, why }` (`why` the spawn's message), opens no decision, and the next tick spawns the task where it now is. When no other machine is eligible, the wave file named the host, or an earlier role of the task already ran there (every later role runs on `host_actual`), the `remote_repo_missing` decision opens as before (the first case's question ends `no other machine can take it now (<placement's reason>)`). Only a missing clone falls back: a machine that is down has `machine_down`, and a refused launch says nothing about the machine. Nothing running is moved.

**Credentials.** Every Fleet payload carries states (`signed_in`, `no_write`, …), never a credential, token, code or password. An e-mail address and an organisation name are identity, not credentials, and a machine reports its default profile's so that one account on several machines is shown once. Each machine keeps its own sign-ins: its broker login is its peer account, GitHub is its own `gh`, and Claude is its own default profile. A paired machine's Claude sign-in runs Claude Code's own flow on that machine, through the one forward §4.6.11 permits.

**Owner decisions (2026-10-19).** Placement is opt-in (`placement: auto` per wave or `host: auto` per task). Heavy work is held by a `per_machine` cap per lease pool and by heavy-aware placement. The supervisor computes readiness, on its own retained topic, and publishes its own machine record. `require_fresh_base` defaults to `true` on every host. A machine that stays down parks its work and, after five minutes, asks; nothing is re-placed without an answer. A peer's default `max_agents` is 4. A paired machine's Claude sign-in is run from the supervisor's browser through one fenced, transient ssh forward, or typed into the sign-in terminal on the machine itself, never into a Volley field.

**Owner decisions (2026-10-21).** New waves default to automatic placement (`placement.default: auto`) once a machine is paired, superseding opt-in placement above, and a paired machine's `max_agents` is derived from its cores and memory at join (4 only when its size is unknown).

**Overloaded while a peer idles.** While a running wave's placement is `local`, the supervisor's own load per core (the higher of its 1- and 5-minute load averages) is over `placement.load_per_core_max`, and a peer is ready, not draining, not down and has free `max_agents` slots, the supervisor journals `alarm_raised { alarm: "peer_idle_under_load", peer, free, message }` once for that wave, and `alarm_cleared { alarm: "peer_idle_under_load" }` once its own load per core is back at or under the threshold (or the wave's placement is `auto`); it is not raised again for that wave. A wave that ends while it holds keeps it: its final state and its `wave_complete` digest record that it happened. While it holds, the wave state carries it in `alarms` (§4.6.1), `volleyd status` shows it under the wave's header, and the digest lists it (§4.6.16). A wave under `placement: auto` raises none: placement itself uses the peer.

#### 4.6.16 Autopilot

A supervisor MAY answer a decision (§4.6.2) itself, from a policy table it publishes for review (the reference supervisor prints it with `volleyd policy`), within remediation budgets. It is governed by the `autopilot` tunables (§4.6.4), globally and per wave: `enabled` (default `true`), `owner_only` (the decision kinds it never answers; default `plan_change`, `repo_untrusted`, `model_switch`, `release_go`, `stage_go`, `release_pr_ci_failed`) and the per-wave budgets `relaunch_max`, `nudge_max`, `respawn_max`, `rereview_max`, `ci_fixup_max`, `question_max`, `account_move_max`, `merge_transient_retry_max` (integers 0..10, each counting automatic answers under one budget key, such as `relaunch_max:<task>/<role>`; `account_move_max` counts the automatic account moves of one task's role, `agent_account_limit` at the warn level or at the limit alike) and `budget_raise_max` (a multiplier, 1..10: automatic `raise by <n>` answers to `spawn_budget_exhausted` may take the spawn budget to this multiple of the wave's derived budget). A change applies from the next decision on.

**Churn.** The spawn budget counts productive spawns only: a churn spawn (a branch update, a review round or its fixup a branch update caused, a merge train's spawn, or a relaunch, respawn or retry of a role in its step; journaled `agent_spawned { churn: true, cause }`) never spends it, never opens `spawn_budget_exhausted` and is never held by it (the hard ceiling still holds it); the wave state counts both (`spawns`, `tasks[].churn`). Churn is fused instead: a task whose churn is more than `churn_roles_multiple_max` (3) × its pipeline roles puts its cluster on `hold` (`cluster_strategy_changed { churn }`), and churn that goes on while the cluster is held (or after the monitor let that hold go) opens one task-level `churn_exhausted` decision (`hold cluster` | `continue` | `cancel`), never a second while one is open; autopilot answers `hold cluster` once per task (budget key `churn:<task>`), then escalates.

**What it MAY answer.** A decision whose kind and facts match a rule of its table, whose kind is not in `owner_only`, and whose budget (if the rule has one) is not spent. Every automatic answer MUST be one of the decision's own `options` (any answer, for a decision that offers none); a rule whose answer the decision does not offer escalates instead. It MUST NOT answer a decision whose kind is in `owner_only`.

**What it MUST journal.** An automatic answer is journaled as `decision_auto_resolved { decision_id, kind, policy, answer, rationale, evidence, budget? }` immediately before the ordinary `decision_resolved` with `by` set to the supervisor's agent id; the retained decision topic is published resolved and cleared like any other resolution, and the supervisor does not publish its attention envelope for it (the `blocked` envelope on its own `progress` topic that a decision opening rings, which `volley notify` watches). A decision it does not answer (no rule matches, its kind is owner-only, its budget is spent, or the answer could not be applied unattended) stays open and is journaled as `decision_escalated { decision_id, kind, why, budget? }`, `why` being `owner_only` \| `no_policy` \| `budget_exhausted` \| `unattended_safety`; only then does the supervisor publish that attention envelope, and the retained decision's `question` starts with `Autopilot could not resolve this (<why>): `. An escalated decision is never left as a silent wait. With autopilot disabled neither event is journaled and every decision waits for its answer. The wave state's `autopilot` (§4.6.1) counts both and carries each budget used.

**Self-healing CI.** Before a red head (a CI failure on a head the pipeline verifies) is put to anyone, the supervisor classifies it from the failing tests (from the failed runs' logs), the PR's changed files, the release branch's latest CI (the latest run per workflow among its recent runs, with the tests failing there) and, for a GitHub repository, GitHub's status page:

| Classification | When | Remedy |
|---|---|---|
| `infra_incident` | the failure is infra-shaped (a run never started; every failed job failed in a runner, checkout or network step; a run was cancelled and nothing replaced it), or no failing test's file is among the PR's files and the status page reports an Actions or API component that is not operational | a CI hold: the task stays in its stage with `why_waiting: "CI infra incident: <what>; re-checking"` and is re-verified at the CI poll interval; once `autopilot.incident_wait_max_s` (default 14400) has passed since the hold started, a `ci_failed` decision opens with `classification: infra_incident`, which autopilot escalates `budget_exhausted` |
| `own_change` | a failing test's file is among the PR's changed files (this wins over a status-page incident), or a failing test names no file and the release branch's latest CI does not fail that same test (a release branch red on something else does not count), or no failing test can be named at all (neither the PR's run nor the release branch's) | `ci_failed` with `fixup` first: a fixup agent at the red head with the CI result as its directive |
| `flake` | otherwise: no failing test's file is in the PR's changes (whether or not the same test fails on the release branch), or the tests name no file and the release branch's failing tests include them | `remediation_requested { kind: fix_flake, test, test_file, head, run_urls, for }` is journaled (once per head and test), then `ci_failed` offering `fix flake` first; that answer leaves the task parked (`tasks[].remediation`, `why_waiting: "CI flake in <test>: fixer pending"`) for a dedicated fixer |

The `ci_failed` decision carries `classification` and `evidence: { failing_tests, test_files, pr_files, release_ci, status_page }`. An unreadable status page is unknown and never an incident; unreadable PR files never make a flake. A supervised agent's `blocked` status whose reason is about a failing test or CI, while its task's PR head is red, is classified the same way: its `agent_blocked` decision carries the classification and the evidence, `pipeline.on` is `agent_blocked_ci`, and it offers `fixup` (own change: the blocked agent is stopped and a CI fixup starts at the red head) or `fix flake` (a flake) beside `continue`, `respawn` and `cancel`; the policy table answers an own change or a flake as it answers `ci_failed`, and leaves an infra incident to the owner. A supervisor MUST NOT re-run a failed run as a remedy for any classification, and never re-runs one at all: a flake is fixed, an incident waited out.

**Synthetic tasks: a flake's fixer.** A supervisor that fixes flakes adds a *synthetic task* to the wave for each distinct failing test: on `remediation_requested { kind: fix_flake }` (or a `fix flake` answer) it journals `task_queued` for task `fix-<slug>` (the test id lowercased, every run of other characters one `-`, trimmed, at most 40 characters, suffixed `-2`, `-3`, … when taken) with `data: { issue: 0, synthetic: true, title: "Fix flaky test <test>", remediation: { kind: fix_flake, test, test_file, run_urls, for: [<task>] } }`. A synthetic task is never read from a wave file: it exists in the journal only (the wave state shows it with `synthetic: true`, it is absent from `spec`, and a later plan version keeps it). It has no `after`, runs the wave's own pipeline, is scheduled ahead of every other ready task, and is placed and admitted like any task. Its agents have no issue to read: the supervisor writes the root-cause brief (the test, its file, the failing runs, the blocked tasks, and the rules: reproduce it locally alone, in the suite and under load; find the cause; fix it test-first; never re-run, skip, `.only`, wrap in retries or quarantine, but publish `blocked` if that is the only fix) as its `ISSUE.md`. Its implementer branches from the release branch and opens a PR against it; reviews, fixup and the gate run as for any task. A second request for the same test joins the fixer's `for`; at most `autopilot.fix_flake_max` (default 3) fixers per wave, past which the request's red-head decision is escalated `budget_exhausted` (budget key `fix_flake_max`). When the fixer is `done` (its PR merged, however), the supervisor journals `remediation_closed { kind, test, task, outcome: landed, released }`, `released` being the tasks of `for` still parked on that test; it resolves each one's open red-head decision with the answer `fix landed` (by the supervisor), and each enters the branch-update step (§4.6.4 `branch_update`) at its red head, so its PR takes the fix from the release branch; its new head is verified like any other and the pipeline continues. When the fixer is cancelled, `blocked` (its agent's `blocked` status opens an `agent_blocked` decision, with or without autopilot), or one of its decisions is escalated, the supervisor journals `remediation_closed { outcome: failed, why, released: [] }` and puts each blocked task's red head to the owner once: its open decision escalated `unattended_safety`, or an answered one opened again (without `fix flake`, naming the fixer's PR and agents) and escalated. A fixer closed `failed` that reaches `done` after all (the owner unblocked it and its PR merged) is closed again, `landed`, and releases its tasks as above.

**The morning digest.** A supervisor SHOULD publish, retained on `volley/_waves/<wave>/digest`, one digest per wave (`digest.schema.json`) computed from its journal: `shipped` (each merged task with `issue`, `title?`, `pr { number, url }`; a bundle, §4.6.22, once per issue, each with its own `issue` and `title?` and the shared `pr`, `merge_sha` and `merged_by`: `supervisor` for its own merge, §4.6.17, `operator` for one the owner made outside GitHub's merge button, `github` otherwise), `closes` (the shipped tasks' issues, each once, in merge order: the release PR's `Closes #N` lines, §4.6.19), `auto` (`decisions_resolved`, the `decision_auto_resolved` count; `flakes_fixed`, one `{ test, fixer, prs_released }` per `remediation_closed { outcome: landed }`; `conflicts_resolved`, the branch-update steps that verified; `retries`, the `spawn_recovered` and `relaunched` count; `merges`, the PRs it merged; `churn`, the churn spawns by cause, `{ branch_updates, rereviews, retries, trains }`), `waiting` (each open decision that is not held: `{ id, kind, task?, question, since, owner_only }`, `owner_only` when it was escalated `owner_only`), `held` (each held one, §4.6.2: `{ id, kind, task?, question, since, on, label, held_since }`, `label` saying what it waits on, as `T4 (#194)`, `PR #12` or `issue #7`), `release?` (the wave state's `release`, §4.6.19), `failures` (each cancelled task with `why`), `alarms?` (the wave state's `alarms`, §4.6.15), and `wave`, `release_branch`, `generated_at` and `trigger`. It publishes it, and journals `digest_published { trigger }`, on `wave_complete` or `release_done` (`trigger: wave_complete`), `wave_stopped` (`stopped`), a `release_go` decision opening (`release_go`), and a `decision_escalated` (`escalation`; a `release_go`'s own escalation publishes none). A trigger is not published again within `autopilot.digest_min_interval_s` (default 1800, 0..86400) of its last `digest_published`, so the owner is told once about the first thing that genuinely needs them, not once per item; the retained digest is therefore as of its last publish and can lag a later decision (the wave state's `decisions` are current). Each publish also sends exactly one push: a `progress` envelope of type `digest` on the supervisor's own topic, `payload: { msg, wave, trigger }`, `msg` being a one-line summary (`w1 complete: 27 shipped, 3 flakes fixed, 2 conflicts resolved, 1 waiting for you (release_go)`). Archiving the wave (§4.6.20) clears the digest topic.

#### 4.6.17 Autopilot merging

A supervisor MAY merge a gated PR itself, so that an unattended wave does not stall at the gate. A wave file's `merge: auto | manual` chooses; without the key, the supervisor's `autopilot.merge` tunable (§4.6.4, default `auto`) does. Beside it, `ci: auto | none | required` states the repository's CI (§4.6.8). Under `manual` the supervisor never merges and everything in §4.6.8 holds unchanged. Under `auto`:

- The supervisor merges only a task at `merge_ready`, only at the head the task was gated at (the head its evidence package describes), and only into the release branch the PR targets. It squash-merges with GitHub's head guard (`gh pr merge <n> --squash --match-head-commit <head>`, optionally `--delete-branch`), so GitHub refuses the merge when the PR's head moved since the gate. It never forces a merge (no administrator override, no auto-merge, no other strategy but a merge train's merge commit, §4.6.23) and never merges, pushes or rebases anything else. A reference supervisor holds this in its authority fence: the merge command is allowed only with a token the gate mints after writing the evidence package, for exactly that PR and head.
- A merge is journaled `merged_by_supervisor { task, pr, head, merge_sha, by }` (`merge_sha` `null` when the merge commit could not be read back), followed by the same merge record a human's merge gets (`artifact_verified { role: "merged", via: "supervisor" }`) and `stage_entered done`; the task's open decisions are resolved first, as for any merge (§4.6.8).
- A merge GitHub refuses (the head moved, required checks, branch protection) is journaled `alarm_raised { alarm: "merge_refused", pr, head, stderr, reason, attempt }` (`reason` being `transient` \| `behind` \| `head_moved` \| `retargeted` \| `closed` \| `draft` \| `checks` \| `unknown`; a `draft` refusal marks the PR ready, waits for the CI that starts and merges again, never counting toward `autopilot.merge_retry_max`, §4.6.8), and the PR is read again at once, as at any gate: someone else may have merged it, or its head moved (a moved head invalidates the gate, §4.6.8). The merge is retried no more often than the CI re-check interval. A `transient` refusal (the host busy or unreachable: a merge already in progress, the base branch modified during the merge, a 5xx answer, a rate limit, a transport error) MUST NOT count toward `autopilot.merge_retry_max`: the task keeps its merge turn, the alarm carries `retry_at`, and the merge is retried no earlier than that, attempt n waiting entry n of `autopilot.merge_transient_backoff_s`; the PR is read again before each retry as above. One transient refusal more than the ladder has entries at one gated head opens `merge_refused` with `reason: transient`, `transient_attempts` and `since`; a `retry` answer starts the ladder again. After `autopilot.merge_retry_max` (default 2) refusals at one gated head the task leaves the gate (`blocked`) and decision `merge_refused` (§4.6.2) asks `retry` (one more attempt), `manual` (a human merges this task; the supervisor waits at the gate as under `manual`) or `cancel`. A new gated head starts the count again.
- The evidence package says who merges: under `auto`, that the supervisor merges the PR itself at exactly that head and journals it as `merged_by_supervisor`.

**The merge queue.** A supervisor decides *when* each gated task is merged through a merge queue:

- A task enters the queue when it is gated under `auto` (journaled `merge_queued { task, position }`, `position` 1-based) and leaves it when it merged (by the supervisor or anyone else), was cancelled, or went to a human (`merge_dequeued { task, why }`, `why` being `merged` \| `cancelled` \| `manual`). The wave state shows it as `merge_queue` (§4.6.1).
- The queue is ordered by dependency, then readiness: a task more tasks name in their `after` goes first, and a task never goes ahead of a queued task it comes after; then the task queued earliest. A task whose last merge GitHub refused as `behind` (out of date with, or conflicting with, the release branch), `head_moved`, `retargeted`, `closed` or `draft` goes after the tasks still waiting; a task refused for any other reason keeps its place. A refusal alone never brings a task up to date: only a check that the release branch has commits the head lacks does.
- There MUST be at most one merge in flight per release branch, across every wave the supervisor runs on that repository and branch. The task at the front holds the branch until it merged, its merge was refused as `behind`, `head_moved`, `retargeted`, `closed` or `draft`, it waits for an answer, or the supervisor's checks at its turn keep failing (then it is passed over, with the tasks that come after it, while another queued task can take the turn); its merge is journaled `merge_started { task, pr, head }` before it runs, and a merge that ends without an outcome (it timed out, could not run, or a supervisor restart interrupted it) is journaled `merge_ended { task, why }` (`why` being `timed_out` \| `failed` \| `interrupted`), after which the task can take the turn again. Across waves sharing a branch, the lock goes to whichever wave's front task asks for it first.
- A task is gated at its reviewed head; it is updated only at its turn. A supervisor SHOULD NOT bring a task that is merely behind the release branch up to date before its gate (an update then is stale again by its turn and voids reviews for nothing); it gates it at the head its reviewers saw and records in the evidence how far behind that head is. Only a PR the host reports as conflicting (it gets no CI until it is updated) or one taking a landed flake fix (§4.6.16) is updated before its gate. Before the front task is merged, the supervisor checks it against the release branch. If the branch moved since its gate (a merge before it landed), the task MUST be updated first: a rebase or merge agent brings it up to date per `branch_update` (§4.6.4; `merge` never force-pushes, so it is the mode to choose for an unattended wave), CI runs on the new head, the gate checks it again (§4.6.8), and only then is it merged. A queued task is updated only after the merge before it landed, and only at its turn: never every queued PR at once, so N merges cost at most N−1 updates, one at a time; the tasks behind it keep their gates and evidence meanwhile.
- A rebase or merge agent that cannot bring the branch up to date (it publishes `blocked`, or fails) opens decision `merge_conflict` (§4.6.2) with the options `respawn` (a fresh agent), `manual` (the task leaves the queue and waits at the gate for a human) and `cancel`.
- `merge: manual` on a wave keeps its tasks out of the queue. The owner MAY merge one gated task at once through the same verb, under `manual` too and on a paused or stopped wave (the reference supervisor's `volleyd merge <wave> <task>`, the `merge` control op, owner only); it is refused while another task holds the release branch.

#### 4.6.18 Needs-you inbox

A supervisor MAY keep one record per thing waiting for a person on `volley/_inbox/<id>`, retained, QoS 1, published by the supervisor only (`inbox-item.schema.json`, envelope `channel: "_inbox"`, `type: "inbox_item"` while open and `"inbox_answered"` once answered). It is how every client (a dashboard on a laptop or a phone, a terminal, a CLI) sees the same list, and how two of them never answer the same thing twice.

| Field | Type | Meaning |
|---|---|---|
| `id` | string | By kind: `d-<wave>-<decision_id>`, `p-<agent_id>-<tool_use_id>`, `h-<agent_id>-<seq>`, `r-<wave>-<stage\|go>`, `n-<notice>`. Ids are `[dphrn]-[A-Za-z0-9_-]{1,200}` (a tool use id is mixed-case), not the §2.1 grammar. |
| `kind` | enum | `decision` (mirrors a §4.6.2 decision) \| `picker` (a question a harness put to its user) \| `handoff` (a turn that ended on a question) \| `release` (a release stage, or its go/no-go) \| `notice` (an owner-only notice from the supervisor, below). |
| `version` | integer ≥ 1 | Bumped by every accepted change; an answer names the version it answers. |
| `owner_only` | boolean | Only the owner answers it: autopilot (§4.6.16) never does, and a client SHOULD notify the owner. For a decision, whether its kind is in `autopilot.owner_only`. |
| `wave`, `task` | ids | Optional: what it is about. |
| `agent_id` | agent id | The agent it is about (the supervisor's own id for a wave-level decision). |
| `title`, `question` | string | A short title, and what needs answering. |
| `options` | `[{ label, description? }]` | Suggested answers (optional). `allow_other` (a free-text answer is accepted too) and `multi` (several options may be chosen) are optional booleans. |
| `pointers` | object | Where the evidence lives (`diff`, `transcript`, `screen`, `pr`, …). |
| `opened_at` | date-time | |
| `source` | object | What it mirrors (for a decision, `{ decision_id, decision_kind }`). |
| `answered` | object | `{ answer, by, where, at }`; present exactly when `type` is `inbox_answered`. `where` is `{ kind: desk \| terminal \| cli \| autopilot, device?, machine? }`. |
| `held` | object | Optional, a decision's item only: its decision's hold (§4.6.2), `{ on, note?, by, at }`, mirrored when it is set and removed when it is released. A hold is not an answer: it changes no `version`, and the item still takes one. |

**Notices.** A `notice` item is the supervisor's own (`agent_id` its id, `owner_only: true`), tells the owner something rather than asking, and never blocks a wave. Its link, when it has one, is `pointers.link`, its `options` are `open` and `dismiss`, and those are the only answers the supervisor accepts (`open` acknowledges it: the owner opened the link). Its id is fixed per notice (`n-coordinator-link`, `n-coordinator-failed`, §4.6.25; `n-machine-down-<name>`, §4.6.15): a notice opened again after its last one was answered reuses the id at the next `version`. A client SHOULD show it with an Open button for the link and a Dismiss; the owner's notification for it SHOULD open the link.

**The supervisor is the referee.** An answer is `op: "inbox_answer"` with `{ id, version, answer, where }`, sent either as a control request on the supervisor's mailbox, where `by` is subject to the wave-ownership rule (§4.6.1: the wave's owner or the session bound to its coordinator name answers a wave's item), or by a Desk login (a `steer` or `admin` account, or the fixed `desk` identity) on its own account-op topic `volley/_system/auth/ops/<username>` (§4.6.10), where the broker names the sender: the supervisor MUST check that the sender is a Desk login, and MUST then treat the answer as the owner's, with `by` the sender's username and no ownership check (a `resolve` sent there is treated the same way). The supervisor MUST accept it only when `version` equals the item's current version (compare-and-set) and the item has no `answered`. The first accepted answer bumps `version`, sets `answered`, is journaled as `inbox_answered { id, kind, answer, by, where, version }` (in the item's wave, else `_system`, §4.6.3) and is acted on; the record is re-published with `type: "inbox_answered"`. A later answer MUST be refused with `already answered on <where>`, `<where>` written `desk·<device>`, `<machine>·terminal`, `cli` or `autopilot`, and a stale version of an open item is refused too. Only the supervisor answers with `where.kind: "autopilot"`. Every way an item is answered closes it through the same referee, so every answer is journaled: a decision resolved by any path (its own resolve request, autopilot, a client's `inbox_answer`) answers its item, and an `inbox_answer` on a decision item resolves the decision. The `inbox` op lists the open items.

**Pickers and handoffs.** A supervisor that opens these items opens a `picker` item `p-<agent_id>-<tool_use_id>` for a `picker_opened` (§4.3) from any session, and a `handoff` item `h-<agent_id>-<seq>` for an `awaiting_input` carrying a `question` (`seq` is that event's) that the Stop hook published (`hook_event: "Stop"`), from a session it does not supervise (a coordinator turn that ended on a question; a Notification's `awaiting_input` repeats it or asks for a permission, and opens nothing); `source` records the `workspace` the item can be answered on, when known. A `picker_answered`, a session's next prompt (its `activity` `prompt received`, or that prompt's `resumed`), the end of the turn (the Stop hook's `idle`; a Notification's `idle` closes nothing) for a picker still open, and the session's terminal status (`done`, `failed`, `reaped`) close the session's open items with `where: { kind: "terminal", machine }`, unless the inbox answered them first. A coordinator session's own items are `owner_only`: the supervisor MUST refuse an `inbox_answer` to one whose `by` is neither the session's agent id nor the coordinator name (§6.2) bound to it, unless it came from a Desk login on its own account-op topic. An `inbox_answer` to such an item is carried out in the session before it is accepted: the supervisor reads the session's screen and MUST refuse the answer, leaving the item open, unless the screen shows that same picker (its question's first line and every option label, in order; `picker not on screen`) or, for a handoff, an idle empty prompt (`prompt not idle`) with the item's question above it (`the question is not on screen`); a handoff reply that is not one line of plain text (a second line, a slash command or shell line) is refused before the screen is read; only then does it select the answer by keystroke or type the reply and submit it. A picker with more than one question, and a session whose screen the supervisor cannot read, are answered in its terminal.

**Lifetime.** An answered record stays retained, with `answered`, for `autopilot.inbox_answered_ttl_s` (§4.6.4; default 600 s) so a client that was offline sees what happened, and is then cleared (a zero-length retained payload). The journal is the record: a restarted supervisor rebuilds the inbox from its `inbox_opened` and `inbox_answered` events and re-publishes it.

**Who may read and write.** Every account reads `volley/_inbox/+`; only the supervisor writes it (in the reference roles: `volleyd` and `supervisor`). A client MUST NOT trust an item whose envelope `agent_id` is not the supervisor's.

#### 4.6.19 Release train

A repository MAY ship a **release playbook** at `<repo>/.volley/release.yaml` (`release-playbook.schema.json`): what turns its merged release branch into a release, as named stages a supervisor runs in order. A wave file's `playbook: <path>` (relative to `repo`, or absolute) points elsewhere; `playbook: none` opts the wave out. The playbook is `{ version: 1, stages[] }`, 1..32 stages with unique names, each `{ name, brief, run?, phase?, gate?, verify?, timeout_s?, heavy? }`: `brief` is what the stage's agent does; `run` lists the commands it runs, each an argv array (never a shell line), shown in its brief verbatim; `phase` is `prepare` (the default: before the owner's `release_go`) or `ship` (after its `go`); `gate` is `auto` (the default) or `owner`; `verify` lists facts the supervisor checks once the stage reports done (`commits_on_release: true`, `release_pr: true`, a `tag` glob at the release branch's head, `files` that must exist on the release branch, `result` fields the stage's result must carry); `heavy` names a lease pool (§4.6.5) the stage holds while it runs. The schema is generic hooks: it names no tool, host or environment.

- **Variables.** A stage's `brief`, each element of its `run` argv arrays, `verify.tag` and `verify.result` values MAY name `{{version}}` (the release's version, below), `{{date}}` (the supervisor's UTC day at `release_started`, `YYYY-MM-DD`), `{{wave}}`, `{{release_branch}}`, `{{default_branch}}` (the repository's, read once at `release_started`) and, in a ship stage only, `{{merged_sha}}` (the release PR's merge commit). The supervisor substitutes them when it renders the stage's brief and when it verifies the stage; argv arrays stay shell-free. Any other `{{name}}`, or `{{merged_sha}}` outside a ship stage, is invalid (`stages[0].run[1][4]: unknown variable {{ver}}`).
- **Phases.** Prepare stages come first. A ship stage pushes nothing but a tag: `commits_on_release` and `release_pr` are prepare stages' facts, and a playbook with a ship stage MUST have a prepare stage that verifies `release_pr`; each is invalid otherwise.
- **The version.** At `release_started` the supervisor resolves the release's version, read-only: the newest `vX.Y.Z` tag (a prerelease is never the base), bumped **minor** when the release branch carries any `changes/*.added.md` or `changes/*.removed.md` fragment and **patch** otherwise; `0.1.0` with no tag. The wave file's `release_version: X.Y.Z` overrides it, refused unless it is greater than the newest tag. When the playbook names a variable, verifies `release_pr` or has a ship stage and the version or the default branch cannot be read yet, the supervisor does not start the train and reads again later.

- **Validation.** A supervisor validates the playbook when the wave is submitted: an invalid one, or a configured path that does not exist, refuses the wave with `RELEASE_PLAYBOOK_INVALID` and path-qualified errors (`stages[1].name: duplicate stage 'smoke'`). No file at the default path means no train, and so does a repo that is not on the supervisor's machine (its playbook cannot be read, at submit or at settle). A reference supervisor's `run` prints `release playbook: <path> (N stages, M owner-gated)` or `release playbook: none`, and its `validate` `release playbook: <path> (N stages: P prepare, S ship, M owner-gated)`.
- **Start.** When every task of a running wave is done or cancelled and the wave has a playbook, a supervisor whose autopilot (§4.6.16) is on for the wave journals `release_started { done, cancelled, version?, date?, default_branch?, playbook: { path, sha256, stages } }` (the stages as read, so the train runs exactly what was journaled) in place of `wave_complete`; the wave's `status` becomes `releasing` and its state carries `release` (§4.6.1). No `wave_complete` decision is opened for it. A releasing wave admits no tasks and accepts no new version; it MAY be paused (it resumes `releasing`) or stopped. Without a playbook, or with autopilot off, the wave completes as before.
- **Stages.** Stages run serially, in playbook order. Each stage is entered (`release_stage_entered`), then verified (`release_stage_verified`, only once every `verify` fact holds), failed (`release_stage_failed`) or skipped (`release_stage_skipped`). Before a `gate: owner` stage the supervisor opens `stage_go` and runs the stage only on `go`; that stage is `awaiting_go` meanwhile; `skip` skips it and `hold` asks again, as a new decision. Stages run with the same evidence and authority-fence rules as pipeline stages (§4.6.8): the supervisor runs no stage command itself. It spawns one supervised agent per stage (role `release`, under the pseudo task `_release`, a reference supervisor naming it `<wave>-release-<stage>-<n>` on the branch `<wave>/release-<stage>-<n>`) in a worktree cut from the release branch's freshly fetched tip (a ship stage's: detached at the release's merge commit, the default branch freshly fetched); the agent's brief carries the stage's `brief`, its `run` lines verbatim (variables substituted) as the commands to run in order (stopping at the first that fails), the `verify` facts it must leave true and, for a `heavy` stage, the lease (§4.6.5) to take first. Any push a prepare stage makes goes to the release branch as a fast-forward; a ship stage pushes nothing but a tag. Before its `done` the agent publishes the `stage` result (§4.6.8). A stage's agent that a supervisor restart finds still running is reconciled and watched again like a task's (§4.6.8), so a ship stage may restart the supervisor itself.
- **Verification.** After a stage's `done` the supervisor checks, read-only: every `run` line reported, in order, with exit code 0; `commits_on_release` (the release branch's tip on origin moved past the commit the stage started from, which is an ancestor of it, and the agent's HEAD is on it; a start the supervisor did not record does not hold); `release_pr` (exactly one open pull request from the release branch into the default branch, labelled `no-changelog`, its title starting `release:`; journaled as `release_pr_detected { pr, head, title }`); `tag` (a tag matching the glob, read from the forge's refs API, points at that tip; a ship stage's at the merge commit); `files` (each exists on origin's release branch; a ship stage's at the merge commit); `result` (each field of the stage result has exactly that value). All hold: it writes the stage's evidence (the commands and exit codes, the artifacts, each fact with what showed it) and journals `release_stage_verified` with where it is. A result missing or a fact not holding gets the agent one steer; after that, or on a `failed` or `blocked` status, the stage is `failed` and the owner is asked (`agent_blocked`: `respawn` runs the stage again with a fresh agent, `skip` skips it, `cancel` journals `release_cancelled` and the wave becomes `complete` without its release).
- **The go.** Once every prepare stage is `verified` (or `skipped`) and, when a prepare stage verified the release PR, that PR's head is CI-green (read as a task PR's head is, §4.6.8, honouring the repository's CI mode; a moved head is journaled `release_pr_detected` again and read again), the supervisor opens `release_go` (§4.6.2), whose `stages` point at every stage's evidence and whose question names the version, the PR and the changelog section's first bullets. A red head opens `release_pr_ci_failed` instead (`retry` reads CI again; `hold` asks again), never answered automatically. `release_go`, `stage_go` and `release_pr_ci_failed` are owner-only: a supervisor MUST NOT answer any of them itself, whatever its policy table says (`autopilot.owner_only` names all three by default). On `go`, with a release PR, the supervisor squash-merges it at exactly the CI-green head `release_go` named (a head that moved since, or whose CI reads red, does not merge: `release_merge_failed`, and it is asked again), deleting the release branch (`gh pr merge <n> --squash --match-head-commit <sha> --delete-branch`: never `--admin`, `--merge` or `--rebase`), journals `release_merged { pr, sha }` and checks the issues (below) at once; then runs the ship stages in order, and journals `release_done { by, decision_id, version?, merged_sha? }` once the last one is verified or skipped (at once, with no ship stage). A merge that does not happen journals `release_merge_failed { pr, head, reason }` and asks `release_go` again with the reason. Without a release PR, `go` journals `release_done` at once. The wave becomes `complete` with `release_done`; `hold` (or any other answer) leaves it `releasing` and asks `release_go` again, as a new decision.
- **Issues.** A forge closes an issue from a PR's `Closes #N` only when that PR merges into the default branch, so a task's PR into the release branch closes nothing. A supervisor SHOULD own the lifecycle of its waves' issues instead of leaving it to a coordinator: when a task's merge into the release branch is verified it labels the task's issue `merged-to-release` (creating the label when the repository lacks it) and comments once (`Merged into \`release/<wave>\` in PR #N; closes when the release reaches main.`), journaling `issue_labeled` and `issue_commented`. `release_started` carries `closes` (as the digest's), and each stage's brief gives the release PR's body as one `Closes #N` line per done task's issue. Once the release branch's PR has merged (the supervisor's own merge on the go checks at once; a reference supervisor otherwise looks for it while the wave is `complete`, and `volleyd issues <wave> --verify [--pr <n>]` checks a release merged by hand) it reads every task's issue: a done task's issue still open is closed with the comment `closed by the release PR #N (wave <id>)` (`issue_closed`), the label comes off every issue that has it (`issue_unlabeled`), and a cancelled task's issue (or a deferred one: not done when the release reached main) stays open with one comment `cancelled in wave <id>: <reason>` (or `deferred in wave <id>: <reason>`); then it journals `issues_verified { release_pr, closed, left_open }`. Every comment carries a marker (`<!-- volleyd:<kind> wave=<id>[ pr=<n>] -->`) and the issue is read before each write, so neither a restart nor a journal that lost an event repeats one. A supervisor's authority over issues is exactly these writes: it never edits an issue's title or body, and adds or removes no other label.
- **Production is the owner's.** A supervisor MUST NOT deploy to production as part of a train's automatic run. Nothing after `release_go` runs without the owner's `go`; the `go` is the owner's authority for exactly the ship stages the journaled playbook declares. A ship stage whose deploy is production asks first with `gate: owner` (a `stage_go` after the go).

#### 4.6.20 Archived waves

An ended wave stays in a supervisor's live set, with its open decisions, until it is **archived**. Archiving is a supervisor operation; the wave's journal and evidence stay on disk.

**What archiving does.** Only a `stopped` or `complete` wave can be archived; a supervisor refuses a `running`, `paused` or `awaiting_decision` one. Archiving journals one `decision_resolved` per open decision with `answer: "archived"` (and `by`, `at`), then `wave_archived { by, reason, closed_decisions[] }`; before them, each closed decision's needs-you inbox item (§4.6.18) is answered `archived` (`inbox_answered`). It publishes each closed decision once as `decision_resolved` and clears its topic (§4.6.2), publishes the wave state once with `status: "archived"` and `open_decisions: []`, then clears `volley/_waves/<wave>/state`, `volley/_waves/<wave>/digest` (§4.6.16) and the retained record of every inbox item of the wave. The wave leaves the supervisor's live set: it is not ticked, not listed by default and not re-published after a restart. A supervisor refuses to run a new wave under an archived wave's id, since its journal already holds that wave. There is no unarchive.

**Who may archive.** Through the supervisor's control channel (§4.4 mailbox, `op: "archive"`, `wave`, optional `dry_run`), archiving is a mutating op like `stop`: the wave's owner, or anyone when the wave has no owner. An admin account may archive any ended wave by sending the same op on its account-op topic, `volley/_system/auth/ops/<username>` (§4.6.10). The supervisor archives on its own (with `by` its agent id) when an auto-archive tunable says so. `dry_run: true` answers `{ wave, status, would_close[] }` and changes nothing.

**Auto-archive.** `archive_ended_after_h` (§4.6.4) archives a wave that many hours after its last `wave_stopped` or `wave_complete` (`reason`: `ended <N> h ago (archive_ended_after_h)`); 0 disables it. With `archive_on_ack`, a `complete` wave is archived as soon as its `wave_complete` decision is answered by someone other than the supervisor (`reason`: `wave_complete acknowledged (archive_on_ack)`); the supervisor's own answer, such as autopilot's (§4.6.16), leaves the wave to `archive_ended_after_h`, so its owner still sees the outcome. A wave whose agents have not all ended waits until they have.

**The index.** `volley/_waves/_archive` (QoS 1, retained, `archive.schema.json`) lists archived waves, newest first and capped by the supervisor: `{ archived: [{ wave, status, archived_at, by, reason }], updated_at }`, where `status` is how the wave had ended. A client shows how many waves were archived from it without reading journals; a supervisor republishes it at start.

#### 4.6.21 Repositories

A supervisor treats its machines as a pool for every repository it works on: config says which machines hold a clone of which repository (`repos`, `fleet.repo_root`, `fleet.repos`, `hosts.<name>.repos`, §4.6.4), each machine's record reports its clones (`repos[]`, §4.6.14) and its readiness judges each repository on its own (`repos`, §4.6.15). The ops below change that config and bring each machine's clone and folder trust in line with it.

**The model.** A repository is named by its canonical GitHub `owner/name` (compared case-insensitively; never a URL, host, `.git` suffix or whitespace). Its clone on a machine is the adopted one in `hosts.<name>.repos.<owner/name>` (an absolute path there; `fleet.repos.<owner/name>` on the supervisor's own machine), else the managed one at `<fleet.repo_root>/<owner>/<name>` (`~` being that machine's home). A repository assigned to a machine (`repos.<owner/name>.machines` naming it, or `all`, or an adopted path) is judged in that machine's verdict whether a wave uses it or not, beside every running wave's repository. Its `state` is `ready`, `absent` (no clone at its path), `blocked` (a block check about it, a tool it needs, or the last `repo_add` run there failed, with that run's why) or `cloning` (a `repo_add` run is making its clone there). On the supervisor's own machine, a running wave's repository that config names but assigns only to other machines is `blocked` (`<owner/name> is not assigned to <machine>: add it (Settings → Repositories, or volley repo add <owner/name> --machine <machine>)`), and placement keeps the repository's waves on the machines it is assigned to. A submit of a wave whose `repo:` is a path on a clone of a repository config names (by its `github.slug`, else its clone's `origin`) adopts that clone for the supervisor's machine when config gives it none there: the clone's root (`git rev-parse --show-toplevel`) goes to `fleet.repos.<owner/name>` and the machine to `repos.<owner/name>.machines` (one `config_changed`), journaled `repo_added { by: "wave <id>", slug, machines: [<machine>], paths }`, and its local run follows; the `run` answer carries `notes: ["adopted <root> as <machine>'s clone of <owner/name>"]`. That adoption needs no admin (unlike `repo_add`'s `paths`): the folder is the wave's own `repo:`, the one its agents work in, and only a clone of a repository already in the registry is adopted. A repository config does not name is never adopted (no registration), and a clone config already gives the supervisor elsewhere is left as it is (one clone per machine per repository). Such a wave names the repository by `owner/name`; the supervisor holds no clone of it, its tasks are placed on the machines that hold one, and a task of it pinned to the supervisor's machine is refused at submit. The `gh: no write permission on <owner/name>` reason names the first repository the record reports.

**Ops.** Admin ops on the account-op topic (§4.6.10), answered like `peer_doctor` (§4.6.14); `repo_list`, `repo_status` and `repo_check` without `fix` are reads also answered on the supervisor's mailbox (§4.4), and `repo_add` / `repo_remove` / `repo_probe` and `repo_check { fix: true }` there are refused. The fixed `coordinator` identity MAY send `repo_add`, `repo_remove`, `repo_list`, `repo_status` and `repo_probe` on its own account-op topic, `volley/_system/auth/ops/coordinator`, without an admin account: adding the repository a wave is about is the wave owner's job. The supervisor MUST refuse from it a `repo_add` with `paths` (adopting a clone at a path also trusts that folder on the machine: an admin's), MUST NOT adopt for its `repo_add` the clone a wave runs from (it clones fresh), and MUST refuse every other op on that topic (`repo_check`, pairing, `machine_add`, `peer_doctor`, `peer_retarget`, `archive`, the account, setup, role and coordinator ops), which keep the admin check.

- `repo_add { slug, machines?, paths?, wave?, git_email? }`: `machines` is `all` (the default) or a list of machine names (configured hosts, or the supervisor's own name); `paths` maps a machine (a paired one, or the supervisor's own: `fleet.repos`) to the absolute path of an existing clone it adopts; with the supervisor's machine among `machines`, no path for it and no clone of it there by config, the clone a wave on a path of that repository runs from is adopted (never for a `repo_add` from the fixed `coordinator` identity, below), its status line `<machine>: ready (<root>, adopted from wave <id>)`. The supervisor first runs `gh repo view <slug> --json nameWithOwner,url,visibility` on its own machine: a repository GitHub does not know is refused with gh's reason, and the canonical `nameWithOwner` is the name kept. It then adds the machines to `repos.<slug>.machines` (`all` absorbs any list) and each adopted path to `hosts.<name>.repos.<slug>` (`fleet.repos.<slug>` for the supervisor's own machine), as one `config_changed`; a second `repo_add` that changes nothing changes no config. The answer comes once config is patched: `result: { slug, url, visibility, machines, status, checks, ci? }`, `status` being each machine's state line (below), `checks` the repository half of `repo_check` (below; `repo.exists` and `ci.mode`, no release branch yet) and `ci: { workflows }` its active workflows when read (kept for older clients). Each machine's run then goes on in the background (`repo_status` follows it). `wave` (`volley repo add <owner/name> --for-wave <wave>`) names the one wave the registration is made for, and MUST be a wave id that is not an archived wave's (else refused at `wave`; the wave may be submitted after the add, as setup's first wave does); it is journaled in `repo_added`, and that wave's cleanup removes the registration (§4.6.26). Without it the registration is the owner's and no cleanup ever removes it. `git_email` (`volley repo add <owner/name> --git-email <email>`, on a repository already added too) sets `repos.<slug>.git_email` (§4.6.4) in the same `config_changed`, and `null` (`--git-email none`) clears it; a value that is not an email is refused at `git_email` before anything changes. `repo_list` and `repo_status` carry it per repository.
- `repo_remove { slug, machines? }`: drops the machines from `repos.<slug>.machines` (`all`: every machine; the repository leaves config when none is left, and `all` minus a machine becomes the list of the others) and their adopted paths, then tells each paired machine whose tunnel is up (`--repo-remove`, below). A clone is never deleted by `repo_remove` (the one clone a supervisor deletes is a managed clone its own clone run made for a wave-owned registration, by that wave's cleanup, §4.6.26): `result: { slug, machines, clones, peers }` names each clone's path (`clones`, by machine) and what each paired machine answered (`removed`, or why it was not told). A repository config does not name is refused (`<slug> is not a configured repository`).
- `repo_list {}`: `result: { repos: [{ slug, machines, paths? }] }`, every repository config names (adopted-only ones with `machines: []`).
- `repo_probe { machine, path }`: reads what is at `path` on the machine `machine` before an add, so a client can say whether an adopted clone is the repository being added. `machine` is a configured host or the supervisor's own machine (an unknown one: `no configured host named "<machine>"`) and `path` passes `repo_add`'s `paths` check (else `path must be an absolute path`). Over the machine's ssh (§4.6.14), or through its own exec on the supervisor's machine, the supervisor runs `git -C <path> rev-parse --show-toplevel`, then, when that names a root, `git -C <root> remote get-url origin`, each as its own script so a failing first step is an answer. The answer is `result: { machine, path, state, root?, origin?, slug? }`: `state` is `found` (`root` the clone's top level, `origin` the URL as git prints it, `slug` the GitHub `owner/name` it names, lower-cased, for a GitHub origin), `missing` (no folder there), `not_git` (a folder that is no git clone) or `no_origin` (a clone, `root`, without an `origin` remote). When ssh fails, or git answers anything else, the answer is `ok: false` with the reason. Whether `slug` is the repository being added is the client's to judge. Nothing is journaled and no configuration changes.
- `repo_status { slug? }`: `result: { repos: [{ slug, machines, lines }] }`, each repository (or `slug`) on every machine it is assigned to: `machines` maps a machine to its verdict entry `{ state, path?, reasons }` as readiness judges it now, and `lines` holds one line per machine, `<machine>: <state> (<reasons joined by "; ", else the path>)` — the text clients show.
- `repo_check { slug, release_branch?, machines?, fix? }`: whether the repository can run a wave, on every machine that could run it. Two halves. The repository half is read once on the supervisor with read-only `gh` (`gh repo view <slug> --json nameWithOwner,url,visibility`; `gh api` GETs of `repos/<slug>/actions/workflows`, and for `release_branch` of `repos/<slug>/branches/<b>`, `repos/<slug>/rules/branches/<b>` and, for a protected branch, `repos/<slug>/branches/<b>/protection`), as the lines `repo.exists`, `branch.release` (the branch is on origin; a 404 blocks), `branch.protection` (its required checks; a `warn` when a ruleset's `pull_request` rule or the classic protection requires approving reviews, which GitHub never lets volleyd's own `merge: auto` satisfy; `reviews: unknown (classic protection is admin-only)` when that cannot be read) and `ci.mode` (§4.6.8's words). The machine half is each machine's doctor run fresh for the answer (a paired machine's over §4.6.14's `peer_doctor` ssh step, the supervisor's own as its own doctor runs; concurrently), its checks filtered to those about the repository (`repo.identity` among them) and the machine-level `gh.auth`, `git.identity`, `claude.signin`, `claude.trust` and any failing `block` check, and judged as readiness judges it (§4.6.15). A machine whose doctor run is in progress, or that is down, is judged from its last record and says so. The machines are the repository's holders by config (`machines` narrows them; each a machine name). `fix: true` (an admin's) runs each paired machine's doctor with `--fix --yes` and the repository added (`--repo-add`, so a missing clone is cloned): the doctor's own safe fixes (a clone, a canonical repoint, a fetch, the worktree root), nothing else; the supervisor's own machine is never fixed (its clone is the owner's checkout). The answer is `result: { slug, visibility?, repository, machines, ready_on, summary }`: `repository` the repository half's lines and each `machines.<name>` `{ checks, ready, state, reasons, from, doctor_at, note? }`, every line `{ id, ok, severity, detail, repo?, fix? }`; `ready` is the machine's readiness and the repository's `ready` there; `from` is `doctor` or `record`; `ready_on` lists the ready machines and `summary` is the closing line, `ready for a wave on: <machines>.` or `not ready for a wave on <machine> (<failing ids or first reason>)[; ready on <machines>].`.

**A machine's run.** On a paired machine the supervisor runs the box's doctor (§4.6.14 `peer_doctor`'s ssh step) with `--repo-add <owner/name>` (or `<owner/name>=<path>` for an adopted clone), and with `--fix --yes --clone` while the machine's record reports no clone of it (its state is `cloning` meanwhile): the doctor adds the repository to the machine's own `peer.json` and clones it from `https://github.com/<owner>/<name>.git`. Its report is folded into the machine's record (§4.6.14). One doctor run per machine at a time: Repair's `peer_doctor` is refused while another doctor run is in progress there (`a doctor run on "<name>" is already in progress`); a repository's run that meets one is `blocked` (`a doctor run on "<name>" is in progress: retried after it`) and starts again when that run ends. On the supervisor's own machine nothing is cloned: the clone must exist (`git rev-parse --show-toplevel` in it), else the state is `blocked` with `gh repo clone <slug> <path>` to run by hand; the supervisor's own doctor checks each repository assigned to its machine on its next run. A machine whose record is missing or down, whose ssh fails, or whose doctor reports no clone afterwards stays `blocked` with the reason, and the run is tried again when the machine's record next comes `up`, when a heartbeat carries a newer doctor run (`doctor_at`) than the one the supervisor holds, and after a successful Repair there; a restart keeps the reason (from the journal) until then. A machine whose record already reports the clone and whose trust is recorded is not run again. A run whose repository was removed from the machine (`repo_remove`) before it ended records nothing.

**Folder trust.** Adding a repository to a machine is the owner's consent to trust its clone there (§4.6.2's `repo_untrusted` stays the fallback for anything not added this way): once the clone exists, the supervisor records `projects[<clone root>].hasTrustDialogAccepted` in that machine's default profile and in every signed-in Claude profile on it (§4.6.12), with the same write as an owner's `trust` answer, and journals `repo_trusted { machine, repo, root, accounts, keys }`, `keys` being each (machine, profile, root) as a `repo_untrusted` decision is keyed. A spawn whose (machine, profile, root) a `repo_trusted` covers opens no `repo_untrusted`, whatever the profile's file says by then. A profile signed in later (`claude_signin_done`) is trusted for every repository assigned to its machine, one `repo_trusted` each. The one exception: `volley setup --simulated`, run without `volley repo add`, records the same trust for the scratch clone it made itself for the simulated first wave, in the default profile only and with no `repo_trusted` journaled (no repository was added); setup never trusts a clone on a real run.

**Admission.** A submit (`run`, every version) checks the wave's repository before it admits anything, from the same `gh api` reads its CI mode is decided from (§4.6.8) and the machines' retained verdicts (§4.6.15), the ones placement will use; it never runs a doctor. A wave's candidates are its placement's: a `local` task's the supervisor's own machine, a task's `host: <name>` that machine, an `auto` task's every holder of the repository. It is refused with one `errors[]` entry per fault at the path `repo` when the release branch is not on origin and no task spawns locally (a local wave keeps `RELEASE_BRANCH_MISSING`), when no candidate is ready for the repository and none is `cloning` (each candidate's line, then `fix: volley repo check <owner/name> --fix, or volley repo add <owner/name> --machine <name>`), when a task is pinned to a machine that is not ready for it (that machine's line), or when `merge` is `auto` and the release branch requires approving reviews (`set merge: manual, or drop the rule for <branch>`). The supervisor's own machine takes its `local` tasks whatever its verdict says of the clone, unless git cannot commit in that clone (its `repo.identity` for the repository fails, or no identity stands anywhere, readiness' `git:` blocker: `<machine>: no commit identity in <clone> (git -C <clone> config user.name … && … user.email …, or volley setup --peer --step signin)`); a paired machine is judged by its repository verdict, which a failing `repo.identity` makes `blocked`; a candidate not heard from since the supervisor started, or not yet PATH-probed, refuses nothing. What the check finds without refusing (another candidate not ready, a `!` repository line) is in the answer's `repo_check: { lines }`, which `volleyd run` prints under its placement line; facts GitHub would not give refuse nothing and raise the alarm `repo_check_unknown`.

**`remote_repo_missing`.** Its `add` answer (§4.6.2) runs `repo_add` for the decision's repository on that one machine (no `gh` check: the slug is the wave's), then retries the task as `retry` does.

**Journal.** In `_system`: `repo_added { by, slug, machines, paths?, wave? }` (`by: "wave <id>"` for a submit's adoption), `repo_removed { by, slug, machines, clones }`, `repo_clone_run { machine, slug, ok, cloned, path?, error? }` (one per machine run; `cloned`: the run made the clone) and `repo_trusted`; the configuration change is a `config_changed` whose removals read as `null` leaves.

#### 4.6.22 Footprints and the overlap plan

A wave's tasks that touch the same files collide when they merge: each one after the first updates its branch, and a big shared file can turn a wave into a queue of conflicts. A task's *footprint* says which files it is expected to touch; the *overlap plan* groups tasks by the source files they share into clusters, and runs each cluster so they collide less: strongly coupled tasks are *collapsed* into one task (a bundle), a strong pair that cannot bundle is *chained* (one after the other), and a big cluster is *capped* in flight.

**Wave-file keys.** Per task (`wave-file.schema.json`): `files` (the footprint: paths and globs), `footprint: { confidence, unresolved? }` (how `files` was found: `listed`, every entry of the issue's Files list resolved against the repository tree; `resolved`, some did not, named in `unresolved`; `guessed`, no Files list, so the tree paths the issue body names; `none`, nothing), `plan: { cluster?, by, why }` (the cluster, the strategy that placed the task: `collapse`, `chain`, `cap` or `independent`, and why in one line) and, for a bundle, `issues` (every issue it closes; it MUST contain `issue`, MUST NOT repeat one and MUST NOT name an issue another task closes, each refused with a path-qualified error). A file's own plan is read from these keys: tasks with the same `plan.cluster` form a cluster, a bundle is a collapse, an `after` entry whose `why` names it (`after <task>: …`) is a chain, and a cluster with more tasks than `plan_cluster_in_flight_max` is capped.

**Writing the plan.** A generator of wave files from issues (the reference one is `wave-from-issues`) SHOULD resolve each issue's Files list against the tree of the release branch (`origin/<branch>`, else the local branch; with neither, every footprint is unresolved and it says so), plan the wave, and write `files`, `footprint`, `plan`, `issues` and the chains' `after` into the file, with the plan in words as a header comment. Collapse is automatic: there is no confirmation step, and the owner edits the generated file to plan differently. It SHOULD offer footprints without a plan (no bundle, chain or `plan`), and the plan without a file.

**Validate and run.** A supervisor's `validate` and `run` SHOULD print, after the placement line, the file's own plan in words (one line per cluster, the independent tasks, the expected branch updates), one `note: …` per place where the planner would plan the file's tasks differently (advisory: the file is kept as written; only when the tree can be read), and the footprint line (`footprints: 24 listed, 2 guessed (#333, #313); 11 entries unresolved (…)`, counted per issue), or `footprints: none (…)` when no task has `files`.

**At submit.** For each task without `files`, the supervisor reads its issue's Files list and resolves it against the release branch's tree (read once per wave; without one, the list is kept as written, `guessed`). Those files are journaled, never written into the wave definition. Footprints are read on the first submit only: a task a later version adds without `files` has none, and raises no alarm. An issue that cannot be read is never silent: the supervisor journals `alarm_raised { alarm: "footprint_unavailable", task, why }` and `run` prints a warning. Each `task_queued` of a wave-file task carries `issues` (a bundle), `files` (the file's, else the ones read), `footprint` and `plan`. Right after the tasks queue, once per plan version that has a plan, the supervisor journals `wave_planned { clusters }`, the file's own clusters with their hot files sized from the tree. The wave state carries the plan in `overlap_plan`, each task's cluster in `tasks[].cluster`, and the keys above in `spec.tasks[]`; `status` prints one `plan:` line per cluster under the wave's header.

**Running a bundle.** A bundle is one agent's job and one PR. A supervisor that spawns its agent SHOULD fetch every issue of `issues` (each refused on a mismatched number, as one issue is), put them all in the agent's copy of the issue under one header naming them and the plan's `why`, list them in its brief with one `Closes #<n>` line per issue (GitHub closes only the first issue of a shared `Closes #a, #b` line) and one changelog fragment per issue, and write `issues` into its assigned identity (§6.5). Before accepting the implementer's PR it SHOULD check the PR body for those lines and steer the implementer once with the missing ones; after that the PR is accepted and the lines still missing (`artifact_verified { closes_missing }`) go to the fix-up's findings. The fix-up then runs even when every reviewer approves, and its own PR body is checked the same way, with its own one steer; lines still missing after that are journaled on its `artifact_verified` and left to the release PR. The digest (§4.6.16) ships each issue of a merged bundle, all with the bundle's one PR.

#### 4.6.23 Merge train

Under `merge: auto` (§4.6.17) with `autopilot.merge_train` on (§4.6.4, default `true`), a supervisor MAY merge several gated tasks of one wave as one *merge train*, instead of one at a time through the merge queue: it integrates their gated heads onto one branch, gates that branch once and merges it once with a merge commit, so that every member PR, whose head the merge contains, reads as merged. With `autopilot.merge_train` off, everything in §4.6.17 holds unchanged.

- **Formation.** A train forms on a release branch with no merge in flight (§4.6.17: no task holds its turn, none is merging, and no other train forms or runs there) whenever at least two of the queue's tasks qualify: at `merge_ready`, gated at their current head, with a PR, and not handed to a human (`manual`). A single qualifying task takes the ordinary turn. The members are the first qualifying tasks, at most four, of the wave of the task that would take the turn next (the *front* task), in the order the ordinary turn would take them (queue order, a refused task that loses its place last), with the tasks of the front task's overlap-plan cluster first.
- **Names.** A train is the wave's synthetic task `train-<n>` (§4.6.16; `n` counts the wave's trains from 1, as journaled by `train_started`), integrated on the branch `volley/train/<wave>-t<n>`. While a train forms or runs, its members stay in the merge queue as `merging` and none of them takes the ordinary turn; a train holds the release branch as a merge in flight does.
- **The merge.** The supervisor merges only the train's PR, only at the head the train was gated at, and only into the release branch it targets, with a merge commit and GitHub's head guard: `gh pr merge <n> --merge --match-head-commit <head>`, never a squash, an administrator override, auto-merge, a rebase or a branch deletion. Right before merging it reads the PR again and does not merge one retargeted away from the release branch, whose head moved, that is closed or a draft; a refusal is classified as §4.6.17 classifies any merge's. A reference supervisor holds this in its authority fence: that merge command is allowed only with a token minted after the train's evidence is written, naming the train, its PR and head, the release branch and each member's task and gated head; the gate's squash token never allows a merge commit, and the train's token never allows a squash.
- **Journal.** `train_started { train, tasks, heads, release_sha }` when the train integrates its tasks' gated heads onto the release branch at `release_sha`; `train_merged { train, pr, merge_sha, tasks }` when its PR merged, landing every member; `train_failed { train, why, tasks }` when it failed (a conflict integrating it, or red CI on its head), its tasks going back to the merge queue (§4.6.3).

*Informative: how the reference supervisor runs a train.* A supervisor never pushes or merges a branch itself, so an agent integrates the train and the supervisor treats the train as a task:

- **The train task.** It forms a train when the task that would take the turn next was gated behind the release branch (one up to date takes the ordinary turn), and holds the release branch for it from `train_started` until `train_merged` or `train_failed` (an owner's out-of-band merge of a member is refused meanwhile, naming the train). Its synthetic task `train-<n>` is queued with `issue: 0`, `synthetic: true`, the title `Train: #310, #312` and `train: { members }`, on the pipeline `[implement, merge_ready]`, and admitted ahead of ordinary tasks like a flake's fixer (§4.6.16).
- **The integrator.** Its implement step runs an `integrator` agent. Its inputs name the release branch and the commit the train starts at, the train branch, and each member in merge order with its PR, branch, gated head and issues. It cuts the train branch from that commit, merges each member's gated head with `git merge --no-ff` (never a rebase, a force-push or an amended member commit), resolves conflicts keeping each PR's intent, runs the repository's gates, pushes, and opens one PR against the release branch titled `train: #310, #312` with one `Closes #<n>` line per member issue. Before its `done` it publishes `result` type `integrate` `{ merged: [pr…], conflicts: [{ pr, files }], touched: [file…] }`, `touched` being every file its conflict resolutions changed.
- **Verification.** The train head must contain every member's gated head (`git merge-base --is-ancestor`), descend from the release commit the train started at, and its PR must target the release branch. A head lacking a member is steered once, then a fix-up agent on the train branch merges the missing members. CI runs once on the head, held and classified as any task's (a red head gets a fix-up on the train branch). When `touched` holds a file a member's reviewer flagged, that reviewer role reviews the train head, scoped to the resolution diff; otherwise the gate journals `alarm_raised { alarm: "train_reviews_skipped", why }`, which is not an invariant breach. The gate writes the train's evidence (its members and their heads, its conflicts and resolved files, its CI) and only then allows the merge.
- **Completion.** Once its PR merged, each member journals `merged_by_supervisor { task, pr, head, merge_sha, by, via: "train", train_pr }`, its merge record, `merge_dequeued { why: merged }` and `stage_entered done`, and the train task is done. Each member PR is read again: GitHub reports one whose head the merge contains as merged; a member PR in any other state raises `alarm_raised { alarm: "train_member_open", task, pr }` and is never closed by the supervisor.
- **Failure.** An integrator that cannot merge a member (`blocked` or `failed`) opens `merge_conflict` about that member, carrying `train`, with the options `drop <member>`, `respawn`, `manual` and `cancel`; it does not park the gated member. Autopilot's answer is `drop <member>`, once per member: the train fails (`train_failed`, with the member as `dropped`) and is formed again without it, and the dropped member keeps its place in the queue and takes an ordinary turn later. A train merge refused `behind`, `head_moved`, `closed` or `retargeted` fails the train and its members queue again, a train being formed anew from the new release tip; a `transient` refusal keeps the release branch and is retried as any merge (§4.6.17). A train still red after `autopilot.ci_fixup_max` CI fix-ups fails, and the overlap-plan clusters of its members are put on `hold` (§4.6.22).

#### 4.6.24 Machine roles

Three long-lived processes make a deployment: the **broker**, the **supervisor** and the **Desk**. Each is a *machine role*, and each MAY run on any machine of the supervisor's pool (its own machine or a paired one, §4.6.14), independently of the other two. A supervisor keeps one record of where each runs and moves a role from one machine to another on an admin's request, one move at a time, health-checked, and rolled back when the new machine does not come up. Naming: "role" also means a broker role (§4.6.13) and an account role (§4.6.10); this section's are *machine roles*, on the topic `volley/_system/roles`, through the ops `role_plan`, `role_move` and `role_rollback`, and the CLI `volley role`.

| Role | What runs | What finds it |
|---|---|---|
| `broker` | the MQTT broker (§4.6.13), its MQTT and WebSocket listeners | everyone: each machine reaches it through its tunnel to the broker's machine, the Desk page over WebSocket |
| `supervisor` | the supervisor (`volleyd`) and its home (journals, config, account registry) | clients, only through the broker; it reaches each paired machine over ssh |
| `desk` | the Desk's web server | browsers and phones, at its address |
| `coordinator` | the owner's Claude Code Remote Control server, kept alive by the supervisor in a fixed directory on one machine | the phone and the browser by its stable name, the Desk by its link |

A machine's own record (§4.6.14, `kind`) stays the machine's statement about itself; the roles are the supervisor's. The `coordinator` role is not moved by `role_move` and is not in the record: its machine is the tunable `coordinator.machine`, and its state has its own topic (§4.6.25).

**The record.** `volley/_system/roles` (QoS 1, retained, `roles.schema.json`), published by the supervisor (`agent_id: "volleyd"`; a client ignores one from anyone else) at start and whenever it changes: `{ broker: { machine, address: { ssh, mqtt_port, ws_port }, lan }, supervisor: { machine }, desk: { machine, url, lan_url? }, version, updated_at, updated_by }`. Each `machine` is the supervisor's own machine name (`fleet.local_name`, §4.6.15) or a configured host (`hosts.<name>`, §4.6.4). `broker.address.ssh` is the ssh destination every machine's tunnel reaches the broker's machine at (null while the broker runs on the supervisor's machine and no move has named one), `mqtt_port` and `ws_port` its listeners there, and `lan` whether the WebSocket listener is open to the LAN (`volley setup --lan`). `desk.url` is the address devices open the Desk at: its private HTTPS address when the Desk is served on the owner's private network (`volley desk install --tailscale`), its LAN address then kept in the optional `desk.lan_url`. `version` counts the record's changes from 1; `updated_by` names who changed it last. The record is kept in the supervisor's home (the reference supervisor's `$VOLLEYD_HOME/roles.json`, written atomically). On its first start, without one, a supervisor writes the default: all three roles on its own machine, `address.ssh` null, the broker's ports as it reaches the broker, `lan` and the Desk's address as its install recorded them (`volley setup`; a recorded private address is `desk.url`, the LAN one `desk.lan_url`), else `false` and `http://localhost:5199`, with `updated_by: "volleyd-defaults"`. A record naming a machine that is neither is refused with its path (`supervisor.machine: "<name>" is neither this machine … nor a configured host …`); the supervisor then keeps publishing the last record it journaled. `volley role status [--json]` prints the retained record, one line per role (`desk        on <machine> (<url>)`); it needs the broker, not the supervisor, and with no record exits 1 with `no roles record: is volleyd running?`.

**Ops.** Admin ops on the account-op topic (§4.6.10), answered there like `setup_plan` / `setup_apply`; the supervisor refuses them on its mailbox.

- `role_plan { role, to, address?, lan?, terminal?, port? }` plans moving `role` (`broker`, `supervisor` or `desk`) to machine `to`, fresh each time, and changes nothing: `result: { role, from, to, plan_id, steps: [{ id, title, where }], blocked: [{ why, fix? }], warnings, terminal: [{ where, reason, command }], after }`, the steps each with the machine it runs on, what keeps the move from running now and how to fix it, the commands only a terminal on a machine can run (re-planned until done, as `setup_plan`'s), and what changes for the owner afterwards (a new Desk address to sign in at, the sessions on a machine the broker left). `address` (broker) is the ssh destination every machine's tunnel will reach the broker at, by default the target's `hosts.<name>.target`; `lan` (broker) whether its WebSocket listener is open to the LAN there, by default the record's; `terminal` (supervisor) the terminal the old machine re-pairs with (`cmux` or `tmux`); `port` (desk) the Desk's port there, by default 5199. A role already on `to` is refused (`<role> already runs on <to>`), so is an unknown machine.
- `role_move { role, to, address?, lan?, terminal?, port?, plan_id, drain?, reply_key }` plans again and starts the move only when the fresh plan's `plan_id` is the one sent, else refuses with an error that starts with `plan changed`; it refuses while the plan is `blocked`, while another move runs, and while the fleet is not quiet (below) unless `drain` is `true`. A `desk` move is answered when it ends: `result: { move_id, status }` (`done`, or `failed` with `step` and `rolled_back`), with the sign-in link for the new address sealed to `reply_key` as `{ link }` (an address too long for one sealed block: `{ token }`, and `result.link_base`, as `signin_link`'s). A `supervisor` move is answered as soon as it starts, `result: { move_id, status: "running", handing_over: true }`: its hand-over ends the old supervisor's broker connection, so it never answers after it. A `broker` move, and its rollback, are answered the same way (`rolls_back` added for a rollback), a moment before the first step stops the broker every connection runs through. With `drain`, waiting for quiet, the answer is `status: "planning"`. Its progress is the moves topic. The blockers that are only the fleet not being quiet are not digested into `plan_id`, so the plan shown moves once the fleet is quiet.
- `role_rollback { move_id }` undoes a completed move (`done`) within the retention window: the role goes back to the machine it came from, as a move does, under a new `move_id` named in `result: { move_id, rolls_back }`, and the move undone becomes `rolled_back`. A move that is not `done`, or whose kept copy is gone, is refused.

**Steps on a paired machine.** A step written `volley …` in this section runs on a paired machine as that machine's own checkout, `bun <volley_dir>/packages/volley-cli/src/cli.ts …`, as one step of the same `ssh -T <target> bash -s` (§4.6.14), never as a `volley` found on the machine's `PATH`; on the supervisor's own machine it runs as `volley …`.

**The Desk move.** Blocked while the target is not paired, is down, runs a volley older than the supervisor's (its record's `versions.volley`), has no `bun` on its ssh `PATH`, or has the port taken. Its steps: `install` there (`volley desk install --port <port> --broker-host <host>`, the Desk told the broker's host), `check` there (`volley desk check --url http://127.0.0.1:<port> --version <the supervisor's>`, the move's health check, retried a few times), `record` on the supervisor's machine, `signin` (the link above), then `unload`, the old Desk's service stopped and kept for a rollback, last, so a browser still at the old address keeps the Desk until then. A failing check uninstalls the new Desk; the old one never stopped. Every device signs in again at the new address.

**The supervisor move.** Preflight: a quiet fleet (or `drain`); the target paired, up, at the supervisor's version, with no failing `block` check, a `gh` login with write access and its Claude default profile signed in (its record's `auth`); ssh from the target to every other paired machine; and its terminal (cmux, else tmux; with neither, a warning that agents will not run there and `fleet.local_agents: never` on it). The old supervisor writes the move's hand-over record (`roles/<move_id>/handover.json` in its home), bundles what travels — its waves, config, pairing and usage registries, the roles record and the hand-over record; the account registry's `accounts.json`, `tokens.json`, `admin.json` and `coordinator.json`; the Claude profiles registry — never worktrees, logs, its own broker credentials, Claude sign-ins or profile directories, copies the bundle to the target over the same `ssh … bash -s` transport, and runs `volley role receive supervisor <bundle> --from <old> …` there: the target restores the files (keeping what they replace), drops `hosts.<target>` and sets `fleet.local_name` to its own name, stops its own machine record (`peer.json` `heartbeat: false`, its tunnel kept), rotates the `volleyd` login with the bundled admin login (the old process can never reconnect), installs and starts its supervisor, and prints a pairing code for the old machine last. The old supervisor then unloads its own service. The new supervisor finds the hand-over record at its start and continues the same move on the same topic: its own retained status `working`, the old machine re-paired as a paired machine with `tunnel: none` (the broker stays there; until ssh-to-cmux, its agents run in tmux over ssh), then `record`. A failing re-pair ends the move `done` with a `warning:` line on that step: the owner re-pairs by hand. A receive that fails changes nothing on the target and ends the move `failed`; one that fails after the rotation has the old supervisor rotate its own login again and restart, so its service comes back. Waves stopped for the move come back `stopped` on the new supervisor and resume with the `resume` op (`volleyd resume <wave>`).

**The broker move.** Preflight: a quiet fleet (or `drain`); the broker on the supervisor's own machine, installed as `volley setup` recorded it (not in a container), its Dynamic Security state file and admin login readable there, and its MQTT port the one the moved broker listens on (1883); the target paired, up and at the supervisor's version, with mosquitto 2.1 or newer (one probe there, `volley broker probe`: its layout and version); ssh from the supervisor's machine and from every other paired machine to `address` (one `ssh -o BatchMode=yes <address> true` each; a paired machine that is down blocks the move, since its tunnel could not be re-pointed); and, with `lan`, the target's WebSocket listener port reachable from the Desk's host (an anonymous probe refused or accepted, not unreachable). On a target whose mosquitto belongs to root (a snap or the distribution package) the receive is a `terminal` command, `sudo volley broker receive ~/.volley/roles/broker/bundle.tgz --lan|--no-lan`, which the move waits for. Its steps: `stop` (the old broker, through its layout's service manager), `bundle` (its state file, the admin login and the choices; mosquitto's persistence never travels, so the new broker starts with no retained message), `copy` (to `~/.volley/roles/broker/bundle.tgz` on the target), `receive` (`volley broker receive <bundle>` there: the state file placed first, then `volley setup`'s security step on it, both listeners checked to refuse anonymous clients), `tunnel` (the supervisor's own machine reaches the moved broker through its own `ssh -L` at the broker's old port, and its service is pointed there), `health` (the supervisor logs in through it, reads the broker's version, and finds both listeners refusing anonymous clients), `retarget-<n>` (`peer_retarget` each paired machine at `address`, the target with `tunnel: none`; each must come `up` through the new broker within the grace), `desk` (the Desk told the broker's new host, `volley desk install --broker-host`), then `record` (`broker` names the target and `address`). A failing step undoes every step done, in reverse: each machine back on the tunnel it had, the own tunnel down, the old broker started. The supervisor and every client lose their connection at `stop`; the supervisor runs the move without one and reconnects through the new broker when it ends (the reference supervisor restarts), republishing every retained topic it owns, the move's included. The owner's own sessions on the supervisor's machine are the one client the move cannot re-point: the plan's `after` names the command that does (`volley setup --step claude-code --broker-url mqtt://127.0.0.1:<port>`). `role_rollback` of a broker move takes the own tunnel down, starts the old broker (its state file was never removed), checks it, puts each paired machine back on the tunnel it had before the move, tells the Desk the old host and records the broker back; the broker on the target keeps running until stopped there.

`peer_retarget` (§4.6.14) re-points a paired machine's tunnel at the broker's new address, a step of a broker move.

**The moves topic.** `volley/_system/roles/moves/<move_id>` (QoS 1, retained, `role-move.schema.json`): `{ move_id, role, from, to, status, steps: [{ id, title, where, status, line? }], since, error?, log_path? }`, republished at every change. `status` goes `planning` (waiting for quiet) → `running` → `health_check` → `done`, or ends `failed` (the health check or a step failed, and every step done so far was undone; or the supervisor stopped in the middle of the move, and its next start ends it `failed` with an `error` saying its steps were not undone) or `rolled_back` (a `role_rollback` undid it). Each step is `pending`, `running`, `ok`, `failed` or `skipped`, with its last line of output or why it failed in `line`. `log_path` names the move's log on the supervisor's machine. A supervisor that hands itself over to another machine (a `supervisor` move) leaves the topic to the new supervisor, which continues it. A move's `record` step makes the record name the new machine (`version` + 1, `updated_by` the requester); a step failing after it puts the previous placement back. The new Desk address, broker address or supervisor take effect for every client then.

**Quiet.** Moving the `supervisor` or the `broker` needs a quiet fleet: no wave `running`, `paused` or releasing and no supervised agent live or spawning anywhere, since worktrees, terminal sessions and every agent's broker address belong to one machine. `role_move` refuses otherwise, naming what is not quiet; with `drain: true` it waits instead: nothing new is admitted (as `peer_remove { drain }` closes a machine, §4.6.14), and the move starts when the last agent ends. Moving the `desk` never needs quiet.

**Retention.** What a completed move replaced (the old machine's files and its service, unloaded) is kept for 7 days, so a `role_rollback` can restore it; the supervisor removes it at its next start after that, with the move's retained topic. There is no tunable.

**Journal.** In `_system`: `roles_changed { by, roles }` whenever the record differs from the last one journaled (at the first start, and after a move or a hand edit of the file), `roles` being the new record; `role_move_started { by, move_id, role, from, to }`; `role_move_step { move_id, step, status, line? }` for each step that changes status; `role_move_completed { by, move_id, role, from, to }`; `role_move_failed { by, move_id, role, step?, error, rolled_back }`; `role_rolled_back { by, move_id, role, to }`. None carries a secret. A supervisor that does not implement the ops answers `unknown op '<op>'`.

#### 4.6.25 The coordinator role

The owner's working session is a Claude Code Remote Control server (`claude remote-control`), driven from a phone or a browser; its MCP server registers under the coordinator name the owner's waves bind to (§4.6.1, §6.2). A supervisor MAY keep that server alive as a machine role: on the machine `coordinator.machine` names (§4.6.4), in a fixed directory, restarted when it dies, its state retained on one topic. A supervisor that does not implement the role answers its ops `unknown op '<op>'`.

**The tunables.** `coordinator: { machine, dir, capacity, permission_mode, restart_backoff_s, allow_laptop }`. `machine` is `local` (the supervisor's own machine, or its `fleet.local_name`), a paired machine's `hosts.<name>` key, or `null`, the default: the role is off and nothing runs. `dir` (default `~/.volley/coordinator`) is expanded on that machine (`~` its home); a later version may pin an absolute path common to every machine, so nothing else may assume `~`. `capacity` (default 4) and `permission_mode` (default `acceptEdits`, one of the values `claude remote-control --help` lists) are the server's own flags. `restart_backoff_s` (default `[5, 30, 120]`) are the waits before each restart; `allow_laptop` (default `false`) the laptop rule below. A change applies at the next tick: a new machine (or directory) stops the session on the old one first and starts it on the new one; `null` stops it.

**The command.** The supervisor starts the server only from a script it renders and writes, `<dir>/.volley/coordinator.sh`, which MUST hold no secret: it changes to `<dir>`, exports `VOLLEY_AGENT_ID=coordinator` (each session registers as `coordinator-<suffix>`), `VOLLEY_COORDINATOR=<name>`, `VOLLEY_NAMESPACE`, `VOLLEY_BROKER_URL=mqtt://127.0.0.1:<port>` (the port that machine's agents reach the broker at: a paired machine's tunnel end, `hosts.<name>.tunnel.remote_port`), `VOLLEY_AUTH_DIR=<dir>/.volley/auth` (the login is the file there), `VOLLEY_HOOKS_COORDINATOR=1` and `VOLLEY_HOOKS_DIR`, puts that machine's `~/.volley/bin` first on `PATH`, and then runs `claude remote-control --continue` (a reattach to the session last recorded in that directory: Claude Code refuses `--continue` with the spawn flags, so it runs alone). When the reattach exits within a short grace (nothing was recorded), it runs `claude remote-control --name <name> --remote-control-session-name-prefix <name> --spawn same-dir --capacity <capacity> --permission-mode <permission_mode>`, and nothing else: `<name>` is the coordinator name `volley setup` recorded (the name the owner knows, the one waves bind to). A supervisor without a recorded name runs nothing. The script runs inside a detached tmux session named `volley-coordinator-<name>` (`tmux new-session -d -s volley-coordinator-<name> -c <dir> 'bash .volley/coordinator.sh'`), on every machine: Remote Control is a server, not a workspace anyone looks at. The supervisor types nothing into that session.

**The directory.** Before a start the supervisor writes, on that machine (a paired machine through its fenced ssh steps, §4.6.14): the script; `<dir>/.volley/auth/coordinator.json`, the coordinator login it holds (mode 0600, as a supervisor move copies it); `<dir>/.mcp.json`, the `volley` MCP server (`bun <volley checkout>/packages/volley-mcp/src/index.ts`, with the script's environment and no secret); `<dir>/.claude/settings.json`, `{ "enableAllProjectMcpServers": true }`, so that server loads without a question; Claude Code's folder trust for `<dir>`; and `<dir>/repos/<owner>/<name>`, a link to each repository's clone on that machine (§4.6.21), so a session there can work in a checkout.

**Supervision.** Each tick the supervisor compares what the config wants (a machine set, its record in and its tunnel not down; `local` is always up) with what runs (`tmux has-session` there). A missing session it ran is a death: it starts it again after `restart_backoff_s`'s next wait (the last repeated; the ladder starts over after a server that was up 10 minutes), and a third death in a row, each within the waits' total of its start, leaves the role `failed` with the server's last screen lines, until `coordinator_restart`. A start that fails (its directory cannot be prepared, the launch is refused, the supervisor holds no coordinator login) counts as a death on the same ladder, `last_error` saying why. While its machine is down the role is `stopped` (`last_error` `<machine> is not up`, no `session_url`); when the machine is back, a session still running there is adopted. A supervisor that starts while the session already runs adopts it; a supervisor that stops leaves it running. The supervisor reads the server's screen after a start: the first `https://claude.ai/code/…` URL on it is the role's link (`session_url`); without one, the name is the handle (the phone lists the session by it). A question on the screen that nobody answers unattended — Claude Code's folder trust, or the first run's `Enable Remote Control? (y/n)` — is reported (`needs_terminal`, with how to attach in `last_error`), never answered.

**The topic.** `volley/_system/federation/coordinator` (QoS 1, retained, `coordinator-role.schema.json`), published by the supervisor (`agent_id: "volleyd"`, channel `_system/federation`, type `coordinator`; a client ignores one from anyone else) at start and on every change: `{ machine, name, state, since, session_url?, restarts, last_error?, needs_terminal?, dir? }`, `state` one of `starting`, `running`, `restarting`, `stopped`, `failed`; `dir` is the directory on that machine, absolute, absent until the supervisor has expanded it there (its machine down before the role was first placed on it). While `coordinator.machine` is `null` the topic is cleared (an empty retained payload).

**The laptop rule.** A machine record (§4.6.14) MAY say `laptop: true` (a battery is present: Linux `/sys/class/power_supply/BAT*`, macOS `pmset -g batt` naming `InternalBattery`). A laptop sleeps and travels: `config_set` refuses `coordinator.machine` naming a machine whose record says so, at `coordinator.machine` with `<name> is a laptop: it sleeps and travels; set coordinator.allow_laptop: true to host the coordinator there anyway`, unless `allow_laptop` is `true`.

**Ops.** Admin ops on the account-op topic (§4.6.10): `coordinator_restart` (the session ended if it runs, the backoff, a stop and a failure cleared, and started again) and `coordinator_stop` (the session ended; it stays stopped, across supervisor restarts, until `coordinator_restart`), each answered with the topic's payload; `coordinator_status`, the payload (null: off), also answered on the mailbox as a read. The supervisor refuses `coordinator_restart` and `coordinator_stop` on its mailbox. The CLI is `volley coordinator status | open [--browser] | restart | stop`; `open` prints the link, or with none exits 1 with `no link yet: open the Claude app and pick "<name>"`.

**Notices.** A supervisor that runs the role SHOULD tell the owner when the link changes and when the role fails, as owner-only `notice` items (§4.6.18). A new `session_url` opens `n-coordinator-link` (title `Coordinator on <machine>: open it`, `question` and `pointers.link` the link); a `state: failed` opens `n-coordinator-failed` (title `Coordinator on <machine> stopped`, `question` the last error and how to restart it). Before opening one, the supervisor answers the open notices it replaces `superseded` (`by` its own id, `where: { kind: autopilot }`): a new link supersedes the link and failure notices, a failure the link notice, the role turned off both; a payload without a `session_url` after one with it supersedes the link notice, and the role back to `running` the failure notice. A notice already open saying the same (a supervisor restart adopting the running session) is not opened again.

**The handoff text.** A fresh coordinator session knows nothing of the fleet. When a registry entry arrives from its hooks (the re-publish carrying `model_source`, sent once its mailbox session exists, §4.4) whose `coordinator` is the role's name and whose `cwd` is the role's `dir` or under it, while the role is `starting` or `running`, the supervisor SHOULD send that agent one mailbox `steering` message (`from_agent_id` its own id) saying what it is and where it runs, the running waves (each with its repository and tasks done), the open inbox items (id and title), and the previous coordinator session's agent id when known, ending `Use /volley and /volley-issues as usual.` It sends it once per session: it keeps the sessions it greeted (`$VOLLEYD_HOME/coordinator-sessions.json` in the reference supervisor, the last 50), and the newest of them is the next session's previous one.

**Not promised.** A turn in flight when the server dies is lost (the restart reattaches to the session, not the turn). The role runs on one machine: continuity across machines (failover, a replica) is not specified here.

#### 4.6.26 Wave cleanup

When a wave ends, everything a supervisor made for it is removed from every machine; what it keeps is named with the reason and, where there is one, the command that removes it. Cleanup never deletes unmerged work, a registration or clone the owner made, or a person's account.

**The ledger.** What cleanup acts on is derived from the journals, never from a separate file. An item is *owned* (made for the wave, removed) or *borrowed* (exists for the wave but was not made for it, or outlives it: kept and named). Owned: the agents' worktrees, workspaces and tmux sessions (`agent_spawned { worktree, host, remote?, workspace, terminal }`), their spawn locks, the processes under those worktrees (below), the agent branches (`agent_spawned.branch`, release-stage branches included), the agent logins a retired agent left behind (§4.6.13), and a registration or account whose creating event names the wave (`repo_added { wave }`, `account_created { wave }`) together with the managed clones the supervisor made for that registration (below). Borrowed: the repository registration made without `wave` and its clones, the wave's `release_branch` (a supervisor never creates it), merged agent branches' copies on GitHub, and every account made without `wave`. A borrowed registration is named only when no other wave on file uses it: `kept repo <owner/name>: added by <account> (not for a wave) — volley repo remove <owner/name>`.

**Every machine.** A paired machine's items are cleaned through its ssh steps under the cleanup consent: its sessions (`tmux kill-session`), the branch evidence reads, `volley peer cleanup --json --worktree <abs>… --yes` (its processes), `git worktree remove`, then `volley peer cleanup --json --repo <abs> --branch <name>… --clone <abs>… --yes` (its proven branches and owned clones), run in that machine's own checkout. A machine that cannot be reached is not "nothing to do": its items are kept, `(<machine> unreachable; cleanup runs again next tick)`, and a later run finishes them.

**Processes.** A process belongs to a worktree when its `--mcp-config=` lies under it (the agent itself) or its current working directory does (a dev server, watcher or REPL the agent started there). A supervisor reads working directories from `/proc/<pid>/cwd` on Linux and from `lsof -a -d cwd -F pn` on macOS, and stops each process with SIGTERM, a grace, then SIGKILL. Retiring an agent (§4.6.4) uses the same rule on the supervisor's machine, so a dev server ends with the agent that started it. Never a process outside the listed worktrees, and never one under a worktree a live agent of the wave still holds.

**Branches.** An agent branch is deleted only when the wave's journal names it (`agent_spawned.branch`), its task's PR is journaled merged (`merged_by_supervisor`, `merged_by_operator`, a train member's `merged_by_supervisor`, or a release stage's `release_stage_verified`) and the branch's tip (`git rev-parse` where it lives) equals the head those events record; a commit pushed after the merge keeps it (`kept branch <b>: 1 commit after the merged head`), and a cancelled or failed task's branch is always kept (`unmerged`). The delete is `git -C <repo> branch -D <branch>` (`-D`: a squash merge is never an ancestor), each under a token minted for that one branch; on a paired machine the supervisor proves the merge from the box's own `git rev-parse` and names each proven branch to `peer cleanup --branch`, which deletes the box's copy; the box never picks a branch itself. Copies on GitHub are the merge's business (`autopilot.delete_branch`). The wave's release branch is never deleted: `kept release branch <b>: merged into <default> — git push origin --delete <b>` when GitHub reads it fully merged (`ahead_by: 0`, a read-only compare), else `kept release branch <b>: <n> commits not on <default>`.

**Managed clones.** A clone is owned only when its registration is owned, the supervisor's own clone run made it after that registration (`repo_clone_run { ok: true, cloned: true, path }`; an adopted clone or one the run found there reads `cloned: false`), and `path` is still that machine's managed `<fleet.repo_root>/<owner>/<name>`. Before deleting it, cleanup reads it: a clean work tree, no stash, and every local branch either at its upstream or an agent branch this run proved merged; otherwise it is kept with the reason (`kept clone <path>: 2 unpushed commits on <b>`, `dirty work tree`, `stash`). The delete is `rm -rf <path>` under a token minted for that one journaled path (on a paired machine, `peer cleanup --clone <path>`, which re-runs the checks there), journaled `repo_clone_removed { machine, slug, path, wave }` in `_system`; the registration's `repo_remove` runs after the clones are gone, and only on the machines whose clone went. Nothing else is ever `rm -rf`'d: a worktree is always `git worktree remove`d.

**The result.** Every run prints one `kept <kind> <what>: <why>[ — <command>]` line per kept item, then one summary line: `cleaned <wave>: <n> worktrees (<m> on <machine>), <n> sessions, <n> processes, <n> branches, <n> logins; kept <k>` (zeros omitted; `nothing to clean` when nothing was removed; `would clean` on a dry run). Each run journals `wave_cleaned { by, removed, kept[], summary, dry_run, task?, tasks? }` in the wave's journal, `removed` counting `worktrees`, `sessions`, `processes`, `branches`, `logins`, `repos`, `accounts` and `clones`, each kept item `{ kind, host, what, task?, why }`; a whole-wave run's counts include the per-task runs since the last whole-wave run, and its `tasks` names the tasks that were `done` or `cancelled` when it ran (it covered them: no per-task pass follows for them). The wave state's `cleanup { at, removed, kept, summary, task? }` is the last real run's (a dry run does not change it), except that a per-task run never replaces a whole-wave run until the wave resumes or ends again; `volleyd status` prints `cleanup: <summary>` and the Desk shows a `cleaned` chip with the kept items.

**When it runs.** With `cleanup_on_end` on (the default, §4.6.4) the supervisor runs cleanup itself: a task's items (worktrees, sessions, processes, locks, its merged branch) on the tick after the task is `done` or `cancelled` with none of its agents live, journaled `wave_cleaned { task }`; the whole ledger (logins, owned registrations, accounts and clones too) once the wave is `complete` or `stopped` and none of its agents is live, the stop grace over. A task that was unfinished at the time (`merge_ready`) is cleaned when it ends. A run that kept an unreachable machine's items runs again. Archiving (§4.6.20) runs one last pass first, and its answer repeats the kept items (`result.kept`). `volleyd cleanup <wave> [--yes] [--force] [--all] [--by <name|agent-id>]` stays the manual path (the mailbox op `cleanup { wave, dry_run, force?, all? }`, the owner only, answered with the printed `lines`); the manual path identifies the caller as every owner-gated command does (`--by`, else the caller's session, else `VOLLEY_COORDINATOR`); on an auto-cleaned wave it prints `nothing to clean`. While the supervisor is down the command reads its files directly and leaves logins, registrations and accounts for the supervisor (`kept …: daemon down`).

## 5. Lifecycle states

Agents publish lifecycle state transitions on the `status` channel. The retained value at `volley/<ns>/<id>/status` always reflects the agent's current state.

### 5.1 State diagram

    spawning → registered → working → ( done | blocked | failed ) → reaped

### 5.2 State definitions

- **`spawning`** — agent process started; broker connection in progress. Published by the MCP/CLI on connect, before `vol_register` returns.
- **`registered`** — agent has called `vol_register`; registry entry exists at `_system/registry/<id>`.
- **`working`** — agent has begun task execution. First user-controlled state.
- **`done`** — agent completed its task successfully. Terminal state.
- **`blocked`** — agent cannot proceed without external input. Terminal state, but agent process MAY remain alive awaiting mailbox guidance.
- **`failed`** — agent encountered an unrecoverable error. Terminal state.
- **`reaped`** — agent's broker connection terminated (clean shutdown OR crash detected via LWT). Terminal state, published by the broker (via LWT), by the agent itself, or by a supervisor that deletes the agent's login (§4.6.13, no LWT follows a delete). In the last case the supervisor then clears the agent's retained `status`, so only live subscribers and its journal see the `reaped`.

### 5.3 Transition rules

- Transitions MUST be linear; agents MUST NOT publish a `working` after a terminal state in the same session.
- Because `status` is a retained channel (§4.1), all status publishes — including terminal states — are retained and visible to late-attaching observers.
- An agent MAY skip `working` if it terminates immediately after registering.
- An agent's LWT MUST be configured to publish `{type:"reaped", reason:"disconnect"}` so crash detection works without agent cooperation.

## 6. Registry (discovery)

Agents register themselves on a reserved retained topic so observers can enumerate the live agent set.

### 6.1 Topic

    volley/_system/registry/<agent_id>

### 6.2 Payload

```json
{
  "schema_version": "0.1",
  "agent_id": "issue-42-fix-7a3f",
  "namespace": "default",
  "parent_id": "coordinator-abcd",
  "wall_time": "2026-05-14T02:11:23.000Z",
  "channel": "_system/registry",
  "type": "registered",
  "payload": {
    "capabilities": ["implements-issue", "writes-tests", "runs-mvn-verify"],
    "cwd": "/private/tmp/example-issue-42",
    "model": "<model id>",
    "title": "#42 fix the login redirect loop — implementer",
    "links": { "repo": "example-org/example-repo", "issue": 42 },
    "started_at": "2026-05-14T02:11:23.000Z"
  }
}
```

An agent a supervisor launched under a Claude account profile (§4.6.11) adds `claude_account` (the account id, or `primary`), from its assigned identity (§6.5).

A coordinator session MAY add `coordinator`: a stable name in the agent-id grammar (§2.2), chosen by the person once (the reference MCP server reads it from `VOLLEY_COORDINATOR` and returns it from `vol_register` beside `agent_id`). The agent id of an MCP server changes at every restart; the name does not, so a supervisor lets a wave's `owner` (§4.6.1) be the name and binds it to the newest live registry entry carrying it (§4.6.1). An agent launched with a supervisor-assigned identity (§6.5) never carries one, whatever its environment holds.

An agent MAY add `pid` (the process id of the publisher, e.g. the MCP server) and `surface` (the terminal pane it runs in; the reference MCP server copies cmux's `CMUX_SURFACE_ID`). Several sessions can share one `cwd`; a harness hook running beside one of them identifies that session's own entry by its `surface`, and never adopts an entry carrying a different `surface` (§4.3).

An agent MAY add `title`: one line (1 to 120 characters, no line break) saying what it is working on, such as the task or issue it was dispatched for (`#42 T3 fix the login redirect loop — spec review`). It MAY add `links`, references for that purpose: `{ repo?, issue?, pr? }`, where `repo` is `owner/name` and `issue` / `pr` is a number (an issue or pull request in `repo`) or an `http(s)` URL. Both are OPTIONAL; an entry without them is conforming. An agent id says nothing about purpose (a dispatched agent's id is often just its prefix and a random suffix), so a dashboard SHOULD show a wave task's own title (§4.6.1 `spec.tasks.<id>.title`) when the agent has one, else this `title`, as the agent's purpose, with the agent id as a secondary detail. The reference MCP server takes both as `vol_register` arguments.

### 6.3 Requirements

- Conforming agents MUST publish a registry entry retained, QoS 1, before publishing any channel other than the initial `spawning` status.
- The registry entry MUST be re-published on any change to `capabilities`, `cwd`, `model`, `title`, or `links`.
- When the LWT fires, the broker publishes `reaped` to the agent's `status` topic but does NOT clear the registry topic — that allows tools to inspect the agent's last-known state after death. Observers SHOULD filter out reaped agents in default views.

### 6.4 Enumeration

To enumerate all registered agents, subscribe to:

    volley/_system/registry/+

The broker delivers all retained registry entries; filter by namespace on the `payload.namespace` field.

### 6.5 Assigned identity

A supervisor that spawns an agent usually needs to know the agent's id *before* the agent registers (to wait on its status, address its mailbox, or render it). The §2.2 prefix + random-suffix mechanism makes that impossible, so a supervisor MAY pre-assign a literal id by writing `.volley/agent.json` into the agent's working directory before starting it (`spec/schemas/agent-identity.schema.json`):

```json
{
  "agent_id": "w1-t1-implementer-1",
  "namespace": "dispatch",
  "parent_id": "coordinator-ab12",
  "wave": "w1",
  "task": "T1",
  "role": "implementer",
  "broker_url": "mqtt://localhost:1883"
}
```

- Only `agent_id` is required. A conforming MCP server that finds this file in its working directory MUST use `agent_id` verbatim (no suffix) and MUST use `namespace`, `parent_id` and `broker_url` when present.
- Values in the file take precedence over the corresponding environment variables (`VOLLEY_AGENT_ID`, `VOLLEY_NAMESPACE`, `VOLLEY_PARENT_ID`, `VOLLEY_BROKER_URL`); keys absent from the file fall back to the environment, then to defaults.
- `agent_id`, `namespace` and `parent_id` MUST satisfy the §2 grammar. A server MUST refuse to start on an out-of-grammar `agent_id` (`INVALID_AGENT_ID`) or on a malformed file, naming the file path in the error, rather than fall back silently to a generated id.
- Uniqueness is the supervisor's responsibility. The RECOMMENDED form is `<wave>-<task>-<role>-<attempt>`, lowercased (e.g. `w1-t1-implementer-1`); a supervisor retry increments `<attempt>` so a dead agent's retained topics are never overwritten by its successor.
- An assigned identity is the one exception to §2.2's unique-id-per-process-start rule. A restart of the MCP server in the same working directory (a harness reconnect, a crash and restart) reuses the assigned id and starts a new session in the §5.3 sense; supervisors MUST tolerate a fresh `spawning` after a terminal status on an assigned id. The file pins one id to one working directory, so do not run two agent sessions there at once.
- Supervisors SHOULD keep the file out of commits by adding `.volley/` to the repository's `info/exclude` (`git rev-parse --git-path info/exclude`) when the working directory is a git worktree.
- `broker` (`{ "username", "password" }`, both strings) carries broker credentials minted for this agent by the supervisor, conventionally with `username` equal to `agent_id` so an ACL can pin the agent to its own topics (§11.5). Every client that runs with the identity (MCP server, CLI, hooks) MUST prefer it over `VOLLEY_AUTH_USERNAME` / `VOLLEY_AUTH_PASSWORD`. The file then holds a secret: supervisors SHOULD create it mode `0600` and revoke the credentials when the agent retires.
- `wave`, `task` and `role` are informational for tools that read the file (hooks, the supervisor itself); the MCP server does not interpret them.
- `issues` (integers, at least two) names a bundle's issues (§4.6.22), the task's issue first; it is informational like `wave`, and absent for a task with one issue.
- `claude_account` names the Claude account profile the supervisor launched the agent under (§4.6.11; `primary` for the default profile). A conforming MCP server that finds it copies it into its registry entry (§6.2).

## 7. Last Will and Testament

MQTT's Last Will and Testament (LWT) mechanism provides crash detection without agent cooperation.

### 7.1 Requirements

Conforming agents MUST configure an LWT on broker connect with:

- **Topic:** `volley/<ns>/<agent_id>/status`
- **Retain:** true
- **QoS:** 1
- **Payload:** a valid `status` envelope with `type: "reaped"` and `payload.reason: "disconnect"`

### 7.2 Behavior

When the broker observes the agent's TCP connection drop without a clean DISCONNECT (timeout, kill -9, network partition), it publishes the LWT message to the will topic. The retained `status` topic flips to `reaped`, and any observer subscribed to `volley/+/+/status` receives the transition.

### 7.3 Keep-alive

Agents SHOULD use an MQTT keepalive of 60 seconds (the default). Longer keepalives delay crash detection; shorter keepalives increase broker load.

### 7.4 Clean shutdown

On clean shutdown, agents MUST publish a terminal `status` (`done`, `blocked`, or `failed`) before calling MQTT DISCONNECT. A clean DISCONNECT suppresses the LWT. A `blocked` published as that terminal status MUST carry `payload.reason: "shutdown"`, so observers can tell it from a live agent awaiting guidance (§5.2, §7.5).

### 7.5 Presence

An agent's presence is its retained `status`. It is **online** while that status is `spawning`, `registered`, `working` or `blocked`: a connected client published it and the will has not fired. It is **offline** once the status is `reaped` (§7.2), `done` or `failed` (§7.4), a `blocked` whose `payload.reason` is `"shutdown"` (left by a clean shutdown, §7.4, which suppressed the will), or when no status exists. Observers MUST NOT require any periodic message to keep an agent online: a quiet connection is online, and the MQTT keepalive (§7.3) is the client library's, not a Volley message. A coordinator name's (§6.2) presence is that of the newest agent carrying it whose status is live. A broker stopped cleanly publishes its connected clients' wills before it exits and persists them (measured on mosquitto 2.1.2), so presence survives a broker restart; only a broker killed outright can leave a stale live status, which the name's next session corrects by binding.

## 8. Versioning

### 8.1 Semantic versioning

The Volley protocol follows semantic versioning on its `schema_version` field:

- **0.x** (pre-1.0): wire compatibility NOT guaranteed across minor versions. Tooling SHOULD pin to an exact minor.
- **1.0+**: wire format is frozen on the major. Breaking changes require a major bump (2.0, 3.0, ...).

### 8.2 Major version handling

Implementations MUST reject envelopes whose `schema_version` major version is unrecognized. The error code is `SCHEMA_VERSION_MISMATCH` (§9).

A v0.x implementation MAY refuse minor versions it does not recognize (e.g. v0.1 implementation refusing v0.2 messages). v1.0+ implementations MUST NOT refuse later minors of the same major.

### 8.3 Forward compatibility

Per §3.3, receivers MUST accept envelopes containing unknown fields and MUST NOT error on them. This permits adding new optional fields to the envelope or to per-channel payloads without a major version bump.

## 9. Error codes

Conforming implementations MUST return one of the following error codes on failure paths. Implementations MAY define additional codes under the `IMPL_*` prefix.

| Code | Meaning |
|---|---|
| `BROKER_DOWN` | Broker unreachable or refused connection. |
| `INVALID_TOPIC` | Topic does not match the grammar in §2. |
| `INVALID_AGENT_ID` | `agent_id` does not match the grammar in §2.2. |
| `TIMEOUT` | A blocking call (subscribe, query) exceeded its timeout without receiving messages. |
| `SCHEMA_VERSION_MISMATCH` | Envelope `schema_version` major version is unsupported. |
| `NOT_REGISTERED` | An operation requiring prior registration was attempted before `vol_register`. |
| `RESERVED_TOPIC_WRITE` | Attempt to publish to a reserved namespace from user space. |
| `AUTH_FAILED` | Broker refused the connection's credentials, or anonymous access (MQTT CONNACK 4/5, MQTT 5 reason 0x86/0x87). Distinct from `BROKER_DOWN` so a client can tell "fix your credentials" from "start your broker". |

Volley v0.1 ships these MCP tools (defined in detail in implementation docs):

`vol_register`, `vol_publish`, `vol_query`, `vol_subscribe`, `vol_list_agents`, `vol_tap`, `vol_send_mailbox`

The following tool names are **reserved** for v0.2+ async-subscription paths and MUST NOT be redefined by conforming v0.1 implementations:

- `vol_subscribe_async`
- `vol_recv`
- `vol_unsubscribe`

Adding these in v0.2+ MUST NOT break v0.1 sync clients.

## 11. Conformance

A conforming Volley implementation MUST satisfy all MUST-level requirements in this document. The following is a non-exhaustive summary cross-referencing earlier sections:

### 11.1 Conforming agents MUST

- Register on startup before publishing any channel other than the initial `spawning` status (§6.3)
- Publish a terminal `status` (`done` | `blocked` | `failed`) before clean exit (§5.3)
- Configure an MQTT LWT for crash detection (§7.1)
- Reject unknown `schema_version` major versions (§8.2)
- Use the QoS and retention values in §4.1 for reserved channels (§4.3)
- Match `agent_id` and `namespace` against the grammar in §2 (§2.2)

### 11.2 Conforming agents SHOULD

- Publish `progress` milestones at meaningful checkpoints (§4.3)
- Include `parent_id` if spawned by another Volley agent (§3.2)
- Use a 60-second MQTT keepalive unless deployment requirements dictate otherwise (§7.3)
- Publish a retained `result` before terminal `status` (§4.3)

### 11.3 Conforming agents MAY

- Subscribe to their own `mailbox` and respond to steering messages (§4.1). An agent that does MUST keep a persistent subscription or drain on a stable clientId, and SHOULD `ack` each message it receives (§4.4)
- Spawn sub-agents with `parent_id` set to their own `agent_id` (§3.2)
- Define user channels under `_user/*` (§4.2)

### 11.4 Conforming brokers MUST

- Be an MQTT v3.1.1 or v5 broker, or equivalent (transport-agnostic — see §1)
- Support retained messages, wildcard subscriptions (`+`, `#`), QoS 1, and LWT
- Support username/password authentication in CONNECT (it MAY also admit anonymous clients, §11.5)

The reference localhost deployment (non-normative) requires authentication on every listener (`examples/mosquitto-auth/`), because any local process and any web page (through a WebSocket listener) can reach a localhost broker.

### 11.5 Conforming brokers MAY

- Require username/password or mTLS authentication. Clients MUST honor `VOLLEY_AUTH_USERNAME` / `VOLLEY_AUTH_PASSWORD` when set, and the `broker` block of an assigned identity (§6.5), which takes precedence over them. A refused CONNECT is `AUTH_FAILED` (§9) and MUST NOT echo the password
- Enforce ACLs on reserved namespaces and per-agent channels. The reference roles (`examples/mosquitto-auth/roles.json`, §4.6.13) let an **agent login** (username = agent id) write only its own channels and registry entry, lease requests, and the mailboxes of the fixed steering identities it acks (§4.4); let steering clients write any mailbox; treats the `coordinator` identity as operator-level (it may also write any agent's standard channels and registry entry, because a coordinator's agent id is random-suffixed); and keeps every topic §4.6 defines under `volley/_waves/*` (including `_waves/_config`) writable by the supervisor only. Because mosquitto's `+` also matches the `_waves` and `_system` levels, that protection covers the topics §4.6 defines, not arbitrary topics under those prefixes. A denied publish is dropped silently by MQTT 3.1.1 brokers, so a client cannot rely on a publish error to detect it

### 11.6 Conforming supervisors MAY

Supervisor topics are informative in 0.1 (§4.6), so nothing here is required of an agent or a broker. A supervisor that implements autopilot is held to the MUST-level rules of the sections it implements:

- Answer decisions itself from a published policy table, within remediation budgets (§4.6.16). It MUST NOT answer a decision whose kind is in `autopilot.owner_only`, MUST answer only with one of the decision's own `options`, and MUST journal `decision_auto_resolved` before the `decision_resolved` it makes, or `decision_escalated` for a decision it leaves open (§4.6.16)
- Classify a red head before asking anyone, and fix a flake through a synthetic task (§4.6.16)
- Publish one retained digest per wave (§4.6.16; SHOULD, for a supervisor that runs waves unattended)
- Merge a gated PR itself under `merge: auto` (§4.6.17). It MUST merge only a task at `merge_ready`, only at its gated head and only into the release branch the PR targets, MUST NOT force a merge GitHub refuses, MUST journal `merged_by_supervisor`, and MUST keep at most one merge in flight per release branch (§4.6.17). Under `merge: manual` it MUST NOT merge on its own; only the owner's explicit merge of one task does (§4.6.17)
- Run a repository's release playbook once every task of a wave is settled (§4.6.19). It MUST NOT answer `stage_go`, `release_go` or `release_pr_ci_failed` itself, whatever its policy table says, MUST NOT run a ship stage or merge the release PR without the owner's `go`, and MUST NOT deploy to production as part of a train's automatic run (§4.6.19)
